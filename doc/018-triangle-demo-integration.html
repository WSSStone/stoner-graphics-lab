2. 本期核心摘要

本期已建立独立 StonerDemo 目标、可重现 shader 输入、显式 runtime mode、Renderer→RHI 三角形命令执行、原生 Vulkan 离屏绘制、GLFW-backed surface/swapchain 可见呈现、确定性耐久监测与三平台 CI 配置。macOS 本机 smoke 已人工确认 RGB 插值三角形。

学习重点是“证据分级”：Mock/deterministic 能证明控制流，native-headless 能证明真实 driver/device/command，surface、swapchain 和人工可见像素 smoke 才证明 presentation；完整交付还需要规定帧数、恢复周期、同 run ID 日志和跨平台证据。

3. 上下文与依赖

  • 前置：016 Window/Input、012 Vulkan Pipeline/Shader、015 Forward Rendering，以及 Core 时间、内存和诊断约定。
  • 编译期外部依赖：GLFW、Vulkan headers/loader、macOS MoltenVK；Linux CI 使用 Mesa Lavapipe。
  • 边界：Application/RHI/Renderer public headers 不暴露 Vk* 或 GLFW 类型，原生细节留在 private/backend。

二、目标与边界

1. 业务与功能目标

  • 引擎开发者可以用 CLI 选择 deterministic、validate、interactive 或 native-headless 模式。
  • 输入是窗口/帧数/采样/内存预算和 SPIR-V；输出是稳定 result、exit code、runtime snapshot 和验证报告。
  • 任一初始化或帧阶段失败只拥有一个 primary failure，仍执行逆序清理。

2. 架构目标与定位

StonerDemo composition root
  -> Application: window + input strategy
  -> Renderer: forward plan + frame executor
  -> RHI: backend-neutral resources/commands/results
  -> Vulkan private backend: native instance/device/offscreen/presentation

Validation monitor <- runtime snapshot + RSS + timing + diagnostics

Demo 是跨层集成点，不是新建一套渲染框架。FForwardFrameExecutor 接受 RHI contract；FVulkanNativeContext 封装原生 API；FWindow 只对外提供 opaque platform window。

3. 边界与非目标（约束）

  • 不引入场景、材质、光照或资产管线：三角形是端到端探针，不是内容 demo。
  • 不接受 native-headless 作为可见成功：它没有 surface/swapchain/present。
  • 不做 Android 可见验证：当前支持范围是 Windows/macOS 真实呈现和 Linux CI 软件 Vulkan。
  • 不实现 pipeline disk cache、shader hot reload 和多帧并行：它们会扩大里程碑的变量。

三、交互与产品设计

1. 用户使用路径

# deterministic endurance
StonerDemo --mode validate --frames 4096 --report report.txt

# Linux CI real Vulkan without a window
StonerDemo --mode headless-vulkan --frames 4096 --report lavapipe.txt

# final visible gate
StonerDemo --mode interactive --frames 10000

失败路径例如 SDK/runtime 不可用、shader 无效、report 不可写，都转换为稳定阶段、结果和 exit code，而不是 silent fallback。

2. 核心规则与状态机

Constructed -> Initializing -> Running
Running -> PresentationPaused (zero drawable)
PresentationPaused -> RecreatingPresentation -> Running
Any active state -> Failing -> ShuttingDown -> Stopped

可见模式必须是 native，零 extent 期间继续 poll event 但不 acquire/submit/present；recovery 更换 generation，防止 stale image 继续被引用。

3. 失败模式与调试入口

  • --inject-failure 覆盖 window/runtime/shader/upload/pipeline/acquire/record/submit/present/memory/report/shutdown。
  • FDemoDiagnostics 保存第一失败，并过滤 native address，便于跨运行 byte-stable 对比。
  • Validation/018/completion.md 记录已验证事实和外部门禁，不伪造 screenshot/log。

四、技术架构与关键决策

1. 技术栈与基础设施

C++20 传统 header/source 分离，SCons 4.10.1，GLFW 3.4-compatible，Vulkan 1.3-compatible，macOS MoltenVK，Linux Mesa Lavapipe，GLSL 通过 glslangValidator 离线生成并用 spirv-val 验证。依赖缺失是可控 unavailable，不影响 deterministic build/test。

2. 关键信息

2.1 模块对应关系

模块责任所有状态
FStonerDemoApplication配置、生命周期、帧协调、逆序关闭presentation/triangle/frame children

2.2 控制流与资源流

load checked-in SPIR-V -> create/upload vertex buffer
-> create target/render pass/framebuffer/pipeline
-> transition to color -> clear -> bind pipeline/buffer
-> viewport/scissor -> draw(3) -> transition to present/offscreen final
-> submit + fence wait -> sample runtime/RSS -> reverse destroy

2.3 诊断与可视化

Runtime snapshot 记录 mode、adapter、software marker 和 live-object counts；不记录 pointer/Vk handle。Report 记录 run ID、frame count、first-present/recovery timing、memory medians 和 final-zero，便于 CI 结构化校验。

3. 架构决策记录 (ADR)

(1) 显式区分 deterministic、native-headless 和 visible native

决策：每个模式输出可验证 runtime proof。被否决：native 失败时自动 fallback，因为会产生虚假绿灯。后果：CI 能说清自己究竟证明了什么。

(2) 原生 API 留在 backend private

决策：RHI 用 description/result/interface，Application 使用 opaque window。被否决：在 public contract 传 VkSurfaceKHR。后果：未来 DX12/Metal backend 不需改 Renderer 和 Demo 协调语义。

(3) Shader 产物入库

决策：GLSL 和经验证 SPIR-V 同时入库。被否决：每次构建强制下载/运行 compiler。后果：离线环境也可构建，但修改 GLSL 时必须同步再生成并验证。

六、设计巧思与最佳实践

1. 当前业务场景的最佳实践

  • Stable first failure：清理阶段的次生错误不覆盖根因，对图形初始化的长失败链尤其重要。
  • Final-zero snapshot：不只检查帧内峰值，还在逆序清理后检查每类 live object。
  • Median memory gate：比单点 RSS 更能抵抗 allocator/OS 噪声，同时保留 absolute 和 relative 两类预算。
  • Opaque native bridge：窗口系统能为 backend 提供平台信息，又不迫使 Application 依赖 Vulkan。

2. 优化方案与收益

已实现的优化主要是工程可验证性：checked-in shader 降低构建环境波动，有界帧数与 watchdog 限制 CI 挂死，稳定 report 减少跨平台差异噪声。未来优化铺垫包括 frame contexts、image-indexed synchronization 和 generation invalidation，它们会在真实 swapchain 完成后转化为 GPU/CPU 并行收益。

3. 已知限制与后续演进

当前 native context 已完成 GLFW window 到 Vulkan surface/swapchain、FIFO present、semaphore/fence、out-of-date/suboptimal 归一化和 generation-aware recreation。仍有一项代码架构缺口：可见帧目前由 native context 直接记录 Vulkan draw，尚未消费 FForwardFrameExecutor 的 backend-neutral RHI bindings。验证方面，真实 resize/minimize/restore 尚未完成 20-cycle 计时，Windows 仍缺同等运行，macOS/Windows 也未保留正式同 run ID 图像与日志。当前单帧 fence 设计优先保证正确性，未来可扩展为 per-frame/per-image 并行上下文。

七、编程语言知识点

1. 标准库接口与用法

  • std::unique_ptr：FWindow 独占拥有 driver strategy，实现文件外定义析构以允许 incomplete private type。
  • std::chrono::steady_clock：计算 first-present/recovery，避免系统时钟回拨。
  • std::filesystem/std::ofstream：report 路径和写入失败可观测。
  • std::vector + sort/median：保留有界采样，从首末各五个样本计算 median。

2. 语言特性与惯用法

enum class 防止 mode/stage/result 混用；RAII 和显式 Composite shutdown 共同保证 partial initialization 也能回收；条件编译 STONER_GLFW_AVAILABLE/STONER_VULKAN_NATIVE_AVAILABLE 将 SDK 差异锁在 implementation；safe default virtual method 使旧 mock 可渐进迁移。

3. 平台相关与编译器行为

Windows RSS 来自 Psapi，macOS 来自 Mach task_info，Linux 来自 /proc/self/statm；全部收敛到 Core 的统一 result。macOS Vulkan 需要 portability enumeration/MoltenVK，Linux CI 显式指定 Lavapipe ICD。MSVC/GCC/Clang 差异通过 CI matrix 而不是 public preprocessor API 处理。

八、软件工程知识点

1. 设计模式与架构模式

  • Strategy：IWindowDriver 在 GLFW 和 headless 间选择，上层 FWindow 规则不变。
  • Composite：Demo 统一管理 presentation/triangle/frame-context 子生命周期，逆序 shutdown。
  • Facade：FVulkanNativeContext 为集成测试提供小型原生能力面，隐藏 Vulkan 对象图。
  • State Machine：暂停/重建/运行显式化，避免 zero extent 变成隐藏 bool 组合。

2. 工程原则与方法论

分层和依赖倒置让 Renderer 只面向 RHI；契约式设计让 invalid shader/binding/stage 立即返回可诊断 result；确定性输出使 20 次重复运行可字节比较；YAGNI 使本期不引入 asset/material/scene 复杂性。

3. 测试策略与质量保障

边界测试覆盖 5,000/2,000 ms 精确门槛，negative path 覆盖所有注入阶段，lifecycle matrix 检查正常与部分初始化清理，headless 用于快速回归，native integration 用于防止 mock-only success，public-header grep 防止 backend type 泄漏。

九、渲染、引擎与图形 API 学习笔记

1. 本期核心概念拆解

  • Swapchain 不是普通 texture array：它由 presentation engine 和应用共同拥有，acquire/present/out-of-date 构成独立生命周期。
  • Image layout/transition：一张 image 用作 color attachment 和 present source 时有不同使用约束，Renderer executor 记录跨 pass transition。
  • Synchronization：acquire semaphore、render-finished semaphore 和 fence 解决 presentation engine、GPU queue 与 CPU frame reuse 之间的三方顺序。
  • Runtime proof：适配器名称/software marker/live counts 是测试证据，但不是像素证据。

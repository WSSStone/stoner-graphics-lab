023 - Material & Shader Assets

状态：本地实现完成，等待三平台 CI · 更新：2026-07-30 · Roadmap Phase 023 · 层级：Asset / Renderer / Application / Vulkan

一、文档与上下文信息

1. 基础元数据

2. 本期核心摘要

本期把 Feature 014 的进程内 Material/Shader 记录升级为稳定 Asset：一个 FShaderAsset 表示完整逻辑 Program，包含 stages、permutations、interface 和 backend/profile payload；FMaterialAsset 与 FMaterialInstanceAsset 用 typed soft reference 表达 shader、texture 和 parent。三个 JSON schema 均可 bounded parse、canonical write、round trip，并以 canonical bytes 生成版本证据。

最值得学习的是“身份、内容、运行时对象”三者不能混为一谈。AssetId 表达逻辑对象，digest 表达某次 source/payload bytes，Renderer snapshot 表达某次显式转换。即使 Point 与 Spot 的 vertex SPIR-V 完全相同，它们仍拥有不同 identity；即使 Registry 中资产被替换，旧 snapshot 仍代表原 source manifest。

3. 上下文与依赖

023 依赖 020 的 identity、registry、resolver/importer 与 execution lease，依赖 021 的 Texture typed reference，并保持 014 的 material/shader 行为。本期为 024 glTF material slots、025 cooker/manifest 和 027/031/032/033 backend-tagged shader payload 奠定 contract。Asset production 只编译依赖 Core；Renderer/Application/Demo 是组合与适配层，Backend 只理解 Core/RHI bytecode。

二、目标与边界

1. 业务与功能目标

开发者可编写版本 1 的 .shader.json、.material.json 与 .material-instance.json。Loader 在成功时发布 immutable payload、metadata、canonical definition 与 source versions；失败时返回稳定 EAssetResult 与归一化 diagnostic。渲染调用方显式选择 backend/profile，再把 selected program 与 flattened material 转为自包含 Renderer snapshot。

2. 架构目标与定位

authoring JSON + GLSL/SPIR-V
              |
              v

       -> validation -> selection/resolution -> source manifest
              |
              v

Schema、logical identity、typed dependency、payload bytes、target tags 和 inheritance 属于 Asset contract。yyjson、文件 resolver 与 repository layout 是 private/composition concern。Renderer 拥有 Feature 014/RHI 映射；Backend 只接收 owned bytecode description。

3. 边界与非目标（约束）

  • 不做 runtime shader compilation 或 shader graph：本期只选择预编译 payload。
  • 不做 cooked binary、manifest、DDC 或 package：由 025 统一解决发布期产物。
  • 不做 async manager、cache、hot reload 或自动 snapshot 更新：由 026 管理请求与版本替换。
  • 不做 MSL/DXIL producer：schema 已保留 backend/profile slot，027/031 再提供真实 payload。
  • 不让 Asset 创建 GPU module：保持 CPU-only boundary，并避免 Vulkan 假设污染未来 backend。

三、交互与产品设计

1. 用户使用路径

Load(definition, resolver) -> FShaderAsset + dependencies
Select(shader, backend=Vulkan, profiles=[vulkan-1.3])
    -> FSelectedShaderProgram + complete source manifest
ConvertShaderAsset(selected) -> FShaderAssetSnapshot

Load(material/instance) -> ResolveMaterial(lookup)
    -> flattened FResolvedMaterialAsset
ConvertMaterialAsset(resolved, shader snapshot)
    -> FMaterialAssetSnapshot

失败路径不会留下半个 output：digest mismatch、wrong stage、ambiguous profile、missing parent、cycle、type-changing override 或 manifest version conflict 都在 destination replacement 前失败。调试优先查看 stable result、stage、subject 与 JSON pointer，再运行 focused suite。

2. 核心规则与状态机

definition:
Read -> Parse -> Schema -> Normalize -> Semantic Validate
-> Optional Dependency Load -> Runtime-ready Validate -> Publish

shader target:
validate request -> profile[0..N] in caller order
-> first complete unique set wins
-> ambiguity at current profile fails; no cross-backend fallback

material instance:
leaf -> pre-visit parent chain -> root
-> validate depth/cycle/types -> apply overrides root-to-leaf
-> merge chain + shader + texture versions -> publish

Program 必须是合法 graphics 或 compute stage set。Source-only program 可 inspect/serialize，但不能冒充 runtime-ready。Material parent 是 Material 或 MaterialInstance 的精确 tagged union；最近 override 获胜，缺失 dependency version 使 render-ready resolution 失败。

3. 失败模式与调试入口

  • InvalidDefinition：closed schema、duplicate decoded key、invalid token/type；看 JSON pointer。
  • DefinitionLimitExceeded：definition、depth、value、text、array 或 schema count 在 model allocation 前超限。
  • DependencyMismatch：typed identity、locator、digest、producer、stage 或 entry 与 bytes 不一致。
  • TargetUnavailable/AmbiguousTarget：检查 request profile 顺序和完整 stage set，不会自动评分或跨 backend fallback。
  • UnresolvedDependency/ParentCycle：检查 source manifest 的 chain、shader 与 texture version。
  • 仓库漂移：运行 verify_repository_shader_assets.py，输出使用逻辑相对路径且稳定排序。

四、技术架构与关键决策

1. 技术栈与基础设施

C++20、传统 public/private header/source、SCons 4.10.1。yyjson 0.12.0 作为带 checksum/license/upstream 证据的 private C dependency。Repository shader 为 checked-in GLSL 与 SPIR-V；没有运行时编译器。macOS 本地可运行 strict Debug/Release 与 fallback/native-unavailable contract，真实 native 证据由支持的 CI runner 提供。

3. 架构决策记录 (ADR)

(1) 一个 Shader Asset 表示完整 Program

决策：stage 是 Program 内部 record/dependency，不是独立顶层 program。理由：permutation、interface 与 backend target 只有在完整 stage set 上才可验证。否决：每 stage 一个 Asset 会把组合正确性推给调用方。后果：Program schema 更丰富，但 selection 能正确构造 pipeline-ready snapshot。

(2) Profile 顺序由调用方提供

决策：同 backend 内按 request 顺序取第一个唯一完整匹配。否决：隐式评分会让新 profile 改变旧设备选择结果。后果：策略显式且确定；能力协商仍可由上层构造 profile list。

(3) Immutable snapshot 不监听 Registry

决策：转换深拷贝并记录 source versions。否决：live pointer/callback 会引入跨层生命周期竞态。后果：旧 snapshot 稳定；026 必须显式调度新转换与 handle swap。

(4) Backend 不拥有 shader 路径

决策：Application/Demo mount resolver，Renderer 产出 RHI description，Backend 只创建 native module。否决：Backend path concatenation 绑定 repository layout 且绕过 Asset digest。后果：Vulkan、未来 Metal/DX12 可消费同一 identity/selection contract。

六、设计巧思与最佳实践

1. 当前业务场景与业务模型的最佳实践

  • 逻辑身份不等于内容去重：相同 payload digest 可用于 cache，但不得抹掉不同 Program/stage identity。
  • 先 preflight 后 model allocation：untrusted local JSON 的 depth/count/text 在建立复杂 C++ object 前受限。
  • Manifest 是 snapshot 的 provenance：它同时证明 program、source、payload、parent、shader 与 texture 的精确版本。
  • Source-only 是合法 authoring state：inspect 与 round-trip 不要求 runtime payload；render-ready validation 单独负责。
  • 全部发布操作是 transaction：loader/importer/library/conversion 都先构造临时结果，最后一次替换 destination。

2. 优化方案与收益

已实现 immutable shared payload、request-local dependency dedup、排序 manifest、一次性 ShaderLibrary batch validation、无 Registry callback snapshot 和无全局 parser/cache，主要收益是确定性、线程隔离、调试性和 API 稳定性。未来 025 可用 digest/manifest 建 DDC，026 可合并 async request；这些优化不要求修改当前 identity 与 snapshot contract。

3. 已知限制与后续演进

当前只有 JSON source definition、GLSL source 与 Vulkan SPIR-V payload；没有 cooker package、reflection tool、runtime compile、hot reload 或 shader cache。Native deferred execution虽然移除了 path ownership并集中 shader module rollback，但其大函数仍包含资源、pipeline、command、readback 与 probe 职责，应在 027 Metal 前继续拆分。

七、编程语言知识点

1. 标准库接口与用法

std::span 传递不拥有的 definition/payload view；std::shared_ptr<const T> 保存 immutable Asset payload；std::variant 表达 typed material parameter；std::optional 表达可选 subresource/parent；std::filesystem 只在 composition/test resolver 处理物理文件；std::thread 验证八路 immutable reader；std::sort 固定 manifest 与 diagnostic 顺序。

2. 语言特性与惯用法

RAII registration token/execution lease 防止 importer/resolver 执行期间被卸载；move semantics 发布 canonical bytes 与 payload；enum class 对 stage/backend/format/result fail closed；[[nodiscard]] 强制处理 validation/transaction 结果；typed soft reference 以模板约束 Asset type 而不持有 live object。

3. 平台相关与编译器行为

Canonical output 不使用 locale-dependent stream formatting，路径不进入 identity/report。MSVC、Clang、GCC 共享相同 schema/model contract；yyjson warning 只在其 C translation unit 隔离。SPIR-V validation 直接检查 word/header/OpEntryPoint，因此不依赖某平台是否安装 Vulkan runtime。

八、软件工程知识点

1. 设计模式与架构模式

Resolver/Importer 是 Strategy；yyjson 与 Renderer conversion 是 Adapter；AssetId/version/snapshot 是 Value Object；load/validate/select/convert 是 compiler pipeline；Registry batch 与 destination swap 是 Unit of Work/transaction；repository verifier 与 native suites形成 Contract Test。

2. 工程原则与方法论

Dependency Inversion 让 Asset 只依赖 Core；Interface Segregation 使 Backend 只接收 RHI bytecode；YAGNI 推迟 cooker/cache/hot reload；Design by Contract 对 type、stage、entry、digest、profile 与 version 逐项验证；deterministic output 使 schema 可作为未来 DDC key；defensive parsing 限制损坏输入的时间与空间成本。

3. 测试策略与质量保障

Valid/invalid corpus 做 equivalence partitioning；exact/first-above 做 boundary testing；golden digest 防 canonical 漂移；failure category 防 first-error 漂移；rollback tests覆盖 transaction；八路 reader 与 TSan 配合检查共享状态；repository verifier 是独立 Python inventory oracle；full regression 确保迁移没有改变 triangle/deferred 行为。

九、渲染、引擎与图形 API 学习笔记

1. 本期核心概念拆解

  • Shader Program Asset：pipeline 所需完整 stage/interface/permutation，而不是一个文件。
  • Target profile：比 backend 更窄的编译目标；同 Vulkan 仍可有不同 capability/profile。
  • Source manifest：类似 build provenance，证明 snapshot 精确消费了哪些版本。
  • Material flattening：把 authoring inheritance 转为 Renderer 可直接验证的单值对象。
  • Native bytecode boundary：Backend 创建 API module，但不决定 Asset identity、文件位置或 fallback policy。

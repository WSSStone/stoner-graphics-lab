025 - Asset Cooker & Derived Data

状态：完成 · 更新：2026-08-15 · Roadmap Phase 025 · 层级：Tools / Asset / Core

一、文档与上下文信息

1. 基础元数据

2. 本期核心摘要

本期把 020–024 的 source Asset 转换为可发布的 cooked generation。独立的 StonerAssetCooker 可以 plan、clean cook、incremental cook、validate 与 inspect；它构造依赖图、固定输入快照、计算 derived key、复用或修复 DDC、生成 canonical manifest，并通过 immutable generation 与原子 current pointer 发布完整结果。

最值得学习的是 build cache 与 runtime package 不是同一件事。DDC entry 是可丢弃、可重建的派生数据；published generation 是必须独立验证、原子可见的部署边界。两者由 AssetId、version 与 digest 串联，却拥有不同的信任模型和生命周期。

3. 上下文与依赖

025 消费 020 的 identity/registry/extension、021 的 image/texture、022 的 KTX2 cook、023 的 material/shader 与 024 的 static model typed payload。它为 026 Runtime Asset Manager、028 Meshlet Derived Data 和 030 Streaming/Residency 提供稳定 cooked contract。编译方向保持 Tools/AssetCooker -> Asset + Core；runtime 模块不得依赖 Tools，Asset 仍只依赖 Core。

二、目标与边界

1. 业务与功能目标

开发者给定 source root、selection、target profile、output、DDC 与 worker count，即可得到确定 generation。未变化节点复用验证后的 DDC；损坏 entry 被隔离并重建；发布前失败不会改变 current generation；发布后的 output 可在 source 和 DDC 都移除后独立严格验证。命令统一使用稳定 exit category、stable reason 和可规范化 JSON report。

2. 架构目标与定位

Source files + target profile
             |
             v
Tools/AssetCooker: discover -> graph -> snapshot -> schedule
             -> DDC lookup/cook/install
             -> generation image -> validate -> atomic publish
             |                              |
             v                              v
Asset public cooked contracts          Core durable file/lease
             |
             v
Future runtime Asset Manager reads generation

Runtime -X-> Tools/AssetCooker
Asset   -X-> RHI / Renderer / Application / Backend

Target profile、derived-key evidence、payload envelope、manifest 与 current pointer 属于 Asset 公共 contract，未来 runtime loader 不需要链接 Tool。图调度、DDC layout、quarantine、publication 与 CLI/report 属于离线 Tool。durable write、no-replace move 和 lease 是可复用 Core primitive。

3. 边界与非目标（约束）

  • 不做 runtime async Asset Manager：025 只产出与验证 cooked generation，026 接管 request、handle 与 cache。
  • 不做 package/archive：当前目录布局优先支持可检查性，打包容器由后续阶段设计。
  • 不做 remote DDC、eviction 或 GC：先证明本地 immutable entry 与竞争收敛。
  • 不做 streaming/residency：chunk priority、CPU/GPU budget 和 eviction 属于 028。
  • 不做 editor database 或 hot reload：source discovery 是一次 request 的固定快照。
  • 不让 Tool contract 泄漏到 runtime：避免游戏目标携带 importer、CLI 与 publication policy。

三、交互与产品设计

1. 用户使用路径

StonerAssetCooker plan ... --normalized-report
  -> read-only graph/key/cache decision; no output/DDC/scratch mutation

StonerAssetCooker cook ... --clean
  -> snapshot -> typed cook -> DDC install -> immutable generation
  -> strict validation -> atomic Current.json replacement

StonerAssetCooker cook ...
  -> validated DDC hits reused; corrupt entries quarantined/rebuilt

remove source + DDC
StonerAssetCooker validate --output ... --strict-files
  -> generation remains independently deployable

2. 核心规则与状态机

DDC: Miss -> Stage -> Lease -> Install -> Hit
     Invalid -> Lease -> Quarantine -> Cook -> Install
     Invalid -> another writer repairs -> Re-query -> Reuse winner

Publication: Build image -> Validate -> Acquire lease
             -> Install generation -> Replace Current pointer
             -> Post-commit audit

Any pre-commit failure: old Current remains authoritative
Post-commit audit warning: new complete Current remains authoritative

Plan 严格只读。Derived key 包含 source/dependency version、importer/cooker/codec version、payload schema、effective settings 和 relevant profile digest；不相关 profile 字段不得造成误失效。成功 generation 的 manifest 与 payload 自描述且 content-addressed。

3. 失败模式与调试入口

  • Profile/argument：closed schema、overlapping roots、非法 worker/timeout 在写入前失败。
  • Source changed：snapshot pin 后再次校验，变化时返回 transient category，不发布混合版本。
  • DDC corrupt：查看 quarantine failure digest 与 stable reason；普通 cook 重建，strict validate 失败。
  • Publication：failure injection 穿过 stage、payload、manifest、install 与 pointer replace 边界。
  • Concurrency：lease timeout 有界；crash 后 OS 释放 ownership；等待者重新查询 winner。
  • 入口：Validation/025/reports/、normalized report、focused suites 与 cross-platform runner。

四、技术架构与关键决策

1. 技术栈与基础设施

C++20、传统 public/private header/source、SCons 4.10.1。CLI orchestration 使用 Python 标准库与参数数组启动子进程，不使用 shell。Asset-private yyjson 实现 canonical JSON typed codecs；现有 KTX/WAMR/cgltf/MikkTSpace/stb producer 由 Tool 经 public Asset extension 调用。Feature workflow 覆盖 Windows/macOS/Linux Debug、strict Release、Linux ASan/UBSan 与 TSan。

2.2 数据与控制流

Discovery 产出 typed assets 与物理 source 集合；graph 固定 reachable nodes 与拓扑序；snapshot 固定 source digest；每节点计算 target decision 与 derived evidence。Scheduler 只在依赖成功后运行节点，先 lookup DDC，miss 才调用 cooker。全部 envelope 形成 canonical manifest；publisher 构造 scratch image，完整重读验证后才替换 current pointer。

2.3 诊断、报告与确定性

Normalized report 排除 host、timing、RSS 和 worker count，只保留稳定 command/result、summary、逐节点 decision、source/dependency evidence 与 diagnostic。Telemetry 不参与 deterministic digest。1-worker 与 8-worker、不同空目录和 20 次重复必须得到相同 generation 与 normalized bytes。

3. 架构决策记录 (ADR)

(1) DDC 与发布目录分离

决策：DDC 可隔离重建，generation 必须 immutable 且独立验证。否决：把 cache entry 直接当发布包。后果：多一次 image 构造，换来清晰信任边界。

(2) Derived key 使用完整 evidence

决策：source/dependency/producer/settings/profile 进入规范哈希。否决：mtime 受复制、时区与文件系统精度影响。后果：跨平台、跨目录可复现。

(3) no-replace install 加 OS lease

决策：唯一 stage 完整验证后持 lease 安装；已有等价 winner 就复用。否决：原地写最终目录。后果：并发 writer 收敛，crash ownership 由 OS 释放。

(4) Current pointer 是唯一可变点

决策：generation 永不修改，只原子替换小型 pointer。否决：覆盖当前 payload/manifest。后果：读者无需全局锁；成功 generation 暂不 GC。

(5) Plan 严格只读

决策：plan 可查询 cache，但不得创建 output、DDC 或 scratch。否决：有副作用的 dry run。后果：plan 只报告 would-rebuild，不暗中修复。

六、设计巧思与最佳实践

1. 当前业务场景与业务模型的最佳实践

  • 先固定输入再并发：并行只改变执行时序，不能改变节点看到的 source bytes。
  • 失败证据也 content-addressed：quarantine 以 failure digest 命名，不用时间戳表达原因。
  • 最终分类互斥：等待者复用 winner 后归类为 reused；过程由 stable reason 保留。
  • 发布前重读：writer 刚写完不等于磁盘满足 runtime contract。
  • normalized 与 telemetry 分层：确定性证据和性能观测不共享哈希域。
  • Tool 是 composition root：producer 经 Asset public extension 注册，runtime 不认识 CLI/DDC layout。

2. 优化方案与收益

已实现节点级 DDC reuse、并发竞争收敛、拓扑调度、content-addressed payload、read-only plan 与 bounded validation。收益是增量 cook 时间、失败可恢复性、跨平台确定性和调试质量。1,000 assets/5,000 edges benchmark 同时覆盖 plan、cached、validation 与 clean，防止小 fixture 掩盖复杂度退化。

3. 已知限制与后续演进

当前 DDC 只在本地目录，没有容量管理、远端传输或 trust domain；成功 generation 不清理；runtime 尚无 async request、handle、package mount 或 residency。026 将复用本期 manifest/envelope 管理 runtime 生命周期；028/030 将 meshlet、mip/chunk 与 budget 建在相同 derived evidence 上。

七、编程语言知识点

1. 标准库接口与用法

std::filesystem 处理 Tool-private path；std::span 传递 bounded bytes；std::shared_ptr<const T> 保存 immutable payload；std::atomic 生成 stage token 与共享失败状态；std::chrono 表达 lease timeout；std::future/std::thread 验证 writer；std::sort 固定 manifest 与 report 顺序。

2. 语言特性与惯用法

RAII 的 FPlatformFileLease 在 normal return、move 与进程退出时释放 native ownership；enum class 区分 lookup/install/result；[[nodiscard]] 强制处理文件与 contract 结果；move semantics 在验证完成后一次发布 payload/manifest；显式 result 保持无异常边界。

3. 平台相关与编译器行为

POSIX 与 Windows 各自实现 native ownership 与 rename/no-replace，public Core API 不泄漏 fd/HANDLE。路径、worker scheduling、host label 与 wall clock 不进入 identity。MSVC、Clang、GCC 共享小端 envelope 与 UTF-8 canonical JSON，CI 比较 normalized report 和 generation identity。

八、软件工程知识点

1. 设计模式与架构模式

Importer/Cooker/Codec 是 Strategy；typed codec facade 是 Adapter；profile/key/manifest 是 Value Object；graph + scheduler 是 build DAG；DDC install 与 publication 是 transaction；lease 是 scoped ownership；immutable generation + pointer 类似 MVCC snapshot；CLI runner 与 schema verifier形成 Contract Test。

2. 工程原则与方法论

Dependency Inversion 保证 Asset 不依赖 Tool；Single Source of Truth 让 semantic manifest 决定 generation；Design by Contract 对 bytes、identity、version、profile 与 limits fail closed；YAGNI 推迟 remote DDC/package/GC；reproducible build 排除时间戳、绝对路径和调度顺序。

3. 测试策略与质量保障

Golden fixture 检查 canonical bytes；mutation 覆盖 key 输入维度；15/30 corruption corpus 做错误分区；failure injection 穿过 commit boundary；process probe 验证 OS ownership；20-run 与 1/8 worker 做 metamorphic determinism；hard benchmark 约束时间/RSS；架构脚本用负向 fixture 证明规则真的会失败。

九、引擎与资产管线学习笔记

1. 本期核心概念拆解

  • Cook：把 authoring Asset 转成 target profile 的 runtime payload，不是复制文件。
  • Derived key：回答哪些输入事实完全相同才允许复用。
  • DDC：可丢弃的编译缓存，命中前仍须验证 evidence 与 payload。
  • Generation：互相一致、独立可验证的 payload 与 manifest 快照。
  • Atomic publication：读者只看到完整旧快照或完整新快照。
  • Relevant profile：只有真正影响 producer 输出的 target 字段进入 key。

027 - Native Metal Backend

版本 1.0 · 2026-08-21 · 已交付 · 原生 macOS RHI backend 与双架构验收通过
工程结论：Feature 027 不是把 Vulkan 调用翻译成 Metal，而是在同一套 RHI 契约下实现第二个真正独立的 native backend。Renderer、Application 与 Asset 不持有 Apple API；私有 Objective-C++ 实现独占设备、资源、命令、同步和 CAMetalLayer 生命周期。GitHub Actions hardware run 32394691067 在 revision 506e49e 上通过 arm64 与 x86_64 两条必需门禁。

2. 本期核心摘要

Feature 027 交付了覆盖当前适用 RHI 契约的 Metal 设备、buffer/texture/sampler、descriptor、render/compute pipeline、command、queue、同步、upload/readback、swapchain 等价物和窗口呈现。三角形与 deferred workload 仍从 Renderer 的 backend-neutral 描述出发，Metal Backend 只消费 RHI 数据；同一 workload 可独立在 Vulkan/MoltenVK 和 Metal 上运行并比较结果。

本期第二条主线是 production shader 路径。GLSL/SPIR-V 继续作为仓库权威输入，Tools-only SPIRV-Cross 确定性派生 MSL；macOS 再用离线 metal 与 metallib 生成 target-tagged native library。runtime 只接收已 cook 的 typed bytes 和 binding evidence，不读 shader 路径，也不进行运行时源码编译。

3. 上下文与依赖

  • Features 007-008 定义 backend-neutral RHI contract；027 通过第二实现检验这些抽象是否真的可移植。
  • Feature 016 提供 Application-owned window/view 借用边界；Metal 只在借用有效期内 attach 自己拥有的 layer。
  • Features 018-019 提供 triangle 与 deferred 的真实 workload、readback 与跨 backend 语义基准。
  • Features 023、025、026 提供 Shader Asset identity、cooked generation 与 strict-cooked runtime loading；Metal 不反向依赖 Asset。
  • Feature 028 将用真实可再分发内容贯通 Asset、Renderer、Vulkan 与 Metal，而不是继续扩张 backend contract。

二、目标与边界

1. 功能目标

开发者能够在支持的 macOS 上选择 Metal，运行已有 RHI workload、创建 production cooked pipeline、执行 GPU readback，并通过真实窗口呈现。非法资源组合、foreign/stale object、缺失 binding evidence、错误 payload/profile、drawable 暂不可用和注入失败都必须在明确边界上 fail closed。

2. 架构目标与定位

GLSL / SPIR-V
权威 Shader Asset
→
AssetCooker
MSL + metallib evidence
→
RHI / Metal
typed bytes + native execution

层次关系仍为 Backend -> RHI + Core。Asset 负责 CPU identity 和 cooked payload，Tools 负责离线变换，Renderer 负责组织 workload，Application 负责窗口；只有 Source/Backend/Metal/Private/*.mm 可以持有 Objective-C 与 Apple framework 对象。这个划分使 Metal 成为 RHI portability test，而不是新的跨层捷径。

3. 边界与非目标

  • 不做 iOS 生命周期：没有 UIKit、移动端 surface、后台切换或触摸输入。
  • 不做 Metal 专属渲染算法：mesh shader、ray tracing、MetalFX 等留给后续独立阶段。
  • 不把 GPU ownership 放进 Asset：metallib 是资产 payload，MTLLibrary 和 pipeline 是 Backend 对象。
  • 不允许运行时 shader compile：strict cooked 缺失或不兼容即失败。
  • 不假装跨 backend 二进制相同：比较的是归一化语义与图像容差，不是 Metal/Vulkan 内部布局。

三、交互与产品设计

1. 开发者使用路径

// Public call site sees only RHI and the C++ Metal factory contract.
FMetalBackendConfig Config;
Config.RuntimeMode = ERHIRuntimeMode::Native;

FMetalDeviceCreateResult Created = CreateMetalDevice(Config);
TSharedPtr<IRHIDevice> Device = Created.Device;

// Renderer submits the same RHI frame description used by Vulkan.
ExecuteDeferredFrame(*Device, FramePlan);
Device->WaitIdle();

生产路径先由 AssetCooker 生成带 profile、compiler、binding-map 和 digest 证据的 native payload，再由 runtime manager strict-cooked 加载。Renderer 深拷贝为 RHI shader module description；Metal pipeline creation 校验 payload format、target profile 和 native binding map 后才调用 Apple API。

2. 命令与呈现状态

Command: Initial -> Recording -> Executable -> Submitted -> Completed
Layer:   Detached -> Attaching -> Ready <-> Paused
         Ready/Paused -> Reconfiguring -> Ready/Paused
         Any live state -> Draining -> Detached
  • command 在提交前记录并验证 RHI intent，提交时才按 Metal encoder scope 编码。
  • resource owner identity、generation 与 live state 共同阻止 foreign/stale handle 被编码。
  • 零尺寸、最小化或 nextDrawable == nil 进入 bounded pause/skip，不忙等、不伪造成功。
  • shutdown 先停止 admission、排空 in-flight work，再 detach layer 和释放借用的 window/view 联系。

四、技术架构与关键决策

1. 技术栈与模块边界

实现使用 C++20 与 private Objective-C++20，ARC 管理 Objective-C 引用；最低目标为 macOS 12.0 / MSL 2.4。Metal、QuartzCore、Cocoa、Foundation 只链接到 macOS Metal target。SPIRV-Cross 固定为仓库 private Tools dependency；Windows/Linux 只执行 MSL 派生和架构验证，不接触 Apple SDK。

2. 关键模块对应关系

3. 架构决策记录（ADR）

(1) 私有 Objective-C++ 边界

决策：公开 header 保持普通 C++，Apple protocol 和 Cocoa 类型只出现在 private .mm。这样 Windows/Linux 可编译同一公共接口，同时 ARC 的强弱引用规则不会渗入 Core/RHI。metal-cpp 并不能消除 Cocoa layer 集成所需的 Objective-C++，反而会再引入一套 wrapper lifetime，因此未采用。

(2) 分解 native object，而非复制巨型 context

决策：资源、pipeline、command、queue、sync 和 presentation 分别实现，并共享小型 owner state。此前 Vulkan 集成已经暴露巨型 native context 在 ownership、失败回滚和测试隔离上的代价；第二 backend 借此把责任域切开，同时保留统一设备身份。

(3) 直接 binding 加版本化证据

决策：Feature 027 使用 direct buffer/texture/sampler binding。Tools 对 (stage,set,binding,type,array element) 只做一次确定性映射，并把 canonical digest 写入 cook evidence；RHI 搬运 backend-neutral map，Metal 只校验和消费。argument buffer 是优化选项，不应在 correctness 首期扩大 GPU-family 差异。

(4) 逻辑 barrier 到 encoder scope

决策：普通资源依赖 Metal tracked hazards，RHI barrier 仍验证 logical state；遇到 encoder 不允许跨越的 transition 时保守结束当前 encoder。Metal 与 Vulkan 的 barrier 模型不同，所以正确抽象不是逐 API 映射，而是让 RHI 描述可观察的顺序和可见性，再由 backend 选择合法机制。

(5) 跨架构而非架构推断能力

决策：arm64 与 x86_64 都是正式目标，但 GPU family、storage mode、format 和 binding limit 来自真实 MTLDevice 查询，不从 CPU 架构猜测。Apple Silicon 常见 unified memory；Intel runner 可能是离散、集成或虚拟设备，代码必须按 capability snapshot 行事。

五、实施与验证

1. 验证分层

层级证明内容不能声称的内容
deterministic三平台 build isolation、MSL/evidence 20 次一致、失败诊断一致不能声称 GPU 执行
native-offscreen真实 MTLDevice、command completion、GPU readback不能替代窗口呈现

cross-backend独立 Metal/Vulkan native evidence 后再按固定容差比较semantic oracle 不能充当任一 native 侧

2. 双架构验证职责

物理 M4 Pro arm64 lane 负责完整 native offscreen、production cook、strict-cooked triangle/deferred、真实窗口、failure、10,000 次生命周期和 Metal/Vulkan 对照。GitHub-hosted macos-26-intel lane 要求真实 x86_64 MTLDevice，并执行等价的 Metal-only native、strict-cooked、presentation smoke、failure 与 lifecycle gate。

为什么 Intel 不要求 MoltenVK 对照：该 hosted Intel 的 Apple Paravirtual device 可正常执行直接 Metal，但无法建立 MoltenVK Vulkan device。把 x86_64 Metal 成功绑定到 runner 不具备的 Vulkan capability，会把“第二 backend 是否正确”混同为“测试主机是否提供第三方兼容层”。跨 backend 对照仍由具备两套真实 runtime 的物理 M4 lane 强制承担。

3. 关键验收量

  • MSL derivation 与 production cook 各重复 20 次，identity-bearing digest 必须稳定。
  • 可见验收运行 3,000 帧并执行 20 个 resize/minimize/restore cycle。
  • 生命周期门禁执行 10,000 次；前 1,000 次 warm-up，随后每 100 次记录 RSS，共 90 个样本。
  • 允许增长为 max(16 MiB, 5%)，同时 terminal native ownership counters 必须归零。
  • native report 记录 OS、CPU architecture、真实 device identity、capability digest、shader evidence、probe 和 artifact digest。

六、设计巧思与最佳实践

1. 当前场景中的最佳实践

  • typed shader bytes：RHI 明确区分 SPIR-V 和 MetalLibrary；禁止把任意 bytes 填进 SPIR-V word contract。
  • evidence accompanies payload：payload digest、target profile、compiler tuple 和 binding policy 都参与兼容性判断。
  • record then encode：公共 command recording 不立即触碰 native encoder，错误可在提交前完整验证并确定性回滚。
  • owner state audit：每类 native object 都计入 inspection，failure injection 与 shutdown 可验证真正归零。
  • capability-correct CI：每个 lane 只声明其运行环境能够真实证明的内容，同时保证所有 requirement 都有明确 owner。

2. 取舍与收益

直接 binding、tracked hazards 和 macOS-only finalization 都是“先把 portable correctness 做实”的选择。它们牺牲了 argument buffer、untracked hazard 和跨平台 native library compilation 的潜在性能或便利，却显著减少首个 Metal backend 的状态空间。等 Feature 028 用真实内容暴露规模特征后，再以测量证据决定优化方向。

3. 已知限制与后续演进

  • GitHub-hosted Intel 是真实 Metal API/GPU readback 证据，但设备为 Apple Paravirtual device；实体 Intel Mac 仍是有价值的可选兼容性补充。
  • 当前 presentation 面向 macOS GLFW/Cocoa；iOS 需要独立 Application lifecycle 与 surface contract。
  • 当前 binding map v1 以 direct binding 为主；未来 argument buffer 必须作为新 policy/version 并保持旧 cooked generation 可读。
  • Feature 028 才会用 licensed artist-authored glTF、PBR material 与 1K/2K texture 验证 source-to-cooked-to-visible 的实际组合。

七、编程语言与 API 知识点

1. Objective-C++ 与 ARC

.mm 允许同一 translation unit 使用 C++ ownership 与 Objective-C protocol。ARC 管理 id<MTLDevice>、CAMetalLayer* 等引用，但 C++ shared owner state、submission retention 和析构顺序仍由引擎明确控制。ARC 解决引用计数语法，不替代跨语言生命周期设计。

2. Metal API 阅读提示

Metal 概念本项目映射关键差异
MTLCommandQueue/BufferRHI queue、submission、completion逻辑多 queue 语义仍由 RHI 验证
render/compute/blit encoderRHI command records 的提交期编码encoder scope 比通用 command list 更严格
storage modehost visible/device local 与 coherencymanaged resource 需要显式 modify/synchronize
CAMetalLayer / drawableswapchain-equivalent presentationdrawable 是帧级短生命周期对象，不能跨帧缓存
MTLLibraryRHI typed MetalLibrary payload 的 native realizationruntime 不从 MSL source 编译

3. 跨语言所有权检查法

阅读 Metal backend 时依次确认四件事：C++ wrapper 是否共享正确 device owner identity；Objective-C object 是否只出现在 private Objective-C++；submission 是否保持 GPU 执行所需的 resource；shutdown 是否先等待 terminal completion 再释放 layer/device。只看 ARC retain count 无法回答后两项。

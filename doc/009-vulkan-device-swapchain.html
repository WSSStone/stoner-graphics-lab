2. 本期核心摘要

本阶段完成第一个可运行的 Vulkan backend slice：runtime instance、deterministic adapter selection、RHI device、queue、fence/semaphore、Core platform-window-backed surface validation、swapchain acquire/present/recreate，以及 shutdown invalidation。

实现没有把 Vulkan SDK 类型泄漏到 RHI 或 Renderer；SCons 会检测 VULKAN_SDK 并定义宏，SDK 不存在时仍能通过 compile-safe fallback 路径跑完 deterministic backend contract tests。

二、目标与边界

1. 业务与功能目标

US1 — 初始化可用 Vulkan backend device P1 MVP

开发者可以创建 headless backend device，查询 queue、format、presentation、sync、frames-in-flight 能力；unsupported runtime 和 no-compatible-adapter 都有显式结果。

US2 — 发现并使用 backend queues P1

graphics、compute、transfer、present queue 按 selected adapter capability 创建，支持 metadata 查询和 wait-idle；submit 在 command recording phase 前明确拒绝。

US3 — 创建与重建 presentation swapchain P1

surface 只接受有效 FPlatformWindow，swapchain 支持 frame count、current frame、acquire、present、resize-required、unavailable 和 recreate。

US4 — 使用 backend synchronization objects P2

fence 支持 initially signaled、wait/not-ready/timeout/reset/signal；semaphore 支持 signal/consume/reset 和非法转移拒绝。

US5 — 干净 shutdown 与 failure recovery P2

device shutdown invalidates owned queues、sync objects、swapchains，后续创建返回 invalid-state；重复 create/destroy cycle 保持 deterministic。

2. 架构目标与定位

本阶段位于 Backend/Vulkan 层，是 RHI contract 的第一个真实后端实现切片。Renderer/Application 仍然只面对 RHI/Core；Vulkan 运行时细节留在 Source/Backend/Vulkan/ 内部。

三、交互与产品设计

1. 用户使用路径

CreateVulkanDevice()
  -> IRHIDevice::GetCapabilities()
  -> CreateCommandQueue(Graphics/Compute/Transfer/Present)
  -> CreateFence / CreateSemaphore
  -> CreateSurface(FPlatformWindow)
  -> CreateSwapchainForSurface(surface, frame count)
  -> AcquireNextFrame -> Present
  -> Shutdown

2. 核心规则与状态机

对象规则
InstanceUninitialized -> Ready 或 explicit Unsupported；validation unavailable 是 diagnostic，不让初始化失败。
Adapter Candidate先过 required capability gate，再按 discrete GPU、queue support、presentation、format support 确定性打分。
DeviceUninitialized -> Active -> Shutdown；shutdown 后所有 factory 返回 invalid-state。
Queue支持 type/submitted count/wait-idle；missing 或 completed command buffer submit 都不会伪造执行。
Surface无效 FPlatformWindow 返回 invalid-state，并写入 presentation skip diagnostic。
SwapchainReady -> Acquired -> Ready；double acquire、stale present、unavailable、resize-required 都是显式结果。
Fence/Semaphore状态转换可查询；shutdown invalidation 后操作返回 invalid-state。

3. 架构决策记录（ADR）

ADR-009-01：SDK 检测与 fallback 分离

构建系统可以看到 VULKAN_SDK 时定义 SDK available，但代码路径仍能在无 SDK 环境中编译。这样不会让 Backend/Vulkan 成为所有开发机的硬依赖。

ADR-009-02：adapter selection 先 gate 后 score

required capability gate 保证不选缺少 graphics/transfer/color format 的 adapter；score 再负责 discrete GPU、queue、presentation、format 的偏好，避免 driver 枚举顺序导致不稳定。

ADR-009-03：queue submit 不伪造 command execution

真实 command buffer recording 是后续阶段。本阶段 queue 可以创建、查询、wait-idle，但 submit 对 missing/non-executable 或暂未支持的 executable buffer 给出显式状态。

ADR-009-04：diagnostics 与 result code 分工

ERHIResult 负责机器可判断的结果；diagnostics 负责解释 selected adapter、validation unavailable、presentation skip 等后端细节。

六、设计巧思与最佳实践

6.1 当前业务场景与业务模型的最佳实践

本阶段的核心做法是“先把后端生命周期和契约边界钉牢，再接真实 Vulkan handle”。这让后续 resource、command、pipeline 阶段可以复用 device/queue/sync/swapchain 生命周期，而不会一边接 SDK 一边改抽象。

6.2 优化方案与收益

  • Deterministic tests：用 synthetic candidates 覆盖 multi-adapter selection，不依赖开发机 GPU 枚举顺序。
  • Clear unsupported behavior：缺 runtime、缺 adapter、缺 queue、无效 window 都有显式结果，避免 silent pass。
  • Owned-object invalidation：shutdown 后已有 queue/sync/swapchain 对象也不能继续工作，减少 stale object 风险。
  • No Vulkan leakage：RHI public surface 不需要包含 Vulkan header，保留多后端能力。

七、编程语言知识点

1. 标准库接口与用法

  • std::max_element：在 adapter candidate 列表中选择最高 score 项。
  • std::string_view：测试和 tie-break 中比较 adapter name，不拥有字符串。
  • std::dynamic_pointer_cast：测试中从 IRHISwapchain 转回 FVulkanSwapchain 以触发 resize/unavailable simulation。

2. 语言特性与惯用法

  • RAII-style shared ownership：通过 TSharedPtr 返回 RHI objects，device 保存 owned object 列表用于 shutdown invalidation。
  • 强类型 enum：availability、validation、device type、RHI result/state 都避免魔法数字。
  • 默认参数：CreateVulkanDevice() 和 FVulkanInstanceDesc 支持默认 headless happy path。

3. 平台相关与编译器行为

SCons 从环境变量 VULKAN_SDK 检测 include/lib 目录，并定义 STONER_VULKAN_SDK_AVAILABLE。当前 public headers 不包含 Vulkan SDK，因此 macOS/Linux/Windows 在 SDK 缺失时仍能编译后端 fallback。

八、软件工程知识点

1. 设计模式与架构模式

  • Facade：CreateVulkanDevice 和 aggregate VulkanDevice.h 给外部一个简洁入口。
  • Strategy-ready backend：Vulkan backend 实现同一组 RHI interfaces，为未来 Metal/DX12/OpenGL 后端保留并行策略。
  • State machine：device、swapchain、fence、semaphore 都用显式状态控制合法操作。

2. 工程原则与方法论

  • Spec-driven delivery：实现严格对应 spec/plan/tasks 的 user stories 与 success criteria。
  • YAGNI：不提前实现 buffer/texture/command/pipeline 后端，只返回 explicit unsupported。
  • Dependency inversion：Renderer/Application 依赖 RHI/Core contract，不依赖 Vulkan 具体类型。

3. 测试策略与质量保障

  • Success path：device init、queue creation、surface/swapchain acquire-present、sync transitions。
  • Negative path：unsupported runtime、no compatible adapter、unsupported queue、invalid window、double acquire、stale present、post-shutdown factory。
  • Regression baseline：完整 StonerTest 同时跑 Core、RHI core/resource/pipeline 和 Vulkan backend tests。

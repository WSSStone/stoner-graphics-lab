2. 本期核心摘要

交付第一个真实图形后端 slice：Vulkan runtime 初始化、deterministic adapter selection、logical device ownership、queue exposure、sync objects、Core window-backed surface validation 和 swapchain lifecycle。无 Vulkan runtime 时也保留 deterministic fallback diagnostics。

最值得学习的是“真实 API 接入不能破坏抽象层”：Vulkan 的 instance/device/queue/surface/swapchain 很具体，但它们必须被封装在 Backend/Vulkan 中，通过 RHI contract 对外呈现。runtime 缺失和 headless 环境不是异常情况，而是 CI 必须支持的路径。

3. 上下文与依赖

  • 前置依赖：Core platform abstraction and RHI core interfaces
  • 后续铺路：Vulkan resources, commands, pipelines, renderer presentation path
  • 层级边界：Backend/Vulkan 只向下依赖已稳定 contract，不能反向 include 更高层模块。
  • 编译期依赖：公共头和 SCons 目标；概念依赖：spec/plan/tasks 中定义的 lifecycle、result、diagnostic 与测试替身。

二、目标与边界

1. 业务与功能目标

  • 后端能初始化 Vulkan instance/physical device/logical device 或进入 unsupported fallback。
  • 按 RHI 队列类型暴露 graphics/compute/transfer/present-like 能力。
  • 通过 Core platform window wrapper 验证 surface/swapchain 生命周期。
  • fence/semaphore 对象遵守 RHI lifecycle。

2. 架构目标与定位

Application / Tests
    ↓ 使用 public contract
Backend/Vulkan feature: Vulkan Device & Swapchain Backend
    ↓ 依赖稳定下层能力
Core vocabulary / diagnostics / platform
    ↓ 按阶段连接
RHI contracts / Backend implementations / Renderer systems

本阶段的 public contract 是调用方可以依赖的最小稳定面；private implementation、测试替身和 backend-specific helper 都不能反向污染上层 API。

3. 边界与非目标（约束）

  • 不支持 command recording，queue submit 对缺失 executable command buffer 明确拒绝。
  • 不创建 buffer/texture/descriptor/shader/pipeline。
  • 不要求 CI 有真实 GPU、窗口系统或 Vulkan loader。

三、交互与产品设计

1. 用户使用路径

创建 FVulkanDevice -> 探测 loader/runtime -> 创建 instance -> 选择 physical device -> 创建 logical device/queues -> 可选创建 surface/swapchain -> shutdown 时按拥有关系失效 owned objects。fallback 模式记录 unsupported diagnostics 但测试仍确定。

学习时建议把这一段当成“最小工作流”：先找到输入对象，再跟踪它如何变成状态、诊断、测试断言或 debug dump。

2. 核心规则与状态机

未创建/空状态
    -> 描述或 Begin/Declare/Create
    -> 可验证中间状态
    -> Success: 可查询、可绑定、可执行或可复用
    -> Reset/Shutdown/Invalidated
    -> 任何后续使用必须返回错误结果或诊断

这个状态机是本项目底层模块的共同风格：显式创建、显式验证、显式失效。不同 feature 的状态名不同，但测试都围绕“合法转换”和“非法转换可观察”展开。

3. 失败模式与调试入口

  • Vulkan loader 缺失不能导致测试不可运行，必须返回 unsupported 并记录诊断。
  • adapter 选择若非 deterministic，回归测试和用户复现会变难。
  • surface 使用无效 native window handle 必须失败，不能让 swapchain 延后崩溃。

调试入口优先看 Tests/VulkanBackendTests.cpp 中的负路径用例，再看对应 diagnostics、result code 或 debug dump 输出；这些测试比源码更快暴露设计意图。

四、技术架构与关键决策

1. 技术栈与基础设施

  • C++20，传统 header/source 分离；公共 API 遵守项目 UE-style 命名。
  • SCons 4.10.1 构建；验证入口保持在单一 StonerTest 可执行文件。
  • Core/RHI/Renderer public contract 尽量不泄漏 backend 或平台实现细节。
  • headless、fallback 和 mock 测试优先保证无 GPU/无窗口环境仍能验证语义。

3. 架构决策记录 (ADR)

(1) deterministic fallback runtime

背景：开发机/CI 可能没有 Vulkan SDK 或可用 GPU。

理由：fallback 让生命周期和错误语义仍可测试。

被否决方案：直接 hard fail：会阻断无 GPU 环境。

后果：真实渲染能力延后验证，但契约更稳。

(2) Vulkan 头只在 backend 内出现

背景：RHI/Renderer 必须保持多 API。

理由：隔离 include 和平台宏污染。

被否决方案：在 RHI contract 暴露 Vk* handle：短期方便，长期绑定 Vulkan。

后果：需要 wrapper 查询底层信息时另设 backend-specific API。

五、实施与验证（任务流）

1. 任务拆解清单

  • Setup/Foundation：建立公共头、private source、测试入口和 SCons 发现路径。
  • Contract/API：定义描述结构、接口、枚举、状态和 result/diagnostic 语义。
  • Core implementation：实现状态机、验证逻辑、数据结构和 deterministic formatting。
  • Integration：把本阶段能力接入已有 Core/RHI/Backend/Renderer 边界。
  • Diagnostics/debug tooling：补齐负路径记录、dump、fallback marker 或测试可观察输出。
  • Tests and validation：覆盖 happy path、failure path、lifecycle、compatibility 和 boundary isolation。
  • Documentation/roadmap update：更新 quickstart、roadmap 和本总结文档。

  • 构建命令可完成：scons。
  • 测试命令可完成并覆盖本 feature 对应测试文件：Tests/VulkanBackendTests.cpp。

六、设计巧思与最佳实践

1. 当前业务场景与业务模型的最佳实践

(1) Instance/Device split

是什么：Vulkan 先有全局 instance，再选择物理设备并创建逻辑设备。

项目表达：FVulkanInstance/FVulkanPhysicalDevice/FVulkanDevice 分离职责。

真实引擎/API 对应：DX12 adapter/device、Metal device 虽结构不同，但都需要 adapter capability 阶段。

(2) Queue families

是什么：Vulkan 队列能力来自 family，而不是单一全能队列。

项目表达：FVulkanQueue 将 family/type 映射到 RHI queue type。

真实引擎/API 对应：DX12 queue types、Metal command queues 也需要能力分类。

(3) Swapchain lifecycle

是什么：呈现资源依赖 window、surface、format、extent 和 resize。

项目表达：FVulkanSwapchain 只在有效 surface 下创建/重建。

真实引擎/API 对应：所有图形 API 的 presentation 都是平台和 GPU 的交界面。

2. 优化方案与收益

本阶段的优化重点不是追求最终性能，而是建立可替换的语义基线：先让行为被测试锁住，再在未来引入 SIMD、真实 Vulkan runtime、更复杂 allocator、pipeline disk cache、render graph aliasing 或 async compute。

这种做法的收益是 migration cost 可控：只要 public contract 和测试矩阵稳定，private implementation 可以逐步从 mock/fallback 演进到真实 GPU 路径。

七、编程语言知识点

1. 标准库接口与用法

本项目优先使用标准库可移植能力，例如容器、智能指针、字符串、chrono、filesystem、mutex 和 algorithm。关键不是“用了哪个库”，而是把标准库行为包装进项目自己的 contract，减少跨模块直接耦合。

2. 语言特性与惯用法

  • RAII/ownership：资源对象在 shutdown/invalidate 时显式失效，避免悬空后继续成功。
  • enum class：用强类型枚举表达 result、queue、usage、stage、state，避免整数误传。
  • 值语义和移动语义：desc、handle、record 适合轻量复制；拥有对象则通过指针或明确 lifecycle 管理。
  • 宏只用于日志/断言等需要调用点上下文的场景，其余优先函数和类型系统。

3. 平台相关与编译器行为

平台相关代码应留在 Core platform 或 Backend private 边界内。公共头尽量避免平台宏分叉和图形 API 头泄漏，这样 Windows/macOS/Linux 与未来 Vulkan/DX/Metal/OpenGL backend 才能共享上层代码。

八、软件工程知识点

1. 设计模式与架构模式

  • Layered Architecture：Core -> RHI -> Backend/Renderer 的依赖方向必须单向。
  • Facade/Aggregate Header：CoreMinimal、RHIMinimal 或 RendererMinimal 提供便利入口，但不能隐藏边界污染。
  • Builder/Compiler/Executor：复杂声明式系统先收集意图，再编译计划，最后执行。
  • Adapter：Backend/Vulkan 把具体 API 对象适配成 RHI contract。

2. 工程原则与方法论

  • Contract-first：先定义 public behavior，再实现 backend 或优化。
  • Fail fast but diagnosable：错误尽早返回，同时留下能解释原因的记录。
  • Determinism：排序、dump、fallback 和测试输出都尽量稳定。
  • YAGNI with escape hatch：推迟工业级复杂能力，但保留未来接入点。

3. 测试策略与质量保障

测试不是只证明“代码能跑”，而是把工程假设固化下来：合法路径、非法路径、边界隔离、重复运行稳定性和 fallback/headless 环境都应该被覆盖。对图形工程而言，mock 与 fallback 不是偷懒，而是让 CI 可以在没有真实 GPU 的情况下守住 contract。

2. 本期核心摘要

本期新增独立 Asset 静态库，为引擎提供与物理文件位置、GPU 对象和内容版本分离的稳定资产身份；同时交付 metadata/dependency registry、resolver/importer/loader/cooker strategy contracts、原子批处理、并发查询、确定性诊断与 inspection。

最值得学习的是“身份、版本、发现、处理、生命周期”必须拆开。把文件路径当身份、把插件注册当执行所有权、或让 Renderer 拥有 importer，短期都能工作，长期却会让 cook cache、hot reload、跨平台格式和 streaming 无法独立演进。

3. 上下文与依赖

Feature 020 只编译依赖 Core，并通过 Core 私有的 FUnicode 使用 utf8proc 2.11.3。它不依赖 RHI、Renderer、Application、Backend 或 Tools。后续 021 image/texture、022 KTX2、023 material/shader、024 mesh/model 和 025/026 cooker/runtime manager 将复用这里的 identity、metadata、extension 与 version contracts。

二、目标与边界

1. 业务与功能目标

引擎开发者可以创建 Texture:UI/Icons/Play#Preview 这样的 typed logical ID，独立记录 source/content/cook SHA-256 evidence，把 metadata 以 atomic batch 写入 registry，并查询 type、source、direct dependency 与 reverse dependent。格式模块可注册 resolver/importer/loader/cooker；dispatch 对 priority、confidence、capacity 和 ambiguity 给出稳定结果。

2. 架构目标与定位

Tools/AssetCooker (future) ---> Asset ---> Core ---> private utf8proc
Renderer (future) -----------> Asset
Application (future) --------> Asset

Asset -X-> RHI / Renderer / Application / Backend / Tools / graphics API

Public contract 位于 Source/Asset/Public/Asset；dependency graph、registry indexes、dispatch selection 和 lease retirement 位于 Private。Asset 只拥有 CPU-side values 和 payload contract；未来 GPU texture/buffer residency 仍属于 Renderer/RHI adapter。

3. 边界与非目标（约束）

  • 不实现 PNG、KTX2、glTF 等 concrete formats：它们分别进入后续 format feature。
  • 不实现数据库、manifest 或 persistent catalog：本期先固定 process-local 语义。
  • 不实现 async request、cancel、coalescing、eviction 或 streaming：这些属于 runtime manager/residency。
  • 不创建 GPU handle：防止 Asset 反向依赖 RHI/Backend。
  • 不把 benchmark timing 作为 CI gate：共享 runner 的时序波动不代表 correctness。

三、交互与产品设计

1. 用户使用路径

FAssetId Id;
FAssetId::Create("Texture", "UI/Icons/Play", {}, Id);

FAssetMutationBatch Batch;
Batch.Register(Metadata);
Registry.Apply(Batch);

auto Snapshot = Registry.Find(Id);
auto Text = FAssetInspection::Format(*Snapshot);

扩展路径先用 scoped token 注册 participant；dispatch 捕获 active capabilities、应用 hint/priority/confidence 规则、获得 execution lease 后才调用 callback。失败时查看 EAssetResult、FAssetDiagnostics::FormatNormalized 和 registry/extension inspection。

2. 核心规则与状态机

raw ID -> UTF-8 validate -> NFC -> path grammar -> immutable FAssetId

batch: Building -> Validating -> Graph Check -> Committed
                                  \-> Rejected (revision/index unchanged)

extension: Active -> token reset -> Inactive for new selection
                  existing execution lease -> callback completes -> destroy once

Required edge 指向缺失 target 时保留为 Unresolved；target 出现后原子变为 Resolved；若新 target 闭合 required cycle，则整批拒绝。Soft edge 不参与 required DAG cycle gate。

3. 失败模式与调试入口

  • InvalidIdentity/InvalidUtf8：检查 type grammar、NFC、root、..、reserved delimiters 和 byte limits。
  • DependencyCycle：检查 proposed batch 与现有 required graph；失败不会留下半更新 index。
  • AmbiguousResolver/AmbiguousImporter：participant ID 只排序诊断，不偷偷打破功能 tie。
  • CapacityExceeded：hint filtering 后超过 64 importers，必须在 source read/probe 前失败。
  • RegistrationInactive：token 已释放且 dispatch 尚未获得 lease；已获得的 lease 不受影响。

四、技术架构与关键决策

1. 技术栈与基础设施

C++20、SCons 4.10.1、std::shared_mutex、std::optional、std::span、RAII token/lease，以及 Core-private utf8proc 2.11.3。Feature 020 完全 headless，不需要 Vulkan SDK、display server 或 GPU。

2. 关键信息

2.1 模块对应关系

模块职责防止的问题
FUnicode / FAssetId统一 UTF-8 NFC 与逻辑 identity grammar不同 OS 文件语义导致 ID 漂移
FAssetDigest / FAssetVersion独立 source/content/cook evidence内容变化污染稳定引用
FAssetRegistryatomic mutation、indexes、shared-reader snapshots读者观察 partial batch
FAssetDependencyGraphresolution transition 与 required DAG gate导入顺序耦合和隐藏 cycle

FAssetDispatchbounded deterministic resolver/importer selectionregistration order 成为隐式策略

2.2 数据流与控制流

source locator 先选 unique-priority resolver；resolver 返回 descriptor 与 bounded source lease；format hint 缩小 importer candidates；每个 importer 最多读取 64 KiB，并给出 0-100 confidence；唯一最高非零者获得 import lease；全部 multi-output metadata、payload type 和 dependency graph 验证通过后，调用方才能提交 registry batch。

2.3 诊断与可视化

normalized diagnostic 固定 severity、stage、result、code、subject、participant、reason；不记录 address、thread ID、native error text 或 timing。FAssetInspection 对 identity、digest、version、metadata、registry snapshot、capability 和 ambiguity candidates 产生 owned deterministic text。

3. 架构决策记录 (ADR)

(1) 逻辑身份不包含 hash

决策：FAssetId 只由 type/path/subresource 构成。理由：内容改变不应让 scene soft reference 失效。否决：把 source hash 放进路径；这会让每次 reimport 都变成新资产。后果：版本失效必须显式比较 FAssetVersion。

(2) Unicode 由 Core 私有封装

决策：utf8proc 只编进 Core，Asset 只见 FUnicode。否决：平台 API 会产生跨平台差异，手写 NFC 表风险过高。后果：新增一份 pinned third-party source，但 public ABI 保持干净。

(3) Registry 采用 staged copy + serialized commit

决策：batch 在 exclusive writer boundary 中复制 proposed records、验证并一次替换，同时重建 indexes。理由：Feature 020 优先 correctness 和简单快照语义。否决：细粒度 lock-free mutation；复杂度不适合当前阶段。后果：大型批次有复制成本，后续可在不改变 public contract 的情况下优化。

(4) Token 与 Lease 分离

决策：token 控制未来 eligibility，lease 控制 in-flight ownership。否决：token 析构阻塞等待 callback，可能因 callback re-entry 死锁。后果：unregister 是非阻塞的，instance 在最后 lease 释放后恰好销毁一次。

六、设计巧思与最佳实践

1. 当前业务场景与业务模型的最佳实践

  • Hash 只做 lookup optimization：equality 永远比较完整值，测试可强制内部 hash collision。
  • Unresolved 是显式状态：允许任意导入顺序，同时不伪造 placeholder metadata。
  • Functional tie 必须失败：participant 名称只能稳定展示，不能掩盖 resolver/importer 配置冲突。
  • Probe 先限 candidate 再读 source：避免恶意或错误配置把一次发现扩大为无界 I/O。

2. 优化方案与收益

已实现 exact-ID unordered lookup、type/source/reverse indexes 和 proportional dependency query；deterministic dump 在边界统一排序。benchmark 样本用于观察 registry 规模变化，不承诺产品级 SLA。未来可把 staged full copy 换成 journal/delta commit，而不改变 reader snapshot contract。

3. 已知限制与后续演进

当前 payload 只有抽象 CPU base，source 只有 contract，registry 不持久化，dispatch 同步执行。021-024 将加入具体 texture/material/mesh payload，025/026 将加入 cooker 与 async runtime manager，028 streaming/residency 再处理 budgets、chunks 和 eviction。

七、编程语言知识点

1. 标准库接口与用法

std::optional 表达 subresource 与 unavailable evidence；std::span 传递 bounded bytes；std::shared_mutex 区分多 reader 与 serialized writer；std::shared_ptr/weak_ptr 让 token 不反向延长 registry、lease 延长 extension；std::atomic 固化 active flag 与 stress counters。

2. 语言特性与惯用法

move-only registration token 用 RAII 表达 scoped registration；enum class 防止 result/stage/role 混用；concept 约束 typed soft reference 必须有稳定 asset type trait；PImpl 隐藏 mutex、indexes 和 extension records。带分配的 factory 不误标 noexcept，避免 allocation failure 直接终止进程。

八、软件工程知识点

1. Contract-first 与边界测试

架构 scanner 不检查运行结果，而检查“错误依赖根本不能进入 production boundary”。suite registry 则把未来 feature 的 focused tests 变成一张表，而不是继续在 Main.cpp 增加 parser 分支或环境变量 skip。

2. Determinism 与诊断责任

result code 用于程序分支，diagnostic 用于定位，inspection 用于完整状态学习。三者分开后，测试可以断言稳定 category，同时允许内部实现和人类可读说明演进。

3. Evidence-driven completion

本地 Debug/Release/sanitizer 与 remote CI 是不同证据。Feature 020 在远程 workflow 成功后才关闭 T052/T054：这样 checkbox 记录的是已经发生的 Windows/macOS/Linux 与 Linux sanitizer 验证，而不是实现者的预期。

九、引擎与图形 API 学习笔记

1. Asset 层为什么不属于 Renderer

Texture、mesh 会进入 GPU，但 identity、source provenance、dependency 和 cook version 同样服务 Tools、scene、audio/font 等系统。把 Asset 放在 Renderer 下会迫使离线工具依赖渲染运行时，也会阻碍 server/headless 使用。

2. 与图形 API 的映射

本期没有 Vulkan/DX12/Metal/OpenGL 类型，这是刻意的。后续 Renderer adapter 才把 FTextureAsset 转成 VkImage、ID3D12Resource、MTLTexture 或 GL texture；相同 FAssetId 可对应不同 target-profile cook payload，而不改变逻辑引用。

3. 推荐源码阅读路线

  1. FAssetId.* 与 FUnicode.*：理解稳定身份。
  2. FAssetMetadata.*、FAssetDependencyGraph.cpp、FAssetRegistry.cpp：理解原子状态。
  3. FAssetExtensionRegistry.cpp 与 FAssetDispatch.cpp：理解 eligibility 和 execution ownership。
  4. AssetCoreTests.cpp：从失败边界反推 contract。

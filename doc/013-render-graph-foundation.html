2. 本期核心摘要

交付 Renderer 层 Render Graph Foundation：DAG 声明、验证、deterministic compile、virtual resource lifetime、transition plan、pass culling、transient resource resolution、imported resource validation、aliasing eligibility diagnostics、fail-fast execution 和 deterministic text debug dump。

最值得学习的是 Render Graph 如何把“渲染代码顺序”提升成“数据依赖图”：pass 只声明读写资源，compiler 负责排序、裁剪、生命周期和 transition，executor 再把计划转成 RHI 命令意图。这是现代引擎从手写 frame function 走向可优化 frame graph 的关键一步。

3. 上下文与依赖

  • 前置依赖：Core types/containers/logging, RHI resource/command/barrier contracts, Vulkan backend tests
  • 后续铺路：concrete forward/deferred passes, material integration, frame scheduling, async compute and real transient aliasing
  • 层级边界：Renderer 只向下依赖已稳定 contract，不能反向 include 更高层模块。
  • 编译期依赖：公共头和 SCons 目标；概念依赖：spec/plan/tasks 中定义的 lifecycle、result、diagnostic 与测试替身。

二、目标与边界

1. 业务与功能目标

  • 开发者用 FRenderGraphBuilder 声明 graphics/compute/copy/side-effect passes。
  • 编译器生成稳定拓扑序、dependency edges、lifetime、aliasing decisions 和 transition records。
  • executor 解析 transient resources、校验 imported resources、按 schedule 调用 pass callback。
  • debug dump 可复现输出成功/失败图状态。

2. 架构目标与定位

Application / Tests
    ↓ 使用 public contract
Renderer feature: Render Graph Foundation
    ↓ 依赖稳定下层能力
Core vocabulary / diagnostics / platform
    ↓ 按阶段连接
RHI contracts / Backend implementations / Renderer systems

本阶段的 public contract 是调用方可以依赖的最小稳定面；private implementation、测试替身和 backend-specific helper 都不能反向污染上层 API。

3. 边界与非目标（约束）

  • 不实现材料系统、shader permutation 或具体 forward/deferred pass。
  • 不做真实 backing-storage alias reuse，只报告 eligibility。
  • 不实现 async compute overlap、多线程 compilation 或 visible presentation。

三、交互与产品设计

1. 用户使用路径

builder 声明资源/pass/output -> compiler 验证 handle 与读写关系 -> 构造 dependency DAG -> stable topological sort -> 计算 first/last use 与 culling -> 生成 transition plan -> executor 创建 transient backing、校验 imported binding、发出 transition、执行 pass callback -> debug dump 记录图结构。

学习时建议把这一段当成“最小工作流”：先找到输入对象，再跟踪它如何变成状态、诊断、测试断言或 debug dump。

2. 核心规则与状态机

未创建/空状态
    -> 描述或 Begin/Declare/Create
    -> 可验证中间状态
    -> Success: 可查询、可绑定、可执行或可复用
    -> Reset/Shutdown/Invalidated
    -> 任何后续使用必须返回错误结果或诊断

这个状态机是本项目底层模块的共同风格：显式创建、显式验证、显式失效。不同 feature 的状态名不同，但测试都围绕“合法转换”和“非法转换可观察”展开。

3. 失败模式与调试入口

  • cycle、read-before-write、invalid/cross-graph handle 必须在 compile 阶段失败。
  • zero-output graph 除 side-effect pass 外应拒绝，否则所有 work 都可能被裁剪。
  • 执行缺失 imported resource 必须 fail-fast，否则 pass callback 会拿到无效资源。
  • transition plan 若不 deterministic，debug dump 和测试很难稳定。

调试入口优先看 Tests/RendererRenderGraphTests.cpp 中的负路径用例，再看对应 diagnostics、result code 或 debug dump 输出；这些测试比源码更快暴露设计意图。

四、技术架构与关键决策

1. 技术栈与基础设施

  • C++20，传统 header/source 分离；公共 API 遵守项目 UE-style 命名。
  • SCons 4.10.1 构建；验证入口保持在单一 StonerTest 可执行文件。
  • Core/RHI/Renderer public contract 尽量不泄漏 backend 或平台实现细节。
  • headless、fallback 和 mock 测试优先保证无 GPU/无窗口环境仍能验证语义。

3. 架构决策记录 (ADR)

(1) Render Graph 放在 Renderer 而不是 RHI

背景：它是帧级调度和资源生命周期规划，不是底层 API contract。

理由：Renderer 可依赖 RHI 抽象，但不暴露 Vulkan。

被否决方案：放入 RHI：会把高层调度概念压进 backend contract。

后果：后续具体 renderer pass 可直接复用。

(2) 先做 aliasing eligibility 不做真实 reuse

背景：真实 alias 需要 allocator、barrier、lifetime 和 debug 工具共同成熟。

理由：当前先证明生命周期分析和拒绝原因。

被否决方案：立刻复用 backing storage：风险高且难定位资源污染。

后果：未来可在 executor/resource allocator 接入真实 alias。

六、设计巧思与最佳实践

1. 当前业务场景与业务模型的最佳实践

(1) DAG scheduling

是什么：pass 之间通过资源读写形成有向无环图。

项目表达：FRenderGraphCompiler 构造 dependency edges 并 stable topological sort。

真实引擎/API 对应：FrameGraph/RenderGraph/Render Dependency Graph 都依赖这个基础。

(2) Virtual resource lifetime

是什么：声明的是虚拟资源，执行时才解析 backing。

项目表达：compiler 计算 first-use/last-use，executor 分配 transient resource。

真实引擎/API 对应：现代引擎用它做 transient memory aliasing 和 barrier 合并。

(3) Transition planning

是什么：资源访问从一种 usage/layout 转到另一种。

项目表达：compiled transition plan 在执行时发出 RHI-facing transition。

真实引擎/API 对应：Vulkan barrier、DX12 resource barrier、Metal encoder boundary 都是对应执行层。

(4) Pass culling

是什么：未贡献 output 且无 side effect 的 pass 可以移除。

项目表达：compiler 从 outputs 反向标记 reachability。

真实引擎/API 对应：真实 renderer 用它去掉未使用 shadow/lighting/postprocess 分支。

2. 优化方案与收益

本阶段的优化重点不是追求最终性能，而是建立可替换的语义基线：先让行为被测试锁住，再在未来引入 SIMD、真实 Vulkan runtime、更复杂 allocator、pipeline disk cache、render graph aliasing 或 async compute。

这种做法的收益是 migration cost 可控：只要 public contract 和测试矩阵稳定，private implementation 可以逐步从 mock/fallback 演进到真实 GPU 路径。

七、编程语言知识点

1. 标准库接口与用法

本项目优先使用标准库可移植能力，例如容器、智能指针、字符串、chrono、filesystem、mutex 和 algorithm。关键不是“用了哪个库”，而是把标准库行为包装进项目自己的 contract，减少跨模块直接耦合。

2. 语言特性与惯用法

  • RAII/ownership：资源对象在 shutdown/invalidate 时显式失效，避免悬空后继续成功。
  • enum class：用强类型枚举表达 result、queue、usage、stage、state，避免整数误传。
  • 值语义和移动语义：desc、handle、record 适合轻量复制；拥有对象则通过指针或明确 lifecycle 管理。
  • 宏只用于日志/断言等需要调用点上下文的场景，其余优先函数和类型系统。

3. 平台相关与编译器行为

平台相关代码应留在 Core platform 或 Backend private 边界内。公共头尽量避免平台宏分叉和图形 API 头泄漏，这样 Windows/macOS/Linux 与未来 Vulkan/DX/Metal/OpenGL backend 才能共享上层代码。

八、软件工程知识点

1. 设计模式与架构模式

  • Layered Architecture：Core -> RHI -> Backend/Renderer 的依赖方向必须单向。
  • Facade/Aggregate Header：CoreMinimal、RHIMinimal 或 RendererMinimal 提供便利入口，但不能隐藏边界污染。
  • Builder/Compiler/Executor：复杂声明式系统先收集意图，再编译计划，最后执行。
  • Adapter：Backend/Vulkan 把具体 API 对象适配成 RHI contract。

2. 工程原则与方法论

  • Contract-first：先定义 public behavior，再实现 backend 或优化。
  • Fail fast but diagnosable：错误尽早返回，同时留下能解释原因的记录。
  • Determinism：排序、dump、fallback 和测试输出都尽量稳定。
  • YAGNI with escape hatch：推迟工业级复杂能力，但保留未来接入点。

3. 测试策略与质量保障

测试不是只证明“代码能跑”，而是把工程假设固化下来：合法路径、非法路径、边界隔离、重复运行稳定性和 fallback/headless 环境都应该被覆盖。对图形工程而言，mock 与 fallback 不是偷懒，而是让 CI 可以在没有真实 GPU 的情况下守住 contract。

API本阶段概念如何映射
VulkanRender Graph transition 最终会落到 image/buffer memory barriers 和 queue ownership/layout transitions。

2. 本期核心摘要

本阶段为 Core 层补齐跨平台基础能力：平台识别、OS/CPU/内存信息查询、单调高精度时间、本地文件读写、显式路径动态模块加载，以及安全的原生窗口句柄包装。它让后续 RHI、Backend、Renderer 和 Application 不再直接散落操作系统条件编译。

3. 上下文与依赖

依赖项说明
Spec 003 Core Types & Memory提供 uint32、uint64、TArray、FString 等基础类型。
Spec 005 Logging & Assertions保留既有日志/断言行为，平台层不引入上层模块依赖。
C++20 标准库使用 <chrono>、<filesystem>、<fstream>、<thread> 等便携设施。
平台系统库动态模块与内存查询在 .cpp 中通过 Windows/macOS/Linux 分支隔离。

二、目标与边界

1. 业务与功能目标

US1 — 统一使用平台能力 P1 MVP

开发者通过 Core API 查询平台身份、OS 名称、CPU 核数、可用内存和高精度时间，不需要在调用点判断操作系统。

US2 — 便携文件操作 P1

支持文件/目录存在性检查、递归创建目录、字节级读写文本与二进制 payload，并明确处理缺失路径和目录当文件等失败场景。

US3 — 可选运行时模块加载 P2

通过显式文件路径加载动态库、解析符号并释放模块，缺失模块和缺失符号都是可恢复失败。

US4 — 安全传递原生窗口句柄 P2

提供 Core 拥有的 FPlatformWindow 句柄包装，为未来 swapchain/surface 集成预留稳定入口。

2. 架构目标与定位

平台抽象位于 Core 层，是上层渲染、后端、应用和测试的基础服务；它只向外暴露引擎风格 API，把系统调用和平台头文件约束在实现文件内部。

3. 边界与非目标（约束）

不做什么原因
完整窗口系统、输入事件、窗口生命周期本阶段只提供原生句柄承载类型。
线程、网络、进程启动、环境变量这些能力会在独立阶段设计，避免平台层过早膨胀。
虚拟文件系统、文件监听、权限管理当前只覆盖测试、启动和早期工具所需的本地文件能力。
插件生命周期管理FPlatformProcess 只处理显式路径动态模块加载。

三、交互与产品设计

1. 用户使用路径

include Core/CoreMinimal.h
  -> query SG_PLATFORM_* / FPlatformMisc
  -> capture FPlatformTime timestamps
  -> use FPlatformFileSystem for local files
  -> optionally LoadDynamicModule(explicit path)
  -> pass FPlatformWindow to future backend code

2. 核心规则与状态机

对象状态/规则
SG_PLATFORM_*Windows、macOS、Linux 三者必须且只能一个为 1，未知平台编译期失败。
FPlatformTimeNow() 返回单调时间点；持续采样不可倒退；差值可转秒、毫秒、微秒。
FPlatformFileSystem操作返回 bool；成功必须意味着最终状态可用，失败不能崩溃或伪装成部分成功。
FDynamicModuleHandleInvalid -> Loaded -> Released；无效句柄释放是安全 no-op。
FPlatformWindowEmpty -> WrappedNativeHandle -> Clear；空句柄可复制、传递、判无效。

四、技术架构与关键决策

1. 技术栈与基础设施

  • C++20，传统 header/source 分离。
  • SCons 4.10.1 自动发现源文件并构建 StonerTest。
  • 公共 API 位于 Source/Core/Public/Core/，平台实现位于 Source/Core/Private/。

2. 关键信息

Source/Core/Public/Core/
├── SGPlatform.h platform detection macros
├── FPlatformMisc.h OS / CPU / memory queries
├── FPlatformTime.h monotonic timestamps
├── FPlatformFileSystem.h local file operations
├── FPlatformProcess.h dynamic modules
└── FPlatformWindow.h native handle wrapper
Tests/
└── CorePlatformTests.cpp 31 platform tests
模块职责调用关系
FPlatformMisc返回 OS 名称、CPU 核数、可用内存。上层只读查询；平台分支在 .cpp。
FPlatformFileSystem存在性、递归建目录、读写字节数组。使用 Core 类型承接路径和 payload。
FPlatformProcess显式路径动态库加载、符号查找、释放。返回 opaque handle，不泄漏平台库类型。
FPlatformWindow保存 opaque native handle。未来 Application 创建，Backend 解读。

3. 架构决策记录（ADR）

ADR-006-01：拆分 FPlatform* 能力，而不是一个总平台类

平台能力被拆成 Misc、Time、FileSystem、Process、Window。这样每个调用点只依赖自己需要的概念，也更容易在未来替换单个子能力。

放弃方案：单一 FPlatform god-class。它短期省文件，长期会把无关职责、平台分支和测试耦合在一起。

ADR-006-02：动态模块只接受显式路径

显式路径避免不同 OS 的搜索路径规则、环境变量和安全策略干扰测试结果。缺失路径、缺失符号都作为可恢复失败处理。

ADR-006-03：窗口能力只做句柄包装

真实窗口创建、事件循环和输入处理被推迟；当前只提供 void* 级 opaque 容器，确保 RHI/Backend 可以先设计 surface/swapchain 接口。

六、设计巧思与最佳实践

6.1 当前业务场景与业务模型的最佳实践

这个阶段的核心不是“封装所有平台能力”，而是给后续渲染路径提供最小可信平台基座。文件、时间、动态模块、窗口句柄这些能力都以稳定小接口暴露，减少未来 Vulkan、Metal、DX12 和 Application 阶段直接碰平台宏的机会。

6.2 优化方案与收益

  • 时间基于单调 clock，适合 frame/startup 诊断，不受系统时间调整影响。
  • 文件 API 使用字节数组，天然覆盖文本和二进制资源。
  • 动态模块句柄是 opaque 值，平台库生命周期被限制在 Core 实现边界。
  • 公共头尽量轻量，降低上层模块 include 链污染。

七、编程语言知识点

1. 标准库接口与用法

接口用途
std::chrono::steady_clock提供不可倒退的进程内时间基准。
std::filesystem处理存在性检查和递归目录创建。
std::ifstream/std::ofstream二进制模式读写文件，保持 payload 字节一致。
std::thread::hardware_concurrency查询 CPU 线程数，并在不可用时回退到至少 1。

2. 语言特性与惯用法

  • [[nodiscard]] 用于提醒调用者不要忽略结果。
  • noexcept 标注基础查询和句柄操作，表达不抛异常契约。
  • 条件编译宏集中于 SGPlatform.h 和私有实现，减少散落分支。

3. 平台相关与编译器行为

Windows 使用 _WIN32，macOS 使用 __APPLE__ && __MACH__，Linux 使用 __linux__。如果三者都不匹配，构建直接失败，避免悄悄产出未知平台行为。

八、软件工程知识点

1. 设计模式与架构模式

本阶段主要采用 Facade 和 Port/Adapter 思路：公共 FPlatform* 类型是引擎侧 port，私有 .cpp 中的平台分支是 adapter。它不是复杂模式展示，而是为了保护层级边界。

2. 工程原则与方法论

  • YAGNI：只做未来 roadmap 已明确需要的平台基座。
  • 契约式设计：显式路径、互斥平台宏、无效句柄 no-op 都写入测试。
  • 依赖倒置：上层模块依赖 Core 抽象，不依赖 OS/windowing/graphics 头。

3. 测试策略与质量保障

测试覆盖正常路径、负路径和边界路径：单调时间 1,000 样本、文件字节 roundtrip、路径特殊字符、目录当文件、动态模块缺失与符号缺失、窗口句柄 empty/wrapped/clear。这样后续平台扩展有明确回归基线。

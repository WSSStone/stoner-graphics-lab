2. 本期核心摘要

本阶段交付 Application 层第一套场景组织基础：单 world、generation-safe entity handle、transform/mesh/light/camera 单实例组件、parent-child hierarchy、默认 preserve-world reparent、递归销毁、deterministic render collection summary、stable diagnostics 与 debug dump。

学习价值在于把 ECS 的“扁平身份与组件存储”和 scene graph 的“层级变换关系”拆开：entity 不是树状存储，树只是 hierarchy relationship 和 traversal view。render collection 也不是树遍历，而是按 renderables/lights/cameras 分类输出稳定的 frame-facing 数据。

3. 上下文与依赖

  • 前置依赖：Core math/types/logging、Application window/input public boundary、Renderer forward/material 的抽象词汇。
  • 后续铺路：triangle demo scene data、editor/runtime scene inspection、Renderer frame preparation 的 Application 输入。
  • 层级边界：public Application 不暴露 RHI resource、Renderer frame plan、backend handle 或 native window。
  • 编译期依赖：Application 仍由 SCons layer builder 自动发现 private 源文件，测试进入既有 StonerTest。

二、目标与边界

1. 业务与功能目标

  • 开发者可以创建 FWorld，获得 FEntity 句柄，并在销毁/slot reuse 后安全识别 stale handle。
  • 开发者可以 attach/read/update/replace/remove transform、mesh、light、camera 组件；重复 add 会返回 DuplicateComponent。
  • 开发者可以组织 parent-child hierarchy，查询 world transform，并在 reparent 时选择 preserve world 或 preserve local。
  • Renderer 后续可以消费 FSceneRenderSummary：renderables、lights、cameras、rejected items 与 diagnostics。

2. 架构目标与定位

Application scene contracts
  FWorld / FEntity / Components / Hierarchy
          |
          v
Application render collection
  FSceneRenderSummary: renderables / lights / cameras
          |
          v
Future Renderer frame preparation
  no RHI resource ownership exposed by Application

本模块向上服务 demo/editor/runtime scene authoring，向下只依赖 Core 的 math/container/string。它不引入 Vulkan、Metal、DX、OpenGL，也不持有 live GPU resource；mesh component 只是抽象 identity。

3. 边界与非目标（约束）

  • 不做 serialization/asset loading：避免把运行时 scene identity 和持久化格式绑死。
  • 不做 physics/animation/scripting/editor UI：这些是不同 domain 的 component/system，需要独立规格。
  • 不做 octree/BVH/grid 作为 authoritative storage：空间索引以后可以作为 derived index，而不是 entity 的所有权结构。
  • 不做 full archetype query optimization：v1 更重视清晰语义和 deterministic tests。

三、交互与产品设计

1. 用户使用路径

FWorld world;
FEntity mesh = world.CreateEntity();
world.AddTransform(mesh, FTransformComponent(FTransform(...)));
world.AddMesh(mesh, FMeshComponent("cube", "mat"));

FEntity camera = world.CreateEntity();
world.AddTransform(camera, FTransformComponent(...));
world.AddCamera(camera, FCameraComponent{});

FSceneRenderSummary summary = world.CollectRenderSummary();

失败路径同样是 API 的一部分：旧 handle 在 destroy 或 reset 后返回 StaleEntity/InvalidEntity；重复 add 返回 DuplicateComponent；invalid light/camera/mesh 在 render collection 中进入 rejected items。

2. 核心规则与状态机

Invalid/default handle
  -> CreateEntity -> Live(slot, generation, world)
  -> DestroyEntity -> Stale(generation mismatch)
  -> slot reuse -> new Live handle, old handle remains stale
  -> Reset -> all old handles invalid

Hierarchy traversal 使用 topological order：parents before children，roots by creation order，siblings by insertion order。Render collection 使用另一套 ordering key：category 内先 optional sort key，再 entity identity(slot index, generation) tie-break。

3. 失败模式与调试入口

  • SCENE-COMPONENT-DUPLICATE：调用方误把 add 当 replace，用 update/replace 修正。
  • SCENE-HIERARCHY-CYCLE：parent 指向自身或 descendant，旧 hierarchy 保持不变。
  • SCENE-RENDER-MISSING-TRANSFORM：mesh/light/camera 缺少 transform，summary 拒绝该项但继续收集其他实体。
  • FWorld::BuildDebugDump 与 FSceneRenderSummary::BuildDebugDump 是稳定字符串入口，不包含 pointer/native handle。

1. 技术栈与基础设施

2.3 关键日志、诊断与可视化

Diagnostics 记录 stable code、severity、category、result、subject 和 deterministic message，不记录 pointer、native handle、platform transient state。result code 表达 API outcome，diagnostic 解释 outcome，debug dump 用于回归测试和人工 inspect。

3. 架构决策记录 (ADR)

(1) Entity/component authoritative storage 保持扁平

决策：entity slot 与 component 数据在 world 内扁平存储，hierarchy 是关系数据。理由：stale handle、slot reuse、component query 更清晰。被否决方案：tree-owned entity node，会让 transform ownership、identity、iteration 混在一起。后果：未来可以加 archetype 或 spatial index 而不改变 public identity。

(2) Reparent 默认 preserve world

决策：SetParent 默认保持 world transform，同时提供 preserve local 选项。理由：手动编辑场景时避免视觉跳变。被否决方案：总是 preserve local，运行时简单但编辑体验差。后果：实现需要使用 parent inverse；遇到 zero scale 时保持确定性 fallback。

(3) Render collection 不按 hierarchy 遍历

决策：summary 分类输出，category 内按 optional sort key 和 entity identity 排序。理由：render collection 以后可能来自 flat query 或 spatial index，树顺序不是渲染语义。被否决方案：hierarchy pre-order，会把 transform ownership 顺序误当作 render submission 顺序。后果：Renderer 后续仍可在 frame preparation 中做自己的 material/depth/light ordering。

六、设计巧思与最佳实践

1. 当前业务场景与业务模型的最佳实践

  • Generation-safe handle：slot reuse 不等于 identity reuse。旧 handle 必须因为 generation mismatch 失败，否则 destroy 后的引用可能修改新对象。
  • Relationship as data：hierarchy 不拥有 entity，它只表达 parent/children。这样 component iteration 和 transform traversal 可以各自优化。
  • Explicit mutation path：duplicate add 拒绝，update/replace 才能改组件，避免误把初始化 API 当覆盖 API。
  • Deterministic summaries：render collection 的输出不依赖 vector 内部布局，而依赖公开排序键，后续存储优化不会改行为。
  • Stable diagnostics：错误能测试、能 diff、能半年后看懂，比临时 log 更适合 engine foundation。

七、编程语言知识点

  • std::atomic<uint32> 用于分配 world id，让跨 world handle 不会误通过验证。
  • std::stable_sort 用于 diagnostics 和 render categories，保证 tie-break 之外的相对稳定性。
  • Core FTransform::TryInverse 对 zero scale 明确失败，reparent preserve world 因此需要 deterministic fallback。
  • Public headers 使用轻量值类型和 forward boundary，避免把 implementation-only 细节扩散到调用方。

八、软件工程知识点

  • Spec 中的 clarification 直接落到 tests：destroy descendants、duplicate add、slot reuse、reparent mode、two ordering keys。
  • 任务按 user story 组织，但实现把共享核心放在 FWorld，把 render collection 和 diagnostics 分成独立模块，避免单个函数承担全部责任。
  • CI 友好设计来自 headless、process-local、no asset/no GPU/no display 的约束。
  • Boundary grep 是一种低成本架构测试，能早发现 public header 泄漏。

九、渲染、引擎与图形 API 学习笔记

这一期没有调用图形 API，但它决定后续 Renderer 能拿到什么“场景事实”：mesh identity、world transform、light placement、camera projection。真实引擎中，这一步类似从 game/application scene 抽取 render scene 或 frame input；Renderer 再把这些抽象数据转换为 material sorting、draw command、descriptor binding、render graph pass。

把 Application scene summary 保持 backend-neutral，是多 API 架构的关键。Vulkan/DX12/Metal 需要完全不同的 resource binding 和 command recording，但它们都可以消费相同的 mesh/light/camera 抽象。这个边界让后续 Triangle Demo 或更复杂 render path 不必把 ECS 绑到某一个 backend。

019 — Deferred Rendering Pipeline

状态：已交付 · 更新：2026-07-24 · Roadmap Phase 018 · 层级：Renderer / RHI / Vulkan

一、文档与上下文信息

2. 本期核心摘要

本期把 deferred rendering 建成与 forward 并列的 Renderer Strategy：它验证 view、output、opaque/masked draw 和三类灯光，生成三颜色目标加 depth 的 surface layout、确定性 pass plan、Render Graph declaration，并通过新增的 backend-neutral RHI 命令录制 descriptor、index、clear 与 texture-to-buffer copy 意图。

学习重点是 deferred rendering 不只是“多几张 GBuffer”。真正困难的是跨层契约：法线在哪个空间、depth convention 如何贯穿 clear/compare/reconstruction、资源什么时候读写、局部光怎样限定体积，以及 deterministic test 与真实 GPU readback 的证据边界。

3. 上下文与依赖

Feature 019 建立在 RHI resource/pipeline、Vulkan command submission、Render Graph、Material System、Forward Renderer、Application window 与 triangle integration 上。它为 meshlet、ray tracing 混合渲染和 GI 铺路，同时保持 Renderer public headers 不依赖 Vulkan。

二、目标与边界

1. 业务与功能目标

引擎开发者提交一个 active view、LDR output、surface draw 与 directional/point/spot lights，即可得到可检查、可重复、可交给 RHI 的 deferred frame。无效 draw/light 被逐项拒绝并给出稳定诊断；view/output/layout 失败则阻止整帧进入执行。

2. 架构目标与定位

Scene / Application
  -> frame inputs
Renderer: FDeferredRenderer -> FramePlan -> RenderGraphDeclaration
  -> FDeferredFrameExecutor
RHI: abstract descriptors / index / clear / copy commands
  -> Vulkan backend: native resources and readback session
Core: math, containers, strings, diagnostics

surface semantics、light records、frame plan、diagnostics 和 executor 属于 Renderer contract；真实 VkImage、VkBuffer、fence、mapped memory 与 cleanup 只能位于 Vulkan private implementation。

3. 边界与非目标（约束）

  • 不做 tiled/clustered lighting：本期先用 sphere/cone volume 建立正确性基线。
  • 不做 shadows、SSAO、SSR、TAA：这些需要独立 pass 与历史资源策略。
  • 不改变 forward 默认策略：现有调用方必须保持行为兼容。
  • 不把 semantic oracle 当像素证据：Linux completion 必须来自实际 attachment copy/map/decode。
  • 不覆盖 Android：本阶段平台集合为 Windows、macOS、Linux。

三、交互与产品设计

1. 用户使用路径

FDeferredRenderer Renderer;
FDeferredFramePlan Plan;
Renderer.PrepareFrame(Inputs, Plan);
auto Graph = BuildDeferredRenderGraphDeclaration(Plan);
FDeferredFrameExecutor().Execute(Plan, Graph, Bindings);

调试时优先阅读 Plan.DebugDump 和 Diagnostics.GetFirstError()。native CI 则运行 run_deferred_validation.py --profile native-lavapipe，并检查 readback report。

2. 核心规则与状态机

Uninitialized -> BindingsValidated -> Recording -> Recorded
                                         \-> Failed
Native session: partial create -> submit/wait -> readback -> reverse release -> zero

executor 在录制前事务式验证所有必需 binding，避免录到一半才发现 attachment 或 pipeline 不兼容。发生错误后停止后续 stage，第一条 error 的所有权由原始 sequence 决定，不因展示排序改变。

3. 失败模式与调试入口

  • DEF-VIEW/DEF-OUTPUT：矩阵、extent 或 output 不匹配。
  • DEF-DRAW-NORMAL-MATRIX：model 上三阶矩阵奇异，无法构造 inverse-transpose。
  • DEF-EXEC-BINDINGS：RHI texture/buffer usage、format、lifecycle 不兼容。
  • DEF-EXEC-READBACK：copy-source transition、destination capacity 或 texture-to-buffer copy 不合法；executor 会停止后续 stage 并重置部分 command。
  • native failure suite 可注入 PartialInitialization、Record、Submit、Fence、Copy、Map、Decode、Probe，首个 stage、bounded wait 和 final live count 是主要排查入口。

四、技术架构与关键决策

1. 技术栈与基础设施

C++20、SCons 4.10.1、Vulkan 1.3-compatible loader、GLSL 和 checked-in SPIR-V。Windows/macOS/Linux 均跑 deterministic tests；Linux 用 Mesa Lavapipe 承担必需的 native offscreen readback。

2. 关键信息

2.1 模块对应关系

模块职责关键关系
FDeferredSurfaceLayout定义 BaseColor/AO、WorldNormal/Roughness、Emissive/Metallic 与 D32 depth同时约束 shader、pipeline 和 readback decoder
FDeferredRenderer验证并生成 deterministic frame plan与 Forward Renderer 并列
FDeferredFrameExecutor把 graph stage 翻译成 RHI command不知道 Vulkan handle
FDeferredLightVolumefrustum/camera-inside/near-plane 分类与 scissor控制 point/spot bounded work
FVulkanNativeOffscreenSession拥有 VkImage/buffer/descriptors/pipelines/commands/fence/staging，并执行 copy/map/decodeprivate Vulkan 实现；成功和八类 partial failure 均逆序释放到零

2.2 数据流、控制流或资源流

输入先被归一化并按 stable entity identity 排序；surface pass 写三个颜色附件与 depth；directional fullscreen 和 point/spot volume 读取 GBuffer 并 additive accumulate；composition 合并 lighting、emissive 与 ambient；transparent draw 在 composition 后交回 forward path；validation stage 将 attachment 转为 copy source 并计划 texture-to-buffer copy。

2.3 关键日志、诊断与可视化

dump 记录 layout、attachment semantics、accepted/rejected draw、light classification、pass reads/writes、composition output 与 transparent handoff，不记录指针或 native address。相同输入重复 20 次必须 byte-stable。

3. 架构决策记录 (ADR)

(1) GBuffer 法线采用 world-space

决策：存 direct normalized world-space normal，model normal 使用 inverse-transpose。理由：灯光同样以 world-space 描述，lighting shader 不必随 view 旋转重新解释法线。被否决：view-space normal 虽有相机局部数值便利，但会增加跨 pass/view 的转换耦合。后果：空间契约清晰，但必须严格测试非均匀缩放与奇异矩阵。

(2) Depth convention 是统一 identity

决策：standard-Z 与 reversed-Z 同时派生 clear、compare、projection/reconstruction 和 probe expectation。被否决：各 pass 自行配置 depth，它容易产生“几何通过、重建错误”的隐蔽 bug。后果：两套 convention 可以共享流程并分别验证。

(3) Native 证据必须来自 mapped readback

决策：CI helper 拒绝 semantic oracle。背景：CPU 参考值自比较只能证明公式，不能证明 attachment format、shader、pipeline、barrier 与 copy 正确。结果：run 30079550556 的 llvmpipe artifact 证明两种 depth convention 各 12 个 probe 全通过，final_live_objects=0。

(4) Instancing 必须携带 FirstInstance

决策：RHI 的 RecordDrawIndexed 增加 FirstInstance，executor 只合并 pipeline、inside/outside mode 和 scissor 相同的连续 local lights。背景：shader 通过 gl_InstanceIndex 索引统一 light storage；若 point 前有 directional records 而 draw 总从零开始，会读取错误灯光。被否决：仅减少 draw count 而不表达首实例索引，因为它统计上像 batching，执行上却不正确。

六、设计巧思与最佳实践

1. 当前业务场景与业务模型的最佳实践

  • 先冻结 semantic contract：shader、uniform offset、attachment format 和 decoder 使用同一布局，避免跨层“各自理解”。
  • 光源不设固定 cap：所有有效且影响 view 的灯都进入 plan；明确 outside-view 才可 cull，identity 是最终排序键。
  • 事务式 binding validation：任何缺失资源在 command begin 前失败，降低 partial recording 清理复杂度。
  • 真实证据与 deterministic 证据分层：前者验证 GPU 集成，后者提供跨平台快速回归。

2. 优化方案与收益

已实现的优化是一次 surface geometry sequence、outside-view local light omission、sphere/cone bounded intent、稳定批次顺序和常量 surface work。未来 tiled/clustered lighting 可复用 GBuffer 和 light record，而无需改变 scene ownership。

3. 已知限制与后续演进

本期完成的是 classic light-volume deferred baseline，不包含 tiled/clustered assignment、shadows、SSAO/SSR、TAA 或透明 deferred。comparison 使用可重复的工程基线而非产品性能承诺。后续 Meshlet、Ray Tracing 与 GI 可以复用 surface semantics、Render Graph 和 failure-safe native validation，但应各自建立 workload 与平台证据。

七、编程语言知识点

1. 标准库接口与用法

std::stable_sort 用于稳定展示诊断；std::ostringstream 生成规范化 dump；std::all_of/std::count_if 聚合 probe；std::unique_ptr 隐藏 Vulkan implementation；std::chrono 支持 comparison statistics。

2. 语言特性与惯用法

enum class 隔离 stage/result/semantic 命名；[[nodiscard]] 防止忽略失败；alignas(16) 与 static_assert(sizeof(...)) 固化 CPU/GPU mirrored record ABI；RAII session destructor 提供异常和早退时的释放兜底。

八、软件工程知识点

1. Contract-first 与可测试边界

先扩展 backend-neutral RHI，再实现 Vulkan deterministic validation，最后接 native runtime。这样 Renderer tests 无需显示设备，CI 仍能在 Linux 增加真实证据。

2. Evidence-driven completion

tasks 的 checkbox 不是完成事实本身。Feature 019 把 build、test、report schema、commit/run identity 与 retained artifacts 都列为 gate，并专门测试“错误证据必须失败”。

3. 回归与兼容

Forward 仍为默认策略，forward plan 不生成 deferred resource；transparent ordering 在 deferred composition 后复用既有 forward 规则。该约束防止新 renderer 破坏旧调用方。

九、渲染、引擎与图形 API 学习笔记

1. Deferred Rendering 的本质

Deferred 把材质表面求值与光照求值分开：geometry cost 主要发生一次，随后每个 light 只读取屏幕空间 surface data。这适合多灯场景，但会增加 attachment bandwidth、透明处理复杂度和 MSAA 成本。

2. 为什么需要 Light Volume

Directional light 影响全屏；point light 的 sphere 和 spot light 的 cone 提供保守影响边界。camera 位于 volume 内或 volume 穿 near plane 时，rasterization/cull mode 必须切换，否则会因近裁剪或背面剔除漏光。

3. Vulkan Readback 为什么是最终门槛

真实 readback 覆盖一整条链：image usage、memory allocation、render pass store、layout transition、pipeline barrier、copy region、fence wait、host mapping、row pitch 与 format decode。任何一步错，CPU 参考算法仍可能全绿；因此 Lavapipe artifact 是架构正确性的必要补充，而不是形式化装饰。

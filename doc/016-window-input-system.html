2. 本期核心摘要

本阶段交付了 Application 层的第一套可用运行时接口：单 primary window 的创建、关闭、销毁、尺寸/焦点/显示模式状态，按帧更新的键盘与鼠标输入快照，最小 application loop，以及 deterministic diagnostics/debug dump。真实窗口路径被保留在 private GLFW adapter 入口后方；当前默认用 headless 路径完成自动化验证。

最值得学习的是“窗口不是渲染，输入也不是平台事件本身”。Application 层把平台事件翻译成稳定的引擎状态，Renderer/Backend 后续只消费 resize、close、presentation-paused 等抽象信号，而不需要知道 GLFW、NSWindow、HWND、swapchain 或具体图形 API。

3. 上下文与依赖

  • 前置依赖：Core platform abstraction、Renderer dependency boundary、SCons layer builder。
  • 后续铺路：Triangle Demo、scene graph/editor input、renderer presentation 与 swapchain resize 处理。
  • 新增边界：Application public contract 不暴露 GLFW、native handle、RHI、swapchain 或 renderer presentation。
  • 编译期依赖：Application 仍只通过 SConscript 依赖 Renderer/Core；测试 executable 链接全层。

二、目标与边界

1. 业务与功能目标

  • 引擎调用方可以用 FWindowDesc 创建一个 primary window，并观察 active/close-requested/destroyed 生命周期。
  • 调用方可以用 FInputManager 每帧读取 pressed/held/released、pointer position 和 pointer delta。
  • 窗口失焦会立即清空 held key 和 mouse button，避免后续帧出现 stuck input。
  • FApplicationLoop 能在 headless 场景运行 300 帧，或在 close requested 时干净退出。
  • 无 display/dependency、非法尺寸、非法生命周期、未知输入都会产生稳定 diagnostics，而不是崩溃或静默成功。

2. 架构目标与定位

这里最关键的定位是：Application 负责“用户与窗口的运行时语义”，Renderer 以后负责“如何把 frame 呈现到 drawable/swapchain”。当前不做 swapchain recreation，也不做 triangle rendering。

3. 边界与非目标（约束）

  • 不做 multi-window：v1 只需要 primary window，避免 API 一开始就过度泛化。
  • 不做 text input/IME/layout translation：本阶段只表达物理键位状态，适合游戏控制和 deterministic tests。
  • 不做 gamepad/controller：后续输入设备可以复用 frame snapshot 思路单独接入。
  • 不做 renderer presentation/swapchain recreation：后续 triangle demo 或 presentation integration 再消费 resize/paused 信号。

三、交互与产品设计

1. 用户使用路径

FWindowDesc desc
FWindow window.Create(desc)
FInputManager input

while (running):
    window.PollEvents()
    input.PollFrame(window.GetLifecycleState(), window.IsFocused())
    if window.IsPresentationPaused():
        update only, skip presentation
    if window.IsCloseRequested():
        break
window.Destroy()

失败路径也必须是可观察的：例如 real-window dependency 不存在时，CreateRealWindow 返回 RuntimeUnavailable，diagnostics 中包含 APP-WINDOW-RUNTIME，不会留下半激活窗口。

2. 核心规则与状态机

Uncreated -> Active -> CloseRequested -> Destroyed
Uncreated -> Destroyed
Active -> Destroyed
CloseRequested -> Destroyed
Destroyed -> Destroyed

输入状态的核心规则是：pressed/released 是当前帧瞬态，held 跨帧保留直到 release 或 focus lost。focus lost 是一个强制清空点，因为真实桌面环境可能不会在失焦后继续发送 key-up/button-up。

3. 失败模式与调试入口

  • 尺寸为 0 或超过 16384x16384：看 APP-WINDOW-SIZE-ZERO / APP-WINDOW-SIZE-LIMIT。
  • poll input 发生在 create 前或 destroy 后：看 APP-INPUT-LIFECYCLE。
  • display-mode runtime 不支持：看 APP-WINDOW-MODE-UNSUPPORTED，旧模式必须保持不变。
  • debug dump 必须稳定且不含 native handle/pointer 细节，方便 headless regression diff。

四、技术架构与关键决策

1. 技术栈与基础设施

  • C++20，传统 header/source 分离，无 C++20 Modules。
  • SCons 4.10.1，BuildLayer 自动发现 Source/Application/Private/*.cpp。

代表性输入流是：driver/test 注入 FInputEvent -> FInputManager::PollFrame 按 sequence 排序 -> FInputState::BeginFrame 清空 transient -> 逐个应用 key/mouse/pointer/focus event -> 调用方读取 frame snapshot。

diagnostics 使用稳定 code，例如 APP-WINDOW-CREATED、APP-INPUT-FOCUS-CLEAR、APP-LOOP-CLOSE-EXIT。debug dump 汇总 window/input/loop 状态，但避免 pointer/native handle，这让 headless CI 能用字符串稳定性检测 regressions。

3. 架构决策记录 (ADR)

(1) Headless driver 是必需路径

背景：CI 和远程环境经常没有 display server。理由：窗口/input 的语义仍必须被测试。被否决方案：要求所有测试打开真实窗口，会导致 no-display 环境不可用。后果：真实窗口 smoke 变成 opt-in/unavailable-safe，而 headless 是默认 gate。

(2) Public API 不暴露 native handles

背景：窗口最终会服务 Vulkan、Metal、DX、OpenGL 等多后端。理由：public header 泄漏平台句柄会把上层绑死到某个平台或库。被否决方案：直接返回 GLFWwindow/HWND/NSWindow。后果：后续 presentation handoff 需要一个独立桥接阶段。

(3) Presentation-paused 是 loop 状态而不是 fatal error

背景：最小化或 zero drawable 是正常桌面状态。理由：应用还要处理 restore/close/focus/input。被否决方案：暂停整个 loop 或继续 presentation。后果：后续 swapchain recreation 可以消费这个明确信号。

六、设计巧思与最佳实践

1. 当前业务场景与业务模型的最佳实践

(1) Frame snapshot 而不是实时查询平台状态

每帧统一 poll 并冻结 snapshot，可以让游戏逻辑、camera control 和 editor tool 在同一帧看到一致输入。否则同一帧中前后两次查询可能读到不同平台状态，调试体验会很糟。

(2) Explicit lifecycle states

Uncreated/Active/CloseRequested/Destroyed 让非法调用有落点。比如 close requested 不立刻 destroy，是为了让 loop 在安全点退出，而不是平台事件突然打断资源清理。

(3) Deterministic unavailable runtime

GLFW 没有接入时不是失败崩溃，而是稳定返回 dependency unavailable。这个模式后续也适合 Vulkan SDK/runtime 缺失、Metal/DX 后端不可用等情况。

2. 优化方案与收益

当前优化主要是工程确定性：事件按 sequence 排序，resize 最终状态确定，diagnostics 稳定排序，dump 不含地址。收益不是 FPS，而是 CI 可重复、回归 diff 有意义、未来真实窗口/真实 swapchain 接入时有基线。

3. 已知限制与后续演进

  • GLFW adapter 当前是 unavailable-safe skeleton，真实窗口 smoke 需要依赖接入后扩展。
  • 没有 text input、IME、gamepad、multi-window；这些应作为独立 feature 增加。
  • presentation handoff 尚未实现；Triangle Demo 将把 window drawable/resize/paused 信号接入 RHI swapchain。

七、编程语言知识点

1. 标准库接口与用法

  • std::stable_sort：用于 deterministic event/diagnostic ordering，避免同 sequence 或同 code 顺序漂移。
  • std::ostringstream：用于构建 debug dump 和 diagnostic format，保证输出集中可控。
  • std::function：FApplicationLoop 的 update callback 让测试和未来 runtime 都能注入每帧逻辑。
  • std::vector via TArray：当前事件队列和状态集合规模小，简单容器足够。

2. 语言特性与惯用法

  • enum class：强类型表达 lifecycle、display mode、runtime availability、event type 和 result。
  • constexpr：FWindowDesc::MaxClientWidth/Height 固化 v1 尺寸边界。
  • [[nodiscard]]：提醒调用方不要忽略 create/destroy/mode change 等 result。
  • 头/源分离：public contract 在 Public/Application，private driver seam 在 Private。

3. 平台相关与编译器行为

CI workflow 使用 GitHub hosted runners 覆盖 Windows/macOS/Linux。Windows job 通过 ilammy/msvc-dev-cmd 进入 MSVC 环境，Linux/macOS 使用默认 Python/SCons 和系统 C++ 工具链。Public Application headers 不使用平台宏或平台对象，减少跨编译器差异。

八、软件工程知识点

1. 设计模式与架构模式

  • Strategy/Adapter：IWindowDriver 隔离 headless 与 GLFW 路径。
  • State Machine：FWindow 显式生命周期状态。
  • Value Object：FWindowDesc、FInputEvent、FWindowEvent 是可复制描述对象。
  • Contract Test：Application tests 只 include public minimal header，验证 public 行为而不是 private 实现。

2. 工程原则与方法论

  • 稳定接口优先：真实 GLFW 接入可以晚些做，但 public 行为先稳定。
  • 防御性编程：非法尺寸、非法 lifecycle、未知输入都返回 diagnostics。
  • 可测试设计：headless path 是第一等验证路径，不依赖 GUI 环境。
  • 跨平台治理：constitution v1.3.0 要求平台敏感 feature 更新 CI/equivalent validation。

3. 测试策略与质量保障

测试覆盖 happy path、negative path、boundary testing、lifecycle matrix、deterministic output 和 dependency boundary grep。最重要的质量门槛是：没有 display 也能证明窗口和输入语义正确；有真实 display 时再补 smoke，而不是把 GUI 环境作为默认前提。

九、渲染、引擎与图形 API 学习笔记

1. 本期核心概念拆解

(1) Drawable size 与 client size

Application 当前记录 client size 和 drawable availability。真实图形 API 中，swapchain extent 必须由后续 presentation 层处理；zero drawable 不能继续 present。

(2) Presentation-paused

这是给 Renderer/Backend 的跨层信号：窗口还活着，update/poll 继续，但 presentation/swapchain work 暂停。它避免了 “minimize == fatal error” 这种常见初学者 bug。

(3) Physical input vocabulary

物理键位适合 camera/game controls；文本输入适合 UI/编辑器。把两者混在一起会在键盘布局、IME 和快捷键上制造长期问题。

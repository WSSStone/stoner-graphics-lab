2. 本期核心摘要

本期交付 Renderer 层的材料与 shader 管理基础：可复用 FMaterial、可继承 FMaterialInstance、类型化参数集、抽象资源引用、显式注册的预编译 shader record、确定性 permutation 选择、材质到 shader variant 的 binding、资源需求摘要、诊断与稳定文本 dump。

学习价值在于它把“材质”从视觉概念拆成可验证的工程 contract。材质不直接持有 GPU 资源，也不编译 shader；它只表达渲染意图、参数、资源需求和 variant 选择，给下一阶段 Forward Renderer 一个稳定可测试的输入面。

3. 上下文与依赖

  • 建立在 RHI resource/pipeline contracts 与 Renderer render graph foundation 之上。
  • 为 Phase 014 Forward Rendering Pipeline 提供 material binding、shader variant 与 resource requirement 输入。
  • 编译期依赖 Core 与 Renderer public contracts；测试烟雾路径会消费 FRenderGraphBuilder，但 material 公共 API 不依赖后端。
  • 继续维护 Renderer public/private 边界：没有 Vulkan、Metal、DX、OpenGL 等 API 头进入 material/shader 代码。

二、目标与边界

1. 业务与功能目标

  • 开发者可以定义包含 shader reference、domain、blend mode、render state summary 和默认参数的材料。
  • 开发者可以创建继承自材料或其他实例的 material instance，通过最近覆盖规则解析最终参数。
  • Renderer 可以从显式注册的预编译 shader records 中选择确定性 variant，并在缺失 shader、未知 flag、缺失 variant 或参数不匹配时得到稳定诊断。
  • Render Graph 前的声明代码可以从材料或实例中提取抽象资源需求，而不需要 live RHI resource 或 graph-local handle。

2. 架构目标与定位

Application / future Forward Renderer
        ↓ consumes material binding and resource requirements
Renderer Material & Shader System
        ↓ uses Renderer graph concepts and Core containers/math
Renderer Render Graph Foundation
        ↓ later resolves to RHI resources and backend objects
RHI / Backend Vulkan, Metal, DX, OpenGL

FMaterial、FMaterialInstance、FShaderLibrary 和 FMaterialResourceRequirement 是 public contract；排序、校验、诊断格式化和 binding 组装是 private implementation。这个划分让后续 forward/deferred renderer 能消费稳定语义，同时保留内部演进空间。

3. 边界与非目标（约束）

  • 不做 runtime shader compilation，因为 shader 编译管线、反射和缓存属于后续工具链或渲染阶段。
  • 不扫描或加载本地 shader 文件，因为本期只支持显式内存注册，避免引入资产目录和文件格式。
  • 不实现 PBR 材质模型，因为 PBR 参数语义属于 Forward Renderer。
  • 不持有 live RHI resource 或 render graph local handle，因为材质应当长期复用，graph handle 只在单次 graph declaration 内有效。
  • 不做 visual material editor、scene graph、presentation 或 concrete render pass，这些在 roadmap 后续阶段接回。

三、交互与产品设计

1. 用户使用路径

happy path 是：创建 FMaterialDesc 和 FMaterialParameterSet，构造 FMaterial 并验证；注册 FShaderRecord 到 FShaderLibrary；可选创建 FMaterialInstance 覆盖参数；调用 ResolveMaterialShaderBinding 选择 variant；再调用 ExtractMaterialResourceRequirements 把抽象纹理需求交给 render graph declaration。

失败路径同样是产品设计的一部分：重复参数返回 DuplicateName，未知 override 返回 NotFound，类型不匹配返回 TypeMismatch，继承环返回 CycleDetected，未知 permutation flag 会在 variant lookup 前失败。

2. 核心规则与状态机

Draft
  ├── Validate succeeds -> Valid
  ├── Validate fails    -> Invalid / CycleDetected
  └── Invalidate        -> Invalidated

Valid
  ├── Resolve binding succeeds -> binding result
  ├── Resolve binding fails    -> diagnostics
  └── Invalidate              -> Invalidated

Invalidated
  └── Reset/clear and rebuild -> Draft

显式状态的价值是防止 stale object 被未来 renderer 当作可渲染对象。shader record、material、instance 都有失效语义，测试覆盖了 invalidated shader record 和 invalidated parent material。

3. 失败模式与调试入口

  • 如果参数名重复，看 MAT-PARAM-DUPLICATE 和 FMaterialParameterSet::AddParameter。
  • 如果实例解析不符合预期，看 FMaterialInstance::ResolveEffectiveParameters 的 parent chain 和最近覆盖顺序。
  • 如果 shader 选择失败，先区分未知 flag、缺失 variant、缺失 shader record、required parameter 缺失四类诊断。
  • 如果 render graph 无法消费资源需求，确认 material 参数是抽象 FMaterialResourceReference，不是 live resource 或 graph-local handle。

四、技术架构与关键决策

1. 技术栈与基础设施

  • C++20，传统 header/source 分离，UE5-style 类型命名。
  • SCons 4.10.1 自动发现 Renderer private sources；测试进入同一个 StonerTest。
  • 只使用 Core 容器、字符串、数学类型和 Renderer render graph public contract；无图形 API 头。
  • headless 测试路径不需要可见窗口、物理 GPU 或真实 shader 文件。

FMaterialDiagnosticLog 记录 severity、category、result、stable code、subject 和 message。result code 负责控制流，diagnostic 负责解释原因，dump 负责让测试和人类比较稳定输出。重复 dump 和 permutation 解析在测试中跑 20 次，确保没有 unordered iteration 漂移。

3. 架构决策记录 (ADR)

(1) 材质系统放在 Renderer 而不是 RHI

背景：RHI 只知道 shader module、pipeline、descriptor、resource；材质的 domain、blend、参数和实例继承属于渲染语义。

理由：Renderer 可以表达 forward/deferred/RT 共享的材料策略，同时不污染底层 RHI contract。

被否决方案：把 material 放进 RHI，会迫使每个 backend 理解高层材质。

后果：后续 renderer 需要把 material binding 翻译成 RHI descriptor/pipeline 输入。

(2) Shader library 只支持显式内存注册

背景：spec 明确排除 runtime compilation 和 file loading。

理由：显式注册让测试确定、无 I/O、无资产系统依赖。

被否决方案：扫描 shader 目录或即时编译，会把 shader toolchain、热重载和文件格式一次性拖进来。

后果：现在不能从磁盘发现 shader，但未来可在资产系统上层生成同样的 records。

(3) 资源参数只保存抽象引用

背景：材质生命周期长，render graph handle 生命周期短，RHI resource 归资源系统或 graph 管。

理由：抽象 reference 让材质可以稳定描述需求，实际解析延迟到 frame graph 或 pipeline 构建时。

被否决方案：材质直接持有 live texture，会造成生命周期耦合和跨 backend 泄漏。

后果：后续需要 resolver 把 reference 映射成 graph import 或 descriptor binding。

六、设计巧思与最佳实践

1. 当前业务场景与业务模型的最佳实践

(1) 最近覆盖优先级

实例链从 root material 开始，按 parent 到 child 应用 overrides，越近的实例越后写入。这避免复制整份材质，同时保留“只改一个参数”的语义。真实引擎里的 material instance、material layer 或 prefab override 都需要类似规则。

(2) Unknown flag 先于 missing variant

如果 shader record 没声明 USE_FOO，那就是材质请求错了；如果声明了但没有 variant，才是库缺资源。这个顺序让诊断更接近根因，避免把拼写错误误报成“资源不存在”。

(3) 抽象资源引用

材质保存 ReferenceId、kind 和 access intent，而不是真实 texture。这样可以在 render graph declaration 阶段统一 import、alias、transition 和 descriptor binding，减少长期对象持有短生命周期句柄的 bug。

(4) 稳定 dump 是测试资产

dump 不只是调试输出，也是 regression oracle。参数、shader records 和 requirements 都排序输出，确保同一输入反复运行得到 byte-identical 结果。

2. 优化方案与收益

当前实现偏向 clarity 和 deterministic behavior，数据量用 vector 排序即可满足代表性场景。未来如果材质库增长，可以在不改变 public contract 的情况下引入索引表、哈希缓存、shader record compiled summary 或 material binding cache。

七、编程语言知识点

1. 标准库接口与用法

实现主要使用 std::vector 背后的 TArray、std::sort、std::unique 和 std::ostringstream。关键点是所有 unordered 可能性都转为显式排序，避免 dump 和测试因容器迭代顺序漂移。

2. 语言特性与惯用法

  • enum class 用于 result、state、domain、blend、value type，避免跨语义整数误用。
  • desc/value 对象使用值语义，material/instance 保存 pointer parent 只表达非拥有引用。
  • 函数返回显式 EMaterialResult，诊断通过可选 log 收集，避免异常跨层传播。
  • 公共头保持轻量 include，private cpp 负责算法和格式化。

3. 平台相关与编译器行为

本阶段没有平台分支和图形 API 头。macOS 构建中出现的 confstr() temp dir warning 来自工具链环境，构建和测试仍返回 0，不影响 material/shader contract。

八、软件工程知识点

1. 设计模式与架构模式

  • Composite：material instance 链形成可递归解析的组合结构。
  • Registry：FShaderLibrary 是显式 shader record 注册表。
  • Value Object：parameter value、resource reference、permutation key 以值对象方式比较和 dump。
  • Facade：RendererMinimal.h 导出使用入口，但不隐藏模块职责。

2. 工程原则与方法论

  • Spec-driven：clarification 中的 5 个答案都被编码进实现和测试。
  • Fail close to source：重复参数在参数集失败，未知 flag 在 shader record 验证阶段失败，live resource 在 requirement extraction 失败。
  • Small contracts over god class：material、instance、shader library、resource requirements、diagnostics 分文件实现。
  • Headless-first validation：没有可见窗口和真实 GPU，也能验证渲染语义基础。

3. 测试策略与质量保障

新增测试没有只测 happy path，而是刻意覆盖容易在真实 renderer 中变成难查 bug 的路径：override 错名、类型错配、cycle、shader record 失效、required parameter 缺失、unknown flag 与 missing variant 的区别、资源引用边界和 render graph 消费烟雾。

九、渲染、引擎与图形 API 学习笔记

1. 核心概念拆解

(1) Material vs Pipeline

Material 表达“要用什么 shader、参数是什么、需要哪些资源”；pipeline 是后端可执行状态组合。本期没有创建 pipeline，是为了让 Forward Renderer 后续按 material binding、render pass 和 RHI pipeline layout 统一生成。

(2) Shader permutation

Permutation 是一组 feature flags，比如 USE_TEXTURE、USE_MASK。它必须 canonicalize，因为用户输入顺序不应该影响最终 variant。真实引擎会把它映射到 shader key、pipeline cache key 或 PSO key。

(3) Resource requirement

资源需求是 Render Graph 与 Material 之间的桥：材质说“我需要这个抽象纹理作为 sampled read”，graph 或 renderer 再决定 import 哪个 live resource、在哪个 pass 声明访问、何时 transition。

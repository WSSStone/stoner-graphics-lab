一、文档与上下文信息

1. 基础元数据

2. 本期核心摘要

本阶段把 Vulkan backend 从资源管理推进到可记录、可提交、可观察完成状态的命令系统。实现采用 deterministic fallback，不声称真实 GPU 执行，但完整覆盖命令生命周期、render pass scope、copy/barrier intent、同步对象和 upload scheduling 的行为契约。

3. 上下文与依赖

  • 依赖 009/010 已实现的 Vulkan device、queue、sync、buffer、texture、upload staging、diagnostics。
  • 扩展 RHI neutral command vocabulary，保持 public RHI headers 不包含 Vulkan 类型。
  • 后续 Vulkan Pipeline & Shader 阶段将消费本阶段的 command recording surface。

二、目标与边界

1. 功能目标

  • 创建并复用 command buffer，支持 Begin/End/Reset/Submitted/Resettable 状态迁移。
  • 记录 draw、indexed draw、dispatch、buffer copy、texture copy、barrier/layout transition、render pass begin/end。
  • 提交 executable command buffer 到兼容 queue，并处理 wait semaphore、signal semaphore、optional fence。
  • 把 pending upload request schedule 进 command buffer，但不提前标记为 GPU 已执行。

2. 架构定位

RHI command contracts | v Vulkan command pool -> Vulkan command buffer -> Vulkan queue submission | | | v v v diagnostics render pass scope fallback completion

3. 边界与非目标

暂不实现 shader compilation、pipeline creation、real pipeline binding、full resource state tracking、render graph scheduling、multi-threaded recording、visible rendering。这些内容留给后续 pipeline/render graph 阶段。

三、交互与产品设计

1. 使用路径

  1. 通过 FVulkanDevice::CreateCommandBuffer 为目标 queue 创建 command buffer。
  2. 调用 Begin() 进入 recording，按 queue 能力记录 graphics/compute/transfer 命令。
  3. graphics draw 必须包在 BeginRenderPass() 与 EndRenderPass() 内。
  4. 调用 End() 进入 executable 状态，再通过兼容 FVulkanQueue::Submit() 提交。
  5. 通过 WaitIdle() 或 backend completion observation 使 command buffer 进入 resettable。

2. 核心状态机

Idle -> Recording -> Completed -> Submitted -> Resettable -> Idle
          |             |             |
          +-- invalid --+-- invalid --+-- shutdown invalidates object

Upload request 的核心状态为 Pending -> Scheduled -> Invalidated。Scheduled 只表示命令记录已引用该 upload，不代表 GPU 执行完成。

四、技术架构与关键决策

1. 技术栈与基础设施

  • C++20 header/source separation，SCons 4.10.1。
  • Core aliases: TSharedPtr, TArray, fixed-width integer types。
  • Vulkan backend public headers 位于 Source/Backend/Vulkan/Public/VulkanRHI。

2. 模块对应关系

模块职责
FVulkanCommandPool按 queue type 管理 command buffer allocation 与 capacity exhaustion。
FVulkanCommandBuffer实现 RHI command lifecycle、recording validation、render pass scope、upload scheduling。
FVulkanQueue验证 executable command buffer，处理 sync，保存 fallback submission。
FVulkanCommandSubmission表达 deterministic fallback completion、not-ready、timeout 和 invalidated 结果。
FVulkanRenderPass/FVulkanFramebuffer最小 single-subpass/framebuffer validation，用于 command scope。
FVulkanDiagnostics记录 allocation、recording、submission、completion、upload scheduling 的最后原因。

3. ADR

ADR-011-01: 使用 deterministic fallback submission。 当前阶段需要验证 command API 和状态机，但还没有 pipeline/shader/real rendering。fallback path 明确写入 diagnostics，避免把“命令被接受”误读为“真实 GPU 执行”。

ADR-011-02: Draw/dispatch 作为 placeholder command。 允许记录命令并报告缺少 pipeline 的 diagnostics，保持后续 pipeline 阶段可增量接入。

ADR-011-03: Barrier/layout 记录 declarative intent。 本阶段只验证 lifecycle、usage compatibility 和 before/after 基本一致性，不引入完整 resource state tracker。

六、设计巧思与最佳实践

6.1 当前场景最佳实践

本阶段把“真实 Vulkan execution”与“backend contract 可验证性”拆开。这样 pipeline/shader 尚未存在时，命令系统仍然能被严格测试，且所有 fallback 行为都通过 diagnostics 公开。

6.2 优化方案与收益

  • Command pool capacity 可配置，便于测试资源耗尽路径。
  • Failed recording 不追加 command，避免半失败状态污染提交。
  • Shutdown 统一 invalidates owned objects，降低 dangling lifecycle 行为。

七、编程语言知识点

1. 标准库接口与用法

  • std::dynamic_pointer_cast 用于测试和 backend queue 识别 Vulkan concrete command buffer。
  • std::move 用于保存 render pass/framebuffer desc 和 submission command buffer ownership。

2. 语言特性与惯用法

  • 接口继承：FVulkanCommandBuffer final : IRHICommandBuffer 保持 RHI polymorphism。
  • 强类型 enum：状态机、command type、layout intent、submission mode 都使用 enum class。
  • RAII-like ownership：device 使用 shared ownership 保存 backend objects，并在 shutdown 统一 invalidation。

3. 平台相关与编译器行为

实现不依赖平台 Vulkan SDK 执行路径；缺少真实 runtime 时仍走 deterministic fallback。Mac 构建期间的 confstr() warning 不影响 build/test 结果。

八、软件工程知识点

1. 设计模式与架构模式

  • Facade：FVulkanDevice 对外统一创建 backend objects。
  • State Machine：command buffer、submission、upload request 都以显式状态拒绝非法操作。
  • Strategy-like fallback：queue submission 可表达 real/fallback/failed mode，目前落地 deterministic fallback。

2. 工程原则与方法论

  • 契约式设计：所有负路径返回 ERHIResult，并写入 diagnostics reason。
  • 边界清晰：RHI header 不包含 Vulkan 类型，backend-specific APIs 留在 VulkanRHI。
  • YAGNI：不提前引入 full resource state tracking 和 pipeline binding。

3. 测试策略与质量保障

测试覆盖 success path、negative path、capacity exhaustion、invalid ordering、queue incompatibility、fallback completion injection、resource invalidation 和 regression baseline，确保 011 能作为后续 pipeline/shader 阶段的稳定底座。

029 - Renderer HDR Post-Processing & Output Transform

版本 0.9 · 2026-09-03 · 实现完成、权威收尾待外部门禁 · 分支 029-hdr-output-transform
工程结论：Feature 029 已把 Forward/Deferred 的正式输出收敛为一个 Renderer 与 Render Graph 共同拥有的管线：RGBA16F linear Rec.709/D65 SceneColor 经过 manual exposure、pre-tonemap 插入、版本化 SDR tone map 或 ACES 2 HDR viewing transform、post-tonemap 插入、output-device gamut/transfer，再以同一 frame token readback 和 present。当前代码与 M4 非视觉验证已完成；Windows fresh SDR、维护者 SDR 接受和四模式 HDR 肉眼验收仍是明确阻塞门禁，因此不得把本阶段标为完成。

2. 本期核心摘要

工程交付上，本期不再让 Forward、Deferred 或 Backend 各自决定“最后一个像素怎么变成屏幕颜色”。两个 renderer strategy 只生产同一 typed SceneColor；Renderer 解析明确的 exposure、transform version 和 output profile，把 pass 接入现有 Render Graph，并在 terminal operation 全部完成后才发布 formal output。

学习价值上，本期最重要的是区分三个常被混在一起的概念：scene-referred HDR lighting、display-referred viewing transform、native presentation encoding。前者描述光照结果，第二层决定观感和峰值目标，第三层只是把既定信号放进 sRGB、PQ 或 linear EDR storage。只有把所有权分开，才能避免 double tone map、double transfer 和“readback 看对但屏幕看错”。

3. 上下文与依赖

  • 013 提供唯一 Render Graph；015/019 提供 Forward/Deferred producer；018 提供 native demo composition；027 提供 Metal private backend；028 提供真实 production content 和历史图像权威。
  • Feature 029 直接依赖 013、015、018、019、027、028。官方 ACES package v2.0.0+2025.04.04 commit 35e1e6a 只作为参考权威，不是 runtime dependency。
  • Feature 030 将在 pre-tonemap seam 放 TAA、在 post-tonemap seam 放 FXAA；029 故意不拥有 jitter、motion vector、history 或 reprojection。
  • Feature 028 v2 sampleCount=1、无通用后处理图像继续是历史证据；029 使用独立 v3 workload、Candidate 和接受记录，绝不覆盖旧 reference。

二、目标与边界

1. 业务与功能目标

  • Renderer integrator 为 Forward 或 Deferred 提交同一 RGBA16F linear Rec.709/D65 handoff，并得到唯一 formal output。
  • 图形开发者显式选择有限 manual exposure、三种 SDR curve 之一，或 HDR ACES 2 viewing transform 与 1000/2000 nit output profile。
  • 后续 feature 以稳定 identity、dependency 和 color domain 注册有限 pre/post operation，不接管 output transfer。
  • Demo/validation operator 能把同一 completed frame 关联到 command、readback、present、extent、generation 与 capability digest。
  • 维护者能独立处理 exact SDR Candidate 和 live HDR observation；机器不能替维护者接受。

Public contract 只暴露 backend-neutral format、color-space、capability、generation、frame token 和 result。Renderer private implementation 拥有颜色数学、profile resolution、graph declaration 和 shader parameter。Vulkan/Metal private implementation 独占 native API；它只能执行已选择的 format/color-space/metadata policy，不能偷偷改观感。

3. 边界与非目标（约束）

  • 不实现 AA/temporal：TAA/FXAA、jitter、motion vectors 和 history 属于 030，避免 temporal state 污染正式输出基础。
  • 不实现 bloom、景深、运动模糊、自动曝光：本阶段先冻结 color domain 和 insertion contract，这些 effect 后续按独立 feature 接入。
  • 不实现 HDR10+/Dolby Vision 或 vendor upscaler：当前仅固定 SDR、PQ 与 linear EDR 设备变换；vendor policy 不能成为基础 contract。
  • 不做 post-process editor：先证明 deterministic API、graph 和 lifecycle，再讨论编辑器 authoring。
  • 不允许 silent fallback：不支持的 HDR pair 返回 Unsupported；不能偷偷呈现 SDR。
  • 不自动判断 HDR 观感：HDR screenshot/FLIP 无法替代实体显示链路上的肉眼检查。

四、技术架构与关键决策

1. 技术栈与基础设施

Runtime 为 C++20；Metal implementation 为 private Objective-C++20/ARC；shader authority 是 GLSL 加 checked-in SPIR-V，经 Feature 027 的确定性 SPIRV-Cross/offline metallib 路径；验证工具只用 Python 3 标准库；构建使用 SCons 4.10.1。Vulkan runtime 缺失可以在 deterministic contract 层继续测试，但 native claim 必须来自真实 Vulkan/MoltenVK/Lavapipe；Metal native claim 必须来自 macOS Metal。

2.3 诊断与证据

  • deterministic diagnostics 记录 stage、first failure、profile/version、insertion digest、generation 和 token；不记录 native pointer、credential 或无界 path。
  • encoded storage 和 decoded comparison 分开。PQ 解码到 Rec.2020 absolute nits/XYZ；scRGB/EDR 先按各自 reference-white packer 解码，再比较 nits/XYZ。
  • SDR authority 只允许有界 lossless PNG/JSON；HDR authority 只允许 JSON/digest，禁止 screenshot 成为 authority。
  • M4 四 profile probe 的 machine result 只证明 native state/command/readback/present；它们不能产生人类视觉结论。

3. 架构决策记录（ADR）

3.1 ADR-001：颜色策略归 Renderer，不归 RHI/Backend

决策：tone/view/output transform identity 和数学全部由 Renderer 拥有。背景：同一 Vulkan/Metal format 可以承载不同 viewing preset；若 Backend 选择曲线，Forward/Deferred 与 API 会发生观感漂移。否决：让每个 swapchain adapter 自带 tone map，因为它会导致不可审计的 double transform。后果：跨 API 行为可测试，但 RHI 需要更精确的 capability/resolved-state vocabulary。

3.2 ADR-002：一个 Render Graph，不建立 post-process 小图

决策：扩展现有 graph 的 typed resource 与 schedule visitor。背景：独立 post-process graph 会丢失 producer barrier、lifetime 和 terminal side effect。否决：先在 Demo 中顺序调用 fullscreen shader；它无法证明真实 graph ordering。后果：基础 graph contract 略增，但 030 和后续效果可复用同一依赖系统。

3.3 ADR-003：Apple PQ 与 EDR 分平台治理

决策：Metal PQ 为 BGR10A2Unorm + ITU-R 2100 PQ + wantsEDR=true + EDRMetadata=nil，允许 Core Animation 对声明的 colorspace 做色彩管理，但不启用 CAEDRMetadata system tone mapping；Metal EDR 为 RGBA16Float + extended-linear sRGB，且同样 metadata nil。背景：Apple EDR 与通用 HDR10 metadata 模型不是同一机制。否决：把 Vulkan VK_EXT_hdr_metadata 一比一映射成 CAEDRMetadata，会把 engine-owned viewing transform 再交给系统。后果：平台诊断不同但 Renderer policy 统一，HDR 观感仍必须 live review。

3.4 ADR-004：机器 preflight 与人眼 authority 分离

决策：机器最多生成 ready-for-live-review request；attestation 没有自动 writer。背景：HDR screenshot 无法包含面板、OS compositor、当前 display mode 与观察者感知。否决：对 HDR PNG 跑 FLIP 或从 metadata 推导 pass。后果：closeout 有人工门禁，但不会出现“自动化绿灯冒充真实 HDR 观感”的假证据。

六、设计巧思与最佳实践

1. 当前业务场景与业务模型的最佳实践

  • Formal output 是资源身份，不是“最后一个 pass 的惯例”：FOutputTransformPlan 明确 single writer 和 frame/view identity，避免 debug pass 或旧 frame 被当成正式画面。
  • Color domain 是类型侧信息：pre-tonemap 只能看到 exposed linear HDR，post-tonemap 只能看到 display-linear；这比靠函数名约定更能拦住 FXAA/TAA 放错位置。
  • Requested 与 resolved state 分离：调用方可以请求 PQ，但证据只能引用 Backend 实际解析出的 format/colorspace/generation；防止 capability 变化后仍相信旧配置。
  • 同帧 terminal identity：command、readback、present token 必须一致，解决多帧并行时“截图来自 N-1、窗口来自 N”的隐蔽错误。
  • Candidate 不是弱 pass：缺 baseline 时仍保存有界审阅材料，但 aggregation 失败；这样既不丢调试信息，也不降低权威门槛。

2. 优化方案与收益

  • 已实现：空 insertion path 的 mandatory fullscreen pass 上限为三，可选 exact copy 单独计数；presentation-only 不触发 CPU readback，减少同步与带宽。
  • 已实现：immutable resolved plan/fingerprint 让 pipeline key、diagnostic 与 evidence 使用同一身份，降低重复解析和跨层漂移。
  • 已实现：surface/mode generation 让 resize/display move 只失效相关对象，且 stale object 在提交前被拒绝。
  • 未来铺垫：030 可复用 pre/post seam、typed graph 和 formal-output ownership，但不会因 029 而获得 temporal performance claim。

3. 已知限制与后续演进

本期 HDR 目标 peak 是 transform 配置，不是面板光度测量；EDR headroom 仍依赖当代 display capability。Deferred 默认维持 sampleCount=1，MSAA、DLSS/FSR/XeSS 后续再议。030 应新增 shared jitter、motion vector、history ping-pong、reprojection/rejection/invalidation；Screen-Space GI 必须复用同一 temporal framework，不得另建一套。

七、编程语言知识点

1. 标准库接口与用法

  • std::optional 表达“没有 HDR metadata”或 optional terminal request；nil 与空结构不能混淆。
  • std::variant/std::get_if 用于 typed graph/pass 或 Asset handle 分支，调用方必须显式处理类型不匹配。
  • std::unique_ptr 和 std::shared_ptr 分别表达 Backend/private owner 与跨 plan/execution 的 immutable evidence。
  • std::filesystem 只在 Application/validation 层管理 probe、lease 与 evidence path，不进入 Renderer public contract。
  • <cmath> 的 isfinite、exp2 与 double precision reference math 用于 exposure 和 conformance oracle；shader 结果按冻结容差比较。

2. 语言特性与惯用法

  • enum class 区分 color domain、transfer、presentation color space 与 result，避免整数互换。
  • constexpr 固定默认 profile/version 和边界值，使测试与 production 共享编译期身份。
  • [[nodiscard]] 标注 settings resolution、native reconfigure 与 execution result，防止忽略 fail-closed 返回。
  • RAII 负责 command、drawable、lease 与 frame-owned resource；失败路径按 owner 逆序释放。
  • 传统 public/private header separation 隐藏 Vulkan、Metal 和 Objective-C 类型；Feature 029 未采用 C++20 Modules。

3. 平台相关与编译器行为

Clang 编译 private Objective-C++/ARC，MSVC/GCC 只看到 RHI 公共值类型。packed 10-bit 与 FP16 的 native 名称、row layout 和 colorspace token 不跨 Backend 泄漏。Windows 不跑 HDR authority；Linux Lavapipe 用于 Vulkan native/readback 契约而非显示观感；macOS Metal live mode 需要真实 Cocoa window 和显示器，sandbox/headless 结果不能替代。

八、软件工程知识点

1. 设计模式与架构模式

  • Strategy：三种 SDR curve、HDR viewing transform 和 output-device packer 由稳定 version identity 选择。
  • Composite：pre/post operations 以受限 DAG/ordered list 组合，并统一验证 domain 与 resource budget。
  • Builder：graph builder 从 immutable plan 声明 typed resources/pass，而不执行 native command。
  • Adapter：Vulkan/Metal 将 RHI resolved state 映射到 native surface/layer；适配器不拥有观感策略。
  • State Machine：frame、surface、authority 与 attestation 都有不可跳跃的显式状态。
  • Contract Test：mock RHI 验证抽象语义，native suite 验证真实 API 映射，二者互不冒充。

2. 工程原则与方法论

依赖倒置让 Renderer 只面对 RHI contract；接口隔离让 presentation capability 不携带 tone-map policy；YAGNI 阻止 AA/bloom/editor 混入；DRY 由 Forward/Deferred 共用 output pipeline 实现，但不会把 Apple EDR 与 Vulkan HDR metadata 强行抽象成同一机制；防御性编程通过 exact pair、finite check、bounds、generation 和 immutable evidence fail closed。

3. 测试策略与质量保障

测试按 oracle 分层：math/vector 检查颜色真值，contract 测试检查拓扑和状态，native 测试检查 API 行为，production workload 检查真实内容，human attestation 检查显示观感。negative/boundary 覆盖 nonfinite、zero extent、unsupported pair、stale token、cycle、duplicate writer、one-pixel mutation 与 forbidden normalization。架构 grep 额外拒绝 Renderer native API、第二套 graph、runtime shader compilation 和越界 feature scope。

九、渲染、引擎与图形 API 学习笔记

1. 本期核心概念拆解

1.1 Scene-referred 与 display-referred

Scene-referred 值表达相对场景亮度，允许大于 1；display-referred 值已面向具体显示能力。误区是把 RGBA16F 等同于 HDR 显示：FP16 只是 storage，必须经过 viewing transform、gamut 和 transfer 才有显示语义。

1.2 Tone map、ODT 与 transfer

SDR curve 压缩动态范围；HDR ACES viewing transform 结合 viewing preset 产生目标 display-linear signal；PQ/sRGB 再编码 storage。把三者塞进 Backend 或重复执行会让亮度和颜色错误。

1.3 PQ 与 Apple EDR

PQ 是面向绝对亮度的非线性编码；Apple EDR 是 extended-linear 工作/合成路径，依赖 reference white 与 headroom。二者不应比较 raw code value，必须解码到 nits/XYZ。Metal PQ 允许 CA colorspace management，但 metadata nil 明确禁止系统接管 tone mapping。

1.4 Temporal 插入语义

TAA 需要 HDR scene signal，因此属于 pre-tonemap；FXAA 依据显示空间边缘，因此属于 post-tonemap。029 只提供 seam 和 domain，不实现 temporal state，这是 030 能保持单一框架的关键。

  1. FHDRSceneColorHandoff.h 与 FOutputTransformSettings.h：先理解输入和策略身份。
  2. FPostProcessInsertion.h 与 private validator：理解 color domain 和可组合边界。
  3. FHDRPostProcessPipeline.cpp、FOutputTransformGraphBuilder.cpp：跟随 plan 到 graph。
  4. FOutputTransformExecutor.cpp：查看 terminal publication 和同帧 token。
  5. RHI presentation headers：理解 requested/resolved capability 与 generation。
  6. FMetalPresentationContext.mm、Vulkan surface/swapchain：对照平台映射。
  7. OutputTransform.frag 与 CPU reference：对比 GPU/CPU 数学。
  8. Renderer、RHI、native、evidence tests：按 oracle 层验证上述假设。

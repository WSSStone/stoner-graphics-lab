2. 本期核心摘要

本期把 Feature 021 的 immutable texture mip chain cook 为标准 KTX2。ETC1S 与 UASTC 通过版本固定的 WebAssembly encoder 产生跨主机 canonical bytes；uncompressed LDR/HDR 由私有 container codec 写入。Asset 能 bounded inspect、load、transcode，Renderer 根据设备 capability 选择 BC、ETC2/EAC、ASTC 4x4 或 uncompressed fallback，RHI 和 Vulkan 再完成 block-aware texture realization。

本期最值得学习的是“存储格式”和“设备格式”必须解耦。KTX2/Basis 是 portable artifact，BC7、ETC2、ASTC 才是某台 GPU 的运行时表示。只有把身份、压缩、选择、footprint、上传分别放在正确层，才能避免 cook 结果依赖开发机 GPU，也避免 Asset 层反向依赖图形 API。

3. 上下文与依赖

022 依赖 021 的 Image/Texture payload、semantic mip 与 Renderer realization 模式，也复用 020 的 AssetId、digest、extension registry 和 execution lease。它扩展 008/010 的 RHI 与 Vulkan resource contract，并为 025 Cooker/Manifest、026 runtime Asset Manager、033 Streaming/Residency 提供 portable cooked texture。KTX、Basis 与 WAMR 是 Asset-private 编译依赖；Vulkan 只在 Backend 编译。

二、目标与边界

1. 业务与功能目标

离线或开发期调用方给出 FTextureAsset、typed cook settings 与 limits，成功后获得保持同一 FAssetId 的 immutable FKTX2TextureArtifact。运行时调用方可 inspect/load artifact，并根据 Renderer target profile 生成一次请求范围内的完整 mip payload。成功才发布 artifact、transcode payload 或 RHI texture；任何阶段失败都返回稳定 result 与 diagnostic，不留下半成品。

3. 边界与非目标（约束）

  • 不做 persistent derived-data cache、manifest 或 package：由 025 建立 key 与离线输出协议。
  • 不做 async loading、request coalescing、cancel：由 026 的 runtime manager 建模生命周期。
  • 不做 mip streaming、budget eviction、virtual texture：由 030 负责 residency。
  • 不做 cubemap、array、volume texture：本期只固定 2D complete-mip contract。
  • 不把 native Basis encoder 当权威输出：host toolchain 差异会破坏跨平台 byte identity。
  • 不让 fallback 冒充 native evidence：真实 Vulkan capability 与行为必须单独验证。

三、交互与产品设计

1. 用户使用路径

FTextureCookParameters Cook;
Cook.Texture = SourceTexture;
Cook.Settings.Compression = ETextureCompressionPolicy::ETC1S;
auto Artifact = Cooker.Cook(Cook);

auto Info = FKTX2TextureCodec::Inspect(Artifact.Bytes);
auto Profile = FTextureTargetProfile::DesktopDefault(Info);
auto GPU = FKTX2TextureRealizer::Realize({
    Device, Artifact.Payload, Profile
});

happy path 先 resolve semantic policy，再按 canonical mip 顺序编码并写 metadata，随后立即 reopen 比对 source facts。运行时先按 profile 顺序筛选 capability，再 transcode 全部 mips、交叉校验 RHI footprint、创建 texture 并升序 upload。失败路径从 diagnostic 的 stage、field、level 和 limit 定位。

2. 核心规则与状态机

cook:
Validate -> Resolve Policy -> Encode/Write -> Preflight -> Reopen -> Publish

load:
Lease Source -> Bounded Read -> Preflight -> Open -> Identity Check -> Publish

realize:
Validate Artifact -> Select Target -> Transcode All Mips
-> Create RHI Texture -> Upload mip 0..N -> Publish
any failure -> discard request state -> release texture exactly once

Color 可以是 linear 或 sRGB；Normal/Data 必须 linear。Data 使用 lossy UASTC 必须显式 opt-in。ETC1S、UASTC、Uncompressed 与 Balanced/High 都进入 cook revision，但 runtime target profile 不得改变 AssetId 或触发 recook。Compressed mip 即使小于 4x4 仍占一个完整 block。

3. 失败模式与调试入口

  • MalformedContainer：先看 FKTX2Preflight 的 identifier/range/alignment/overlap 诊断。
  • KTX2LimitExceeded：检查 dimension、artifact、metadata、pair、level、mip 或 target payload limit。
  • CorruptPayload：结构有效但 Basis global data 或 level bitstream 无法 transcode，结果不得含部分 mip。
  • target selection unsupported：查看每个 candidate 的 usage、semantic、channel、alpha 与 fallback rejection reason。
  • RHI upload 失败：检查 block origin、edge extent、row pitch、required bytes 和失败 mip。
  • 第三方漂移：运行 Tests/verify_ktx2_provenance.py 与 encoder digest suite。

四、技术架构与关键决策

1. 技术栈与基础设施

C++20、传统 header/source、SCons 4.10.1。KTX-Software 4.4.2 只编入 Asset private adapter；WAMR 2.4.5 采用 interpreter-only 最小配置；encoder 由 wasi-sdk 33.0 构建并以内嵌 byte array 进入测试与引擎。Khronos ktx validate 是独立 oracle，不与引擎链接同一 libktx。

2.2 数据流与资源流

Feature 021 mip bytes 与 typed settings 被序列化为稳定 request。ETC1S/UASTC module 返回完整 KTX2，Uncompressed codec 则写 DFD、KVD 和 level payload。Cooker 先做结构 preflight，再用私有 libktx reopen，并逐项核对 identity、source/content digest、cook revision、semantic、transfer、alpha、orientation 与 levels。运行时 transcode 只产生临时 CPU blocks；Renderer 用相同 RHI footprint 校验后才交给 Vulkan。

2.3 关键日志、诊断与验证

Diagnostic 记录稳定 stage/code/field/level/limit，不记录 pointer、thread ID、绝对路径或任意 third-party text。20-run JSON 固定 artifact 顺序、digest、source digest、quality 与 size。独立 validator report 使用 input-NN/relative/path 标签，屏蔽主机路径。九个自定义 stoner.* key 的 7010 集合必须完整且无重复，任何其他消息失败。

3. 架构决策记录 (ADR)

(1) WebAssembly encoder 是唯一 canonical producer

决策：固定 module bytes、ABI、toolchain 与整数路径。背景：native Basis encoder 可能因编译器、SIMD、线程调度产生不同 bytes。否决：各平台本地编译后只比较视觉质量，无法满足 exact derived-data key。后果：cook 更慢，但可复现性强；未来 cooker farm 可用独立进程扩展吞吐。

(2) KTX2 artifact 与 GPU target 分离

决策：artifact 保持 ETC1S/UASTC，Renderer 按设备选择 BC/ETC2/ASTC。否决：为每台 GPU cook 独立 Asset，会让 identity、cache 和 package 数量爆炸。后果：启动时有 transcode 成本，但同一 cooked artifact 可跨 API 和平台使用。

(3) RHI 统一 block footprint

决策：FRHIFormatInfo 是 Renderer、mock 与 Vulkan 的唯一 footprint 定义。否决：Backend 各自计算会在 odd extent、terminal mip 与 row pitch 上产生分歧。后果：portable tests 可精确预测 native upload；后续 backend 只负责映射。

(4) 自定义 metadata 使用窄 validator 例外

决策：继续 warnings-as-errors，但只接受九项完整 7010 集合。否决：移除 identity metadata 会降低 artifact 可诊断性；忽略全部 warning 会掩盖真实格式错误。后果：规则稍复杂，但 validator 仍然 fail closed。

六、设计巧思与最佳实践

1. 当前业务场景与业务模型的最佳实践

  • AssetId 与 cook revision 分离：quality 或 compression 改变 derived bytes，但逻辑 texture identity 不变。
  • 先 preflight 再 third-party parse：恶意 offset/size 在任何大 allocation 前被项目 limit 拦截。
  • 全 mip 或无结果：transcode/upload 在任一级失败时都清空请求状态，避免混合新旧 texture。
  • 候选顺序显式：Desktop profile 以 BC、ASTC、ETC2/EAC、fallback 表达政策，enum 和 capability 容器顺序不参与决策。
  • 小 mip 仍按 block 计算：1x1 BC7 依然需要 16 bytes，这是 compressed texture 最常见的边界错误之一。
  • Capability 是 usage tuple：格式存在不等于可 sampled 和 copy destination，二者必须同时满足。

2. 优化方案与收益

已实现 request-owned WAMR instance、只读 artifact、无跨请求 transcode cache、完整 mip 一次 publication、profile early rejection 和 block-tight upload，优先优化确定性、并发隔离与峰值可解释性。ETC1S 获得更小传输体积，UASTC 提供更高质量和更快 transcode。未来优化可在 025/026 引入 derived cache 和请求合并，在 030 引入按 mip residency，而不修改本期 artifact contract。

3. 已知限制与后续演进

当前 WebAssembly encoder 是单线程解释执行，适合确定性基线而非大规模离线吞吐；没有 package、cache、async manager 或 streaming。只支持 2D 与 ASTC 4x4。macOS 本机 native Vulkan 因 MoltenVK/Metal unavailable 只验证显式 unavailable 分支；Linux CI 的 Lavapipe 承担真实 compressed create/upload/readback 证据。

七、编程语言知识点

1. 标准库接口与用法

std::span 传递不拥有的 bounded KTX2/module bytes；std::shared_ptr<const T> 共享 immutable artifact 与 payload；std::optional 表达可选 identity/expected facts；std::numeric_limits 配合 checked add/multiply 防 overflow；std::mutex 和 thread-local WAMR environment 隔离初始化与请求；std::sort 固定 metadata 和 diagnostics 输出顺序。

2. 语言特性与惯用法

enum class 用于 policy、quality、format、stage 并对未知 cast fail closed；RAII wrapper 管理 libktx object、WAMR runtime/instance 与 registration lease；move-only result 降低大 payload copy；Strategy IKTX2Encoder 让 canonical runtime 与测试替身共享 contract；[[nodiscard]] 防止调用方忽略失败结果。

3. 平台相关与编译器行为

MSVC、Clang、GCC 都编译同一 public contract。Canonical encoder 禁用线程、SIMD、OpenCL 与 RDO，避免 host ISA 差异。Windows/MSVC 与 Unix path 不进入 normalized report。Vulkan SDK/runtime 缺失可走 deterministic backend tests；只有 native-capable host 才满足真实 image/upload/readback gate。

八、软件工程知识点

1. 设计模式与架构模式

IKTX2Encoder 是 Strategy；FWamrEncoderRuntime 与 libktx wrapper 是 Adapter；FKTX2TextureArtifact 是 immutable Value Object；FKTX2TextureRealizer 是跨 Asset/RHI Adapter；target profile 是显式 Policy Object；mock RHI 与 Vulkan 使用 Contract Test；preflight/open/transcode/realize 构成 compiler-like pipeline。

2. 工程原则与方法论

Dependency Inversion 保持 Asset 只依赖 Core；Interface Segregation 让 RHI 只表达 block/capability 而不理解 KTX2；Design by Contract 对 semantic、metadata、range、footprint 与 usage 逐层检查；YAGNI 暂不加入 cache/streaming；deterministic output 与 pinned provenance 让 derived data 可审计；防御性编程确保 untrusted local file 不放大资源消耗。

3. 测试策略与质量保障

Golden exact-byte test 防编码漂移；quality/size test 防“稳定但不可用”；mutation 与 first-above-limit 属于 boundary/negative testing；36+ capability cases属于 equivalence partitioning；failure injection 检查 transaction rollback；eight-way request 与 TSan 检查并发；independent KTX CLI 避免 writer/reader 共用 bug；architecture scanner 防依赖边界回归。

九、渲染、引擎与图形 API 学习笔记

1. 本期核心概念拆解

  • Basis universal representation：它不是最终 GPU format，而是可快速转为多种 block format 的中间表示。
  • ETC1S 与 UASTC：ETC1S 更偏体积，UASTC 更偏质量与 transcode 直接性；semantic policy 决定是否允许有损。
  • Block compression：footprint 按 block 向上取整，logical extent 与 storage extent 不相同。
  • Format capability：设备支持某 VkFormat 仍需分别查询 sampled image 与 transfer destination feature。
  • Cooked artifact：它是可缓存、可验证、跨设备的资产证据，不是 GPU object。

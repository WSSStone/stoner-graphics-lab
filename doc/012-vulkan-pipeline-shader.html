2. 本期核心摘要

交付 Vulkan shader/pipeline slice：shader module、显式 shader interface metadata、triangle-ready graphics pipeline、compute pipeline、process-local pipeline reuse、command binding validation 和 runtime/fallback diagnostics。draw/dispatch 不再只是 placeholder，而会检查绑定 pipeline 的类型和兼容性。

最值得学习的是“pipeline 是静态状态包”：现代 API 在创建 pipeline 时固定 shader、layout、vertex input、render target 和固定功能状态，执行时只绑定兼容对象。显式 interface metadata 是没有完整 reflection 之前保持可验证性的关键。

3. 上下文与依赖

  • 前置依赖：008 RHI shader/pipeline contracts and 011 command binding placeholders
  • 后续铺路：material system, render graph pass execution, pipeline cache persistence
  • 层级边界：Backend/Vulkan 只向下依赖已稳定 contract，不能反向 include 更高层模块。
  • 编译期依赖：公共头和 SCons 目标；概念依赖：spec/plan/tasks 中定义的 lifecycle、result、diagnostic 与测试替身。

二、目标与边界

1. 业务与功能目标

  • 创建并验证 shader module，区分 stage、bytecode 结构和 interface metadata。
  • 创建 graphics pipeline，验证 shader stages、layout、vertex input、topology 和 render target compatibility。
  • 创建 compute pipeline，验证单 compute shader 与 layout compatibility。
  • 用 process-local cache 复用等价 pipeline creation result。

2. 架构目标与定位

Application / Tests
    ↓ 使用 public contract
Backend/Vulkan feature: Vulkan Pipeline & Shader
    ↓ 依赖稳定下层能力
Core vocabulary / diagnostics / platform
    ↓ 按阶段连接
RHI contracts / Backend implementations / Renderer systems

本阶段的 public contract 是调用方可以依赖的最小稳定面；private implementation、测试替身和 backend-specific helper 都不能反向污染上层 API。

3. 边界与非目标（约束）

  • 不引入 shader compiler 和自动 reflection。
  • 不写 pipeline disk cache。
  • 不实现完整 material system、shader permutation 或 draw item batching。

三、交互与产品设计

1. 用户使用路径

创建 shader modules -> 创建/复用 pipeline layout -> graphics/compute pipeline desc 验证 shader interface 与 layout/render target -> cache lookup/insert -> command buffer BindGraphics/ComputePipeline -> Draw/Dispatch 验证已绑定且兼容。

学习时建议把这一段当成“最小工作流”：先找到输入对象，再跟踪它如何变成状态、诊断、测试断言或 debug dump。

2. 核心规则与状态机

未创建/空状态
    -> 描述或 Begin/Declare/Create
    -> 可验证中间状态
    -> Success: 可查询、可绑定、可执行或可复用
    -> Reset/Shutdown/Invalidated
    -> 任何后续使用必须返回错误结果或诊断

这个状态机是本项目底层模块的共同风格：显式创建、显式验证、显式失效。不同 feature 的状态名不同，但测试都围绕“合法转换”和“非法转换可观察”展开。

3. 失败模式与调试入口

  • shader stage 错误必须拒绝，例如 compute shader 不能创建 graphics vertex stage。
  • pipeline layout 与 shader interface 不一致会导致 descriptor 读取错误。
  • draw 时未绑定 pipeline 或绑定 compute pipeline 必须返回清晰 diagnostic。

调试入口优先看 Tests/VulkanBackendTests.cpp; Tests/RHICoreTests.cpp 中的负路径用例，再看对应 diagnostics、result code 或 debug dump 输出；这些测试比源码更快暴露设计意图。

四、技术架构与关键决策

1. 技术栈与基础设施

  • C++20，传统 header/source 分离；公共 API 遵守项目 UE-style 命名。
  • SCons 4.10.1 构建；验证入口保持在单一 StonerTest 可执行文件。
  • Core/RHI/Renderer public contract 尽量不泄漏 backend 或平台实现细节。
  • headless、fallback 和 mock 测试优先保证无 GPU/无窗口环境仍能验证语义。

3. 架构决策记录 (ADR)

(1) 显式 shader interface metadata

背景：当前没有 shader reflection。

理由：调用方显式描述资源需求，pipeline 创建可验证。

被否决方案：跳过 interface validation：会把错误推迟到 GPU 或 validation layer。

后果：未来接入 reflection 时可生成 metadata。

(2) process-local cache 而非 disk cache

背景：先验证等价 key 和 reuse 语义。

理由：避免文件格式、驱动 cache 与失效策略复杂度。

被否决方案：直接实现 disk cache：范围和平台差异过大。

后果：重启后不复用，后续可迁移。

六、设计巧思与最佳实践

1. 当前业务场景与业务模型的最佳实践

(1) Shader module

是什么：编译后字节码与 stage/interface 的封装。

项目表达：FVulkanShaderModule 保存结构摘要和生命周期。

真实引擎/API 对应：SPIR-V/DXIL/MSL library 都是 shader asset 到 pipeline 的中间形态。

(2) Pipeline layout compatibility

是什么：shader 资源需求必须匹配 descriptor layout。

项目表达：pipeline creation 和 command binding 都检查兼容性。

真实引擎/API 对应：Vulkan pipeline layout、DX12 root signature、Metal argument layout 是核心映射。

(3) Pipeline cache key

是什么：昂贵创建结果需要稳定复用条件。

项目表达：FVulkanPipelineCache 使用 process-local stable keys。

真实引擎/API 对应：真实引擎通常还会加 shader hash、render state、driver cache UUID。

2. 优化方案与收益

本阶段的优化重点不是追求最终性能，而是建立可替换的语义基线：先让行为被测试锁住，再在未来引入 SIMD、真实 Vulkan runtime、更复杂 allocator、pipeline disk cache、render graph aliasing 或 async compute。

这种做法的收益是 migration cost 可控：只要 public contract 和测试矩阵稳定，private implementation 可以逐步从 mock/fallback 演进到真实 GPU 路径。

七、编程语言知识点

1. 标准库接口与用法

本项目优先使用标准库可移植能力，例如容器、智能指针、字符串、chrono、filesystem、mutex 和 algorithm。关键不是“用了哪个库”，而是把标准库行为包装进项目自己的 contract，减少跨模块直接耦合。

2. 语言特性与惯用法

  • RAII/ownership：资源对象在 shutdown/invalidate 时显式失效，避免悬空后继续成功。
  • enum class：用强类型枚举表达 result、queue、usage、stage、state，避免整数误传。
  • 值语义和移动语义：desc、handle、record 适合轻量复制；拥有对象则通过指针或明确 lifecycle 管理。
  • 宏只用于日志/断言等需要调用点上下文的场景，其余优先函数和类型系统。

3. 平台相关与编译器行为

平台相关代码应留在 Core platform 或 Backend private 边界内。公共头尽量避免平台宏分叉和图形 API 头泄漏，这样 Windows/macOS/Linux 与未来 Vulkan/DX/Metal/OpenGL backend 才能共享上层代码。

八、软件工程知识点

1. 设计模式与架构模式

  • Layered Architecture：Core -> RHI -> Backend/Renderer 的依赖方向必须单向。
  • Facade/Aggregate Header：CoreMinimal、RHIMinimal 或 RendererMinimal 提供便利入口，但不能隐藏边界污染。
  • Builder/Compiler/Executor：复杂声明式系统先收集意图，再编译计划，最后执行。
  • Adapter：Backend/Vulkan 把具体 API 对象适配成 RHI contract。

2. 工程原则与方法论

  • Contract-first：先定义 public behavior，再实现 backend 或优化。
  • Fail fast but diagnosable：错误尽早返回，同时留下能解释原因的记录。
  • Determinism：排序、dump、fallback 和测试输出都尽量稳定。
  • YAGNI with escape hatch：推迟工业级复杂能力，但保留未来接入点。

3. 测试策略与质量保障

测试不是只证明“代码能跑”，而是把工程假设固化下来：合法路径、非法路径、边界隔离、重复运行稳定性和 fallback/headless 环境都应该被覆盖。对图形工程而言，mock 与 fallback 不是偷懒，而是让 CI 可以在没有真实 GPU 的情况下守住 contract。

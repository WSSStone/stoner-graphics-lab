012 — Vulkan Pipeline & Shader

版本：1.0 · 更新日期：2026-06-30 · 状态：已交付 · Spec：specs/012-vulkan-pipeline-shader

一、文档与上下文信息

1. 基础元数据

阶段定位：Roadmap Phase 011，对应 Speckit 目录 012-vulkan-pipeline-shader。

代码范围：Source/RHI/Public/RHI、Source/Backend/Vulkan、Tests。

2. 本期核心摘要

本阶段把 Vulkan 后端的 shader module、graphics pipeline、compute pipeline、pipeline layout compatibility、process-local pipeline cache 和 command buffer pipeline binding 从占位行为推进为可验证实现。

3. 上下文与依赖

依赖 009 Vulkan resource management 和 010 command recording/submission。前置的 buffer/texture/sampler/descriptor/render pass/framebuffer/command buffer 能力被复用为 pipeline 创建与绑定验证的基础。

二、目标与边界

1. 业务与功能目标

  • 创建可查询、可失效、可诊断的 Vulkan shader module。
  • 创建 triangle-ready graphics pipeline 和 compute pipeline。
  • 让 draw、indexed draw、dispatch 能区分 missing pipeline 与 compatible bound pipeline。
  • 提供进程内等价 pipeline 请求复用诊断。

2. 架构目标与定位

Renderer/Application 仍只依赖 RHI 抽象。Vulkan 细节留在 Backend/Vulkan 内部，新增的 runtime mode、reuse state、interface metadata 被表达为 RHI 级契约。

3. 边界与非目标

未实现运行时 HLSL/GLSL 编译、自动反射、持久化磁盘 pipeline cache、material system、render graph、mesh shader、ray tracing 或可见 triangle demo。

三、交互与产品设计

1. 用户使用路径

  1. 创建 Vulkan device。
  2. 用结构合法的预编译 payload 和显式 interface metadata 创建 vertex、fragment、compute shader module。
  3. 创建包含 descriptor bindings 和 small constant ranges 的 pipeline layout。
  4. 创建 graphics/compute pipeline，重复等价请求可观察 cache reuse。
  5. 在 command buffer 中 bind pipeline，再记录 draw/indexed draw/dispatch。

2. 核心规则与状态机

对象状态遵循 Valid -> Invalidated。失败创建不会返回可用对象，也不会污染 pipeline cache。设备 shutdown 会失效 shader、layout、pipeline、command binding 和 cache records。

四、技术架构与关键决策

1. 技术栈与基础设施

C++20 传统头源分离，SCons 4.10.1，沿用 Core/RHI 容器与 result/lifecycle conventions。Vulkan SDK 不可用时走 deterministic fallback。

2. 关键信息

模块职责
FRHIShaderModuleDesc承载 bytecode、interface metadata、validation mode、runtime mode。
FVulkanShaderModule保存 shader desc、stage、interface、lifecycle、fallback diagnostics。
FVulkanPipelineLayout验证 descriptor binding 与 small constant ranges 是否满足 shader interface。
FVulkanGraphicsPipeline保存 triangle-ready fixed-function state、runtime mode、reuse state。
FVulkanComputePipeline验证 compute shader 与 layout compatibility。
FVulkanPipelineCache基于 shader identity、layout、pipeline state 生成 stable key，进程内复用成功对象。
FVulkanCommandBuffer记录 bind graphics/compute pipeline，并更新 draw/dispatch diagnostics。

3. 架构决策记录

  • 用显式 interface metadata 替代自动 shader reflection，避免提前引入 shader toolchain。
  • 真实 runtime 可用时保留 runtime mode 表达；当前无 runtime 时 deterministic fallback 仍可跑通契约测试。
  • pipeline cache 只做 process-local reuse，不读写磁盘，降低版本和失效策略复杂度。

五、实施与验证（任务流）

5.1 任务拆解清单

  • 扩展 RHI shader/pipeline/layout/command contracts。
  • 新增 Vulkan shader、graphics pipeline、compute pipeline、pipeline cache 对象。
  • 接入 FVulkanDevice factories、ownership、shutdown invalidation、configured failure limit。
  • 接入 FVulkanCommandBuffer bind/draw/dispatch diagnostics。
  • 更新 RHI mock tests 与 Vulkan backend integration tests。

六、设计巧思与最佳实践

6.1 当前业务场景与业务模型的最佳实践

本阶段没有把 pipeline 创建塞进 command buffer，而是保持 device factory、pipeline object、layout compatibility、command binding 各自独立。这样后续 Render Graph、Material System 可以复用相同 RHI 契约。

6.2 优化方案与收益

process-local cache 让重复 graphics/compute pipeline 请求得到确定性 reuse diagnostics。失败、unsupported、invalidated 请求不会成为成功缓存项，避免后续 renderer 重试时复用脏状态。

七、编程语言知识点

1. 标准库接口与用法

  • std::shared_ptr/std::weak_ptr：通过项目别名 TSharedPtr/TWeakPtr 管理对象生命周期和 command binding 的非拥有引用。
  • std::ostringstream：构造 pipeline cache stable key。
  • std::move：移动 desc 到 Vulkan backend 对象内部保存。

2. 语言特性与惯用法

使用 enum class 表达 runtime/reuse/validation 状态，使用 inline validation helper 保持 header-only RHI 描述验证，使用 RAII 风格对象持有 desc 与 lifecycle state。

3. 平台相关与编译器行为

SCons 继续通过 STONER_VULKAN_SDK_AVAILABLE 表达 SDK 可用性。本次实现不依赖平台 Vulkan runtime 才能完成契约验证。

八、软件工程知识点

1. 设计模式与架构模式

RHI 继续作为 Strategy/Facade 边界；Vulkan backend 提供具体实现。Pipeline cache 采用小型 repository/cache 模式，command buffer binding state 采用显式状态记录。

2. 工程原则与方法论

保持 decoupled architecture、contract-first validation、防御性编程和 YAGNI。高级 shader/reflection/cache 持久化功能全部延后。

3. 测试策略与质量保障

覆盖 success、negative、configured failure、runtime fallback、reuse、binding、shutdown invalidation 和旧回归。边界检查确认 public RHI/Vulkan headers 没有 Renderer/Application 依赖泄漏。

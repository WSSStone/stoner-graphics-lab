010 — Vulkan Resource Management

更新日期：2026-06-30 · 状态：已交付 · 对应 Roadmap Phase 009

一、文档与上下文信息

1. 基础元数据

项目内容
Specspecs/010-vulkan-resource-management
实现范围Vulkan 后端资源管理：buffer、texture、sampler、pipeline layout、descriptor pool/set、upload staging。
验证入口conda run -n godot scons 与 Build/Mac/Debug/Tests/StonerTest

2. 本期核心摘要

本阶段把 Vulkan 后端上一阶段遗留的资源 factory 从显式 unsupported 推进为可用的资源管理切片。实现并验证了确定性 fallback allocation、可配置分配失败、固定容量 descriptor pool、descriptor binding 保留查询，以及只记录 CPU-visible 数据和目标范围的 upload staging。

3. 上下文与依赖

  • 依赖 007 的 RHI resource/pipeline contracts：资源生命周期、descriptor layout、descriptor set 更新接口。
  • 依赖 009 的 Vulkan device/swapchain：device lifecycle、diagnostics、queue/sync/surface/swapchain 基线。
  • 当前阶段不要求 Vulkan runtime 存在；SDK 或 runtime 不可用时，资源合约使用 deterministic fallback 路径验证。

二、目标与边界

1. 业务与功能目标

为后续 command recording、pipeline、shader 和 render graph 阶段提供真实可查询的后端资源对象，而不是继续停留在 unsupported placeholder。

2. 架构目标与定位

RHI Interfaces | v FVulkanDevice |-- FVulkanMemoryAllocator -> FVulkanResourceAllocation |-- FVulkanBuffer / FVulkanTexture / FVulkanSampler |-- FVulkanPipelineLayout -> FVulkanDescriptorPool -> FVulkanDescriptorSet `-- FVulkanUploadRequest

3. 边界与非目标

  • 不实现 command buffer recording 或 queue execution。
  • 不实现 shader compilation、graphics/compute pipeline、render pass、framebuffer 或 render graph scheduling。
  • 不把 Vulkan allocation detail 泄漏到通用 RHI public contracts。

三、交互与产品设计

1. 用户使用路径

  1. 初始化 FVulkanDevice。
  2. 通过 RHI factory 创建 buffer、texture、sampler、pipeline layout、descriptor set。
  3. 通过 descriptor set 更新 buffer/texture/sampler/combined bindings。
  4. 通过 staging API 创建 pending upload request。
  5. shutdown 时所有后端资源统一进入 invalidated 状态。

2. 核心规则与状态机

Resource: Valid -> Invalidated
Allocation: RealRuntime | DeterministicFallback | Failed -> Released
Upload: Pending -> Invalidated

Invalidated 对象仍然可查询，但不能参与新的 descriptor update 或 upload staging。

四、技术架构与关键决策

1. 技术栈与基础设施

  • C++20，传统 header/source 分离。
  • SCons 4.10.1，Vulkan backend source 自动发现。
  • Core 层 TSharedPtr、TWeakPtr、TArray 作为项目内统一容器/指针入口。

2. 关键信息

2.1 模块对应关系

模块职责
FVulkanMemoryAllocator估算资源字节数、选择 real/fallback mode、执行 budget/count 限制。
FVulkanBuffer / FVulkanTexture保存 RHI desc、生命周期和 allocation record。
FVulkanDescriptorPool固定容量 descriptor set 分配与 exhaustion 行为。
FVulkanDescriptorSet验证 layout binding、保留绑定记录、报告 invalidated resource。
FVulkanUploadRequest保存 CPU-visible staging data 与目标 buffer/texture 范围，不声明 GPU 执行。

2.2 关键诊断

FVulkanDiagnostics 增加 resource allocation、allocation failure、descriptor pool、descriptor update、upload rejection 等原因字段，便于测试和未来开发者排错。

3. 架构决策记录 (ADR)

  • 确定性 fallback allocation：避免开发机缺少 Vulkan runtime 时资源测试全部不可运行。
  • 测试可配置分配失败：使用 budget/count limit 替代真实内存耗尽，结果更稳定。
  • descriptor 记录保留：资源 invalidated 后保留绑定记录，使错误可诊断而不是被静默清空。
  • upload 只 staging：尊重 roadmap 边界，把 GPU transfer 留给 command submission 阶段。

六、设计巧思与最佳实践

6.1 当前业务场景与业务模型的最佳实践

本阶段让资源生命周期和 allocation lifecycle 分离：资源对象负责 RHI 查询与 invalidation，allocator 负责分配统计和可控失败。这让后续真实 Vulkan memory path 可以替换 allocator 内部策略，而不影响 RHI 层调用方式。

6.2 优化方案与收益

  • 固定容量 descriptor pool 让 exhaustion 测试直接、稳定。
  • weak binding records 避免 descriptor set 强行延长资源生命周期，同时保留诊断能力。
  • upload staging 复制 CPU 数据，为未来 transfer command 生成保留真实输入。

七、编程语言知识点

1. 标准库接口与用法

  • std::shared_ptr / std::weak_ptr：用于资源对象与 descriptor/upload 对目标资源的非拥有引用。
  • std::map：用 binding slot + array index 作为 descriptor binding record key。
  • std::memcpy：复制 upload staging 的 CPU-visible 数据。

2. 语言特性与惯用法

  • RAII 风格的 descriptor set 析构释放 pool allocation。
  • 接口继承实现 RHI 多态，同时保持 Vulkan 具体类型可被测试侧 downcast 查询。
  • noexcept 用于纯查询和确定性状态转换辅助。

3. 平台相关与编译器行为

构建中没有新增平台 API 依赖；macOS 下出现的 confstr() 临时目录 warning 不影响构建和测试结果。

八、软件工程知识点

1. 设计模式与架构模式

  • Facade：FVulkanDevice 对外集中暴露 resource factory 和 staging API。
  • Strategy-ready allocator：当前 fallback/limit 策略封装在 allocator 内，未来可替换为真实 Vulkan memory allocator。
  • 契约式设计：descriptor/update/upload 先验证，再改变状态。

2. 工程原则与方法论

  • YAGNI：不提前实现 command execution 和真实 pipeline。
  • 边界隔离：所有 Vulkan resource implementation 保持在 Source/Backend/Vulkan。
  • 可诊断失败：失败返回显式 ERHIResult，同时写入 diagnostics reason。

3. 测试策略与质量保障

测试覆盖成功路径、无效描述、budget/count limit、descriptor pool exhaustion、wrong type/missing binding、retained invalidated binding、upload missing data/out-of-bounds/invalid region，以及 shutdown invalidation 回归。

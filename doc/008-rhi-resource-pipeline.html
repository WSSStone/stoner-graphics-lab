2. 本期核心摘要

本阶段完成第二层 RHI 合约：buffer、texture、sampler、shader module、pipeline layout、descriptor set、graphics/compute pipeline、render pass 与 framebuffer。生产代码只增加 public RHI contract headers 和 IRHIDevice 工厂扩展，所有行为验证通过 deterministic mock tests 完成。

这让 Vulkan resource/pipeline、Renderer render graph、material system 和 forward pipeline 后续阶段拥有统一语言：资源如何描述、如何绑定、pipeline 如何声明、render target 如何匹配，以及 Valid/Invalidated 生命周期如何被显式拒绝。

二、目标与边界

1. 业务与功能目标

US1 — 描述并创建 RHI 资源 P1 MVP

开发者可以用稳定描述对象创建 buffer、texture、sampler，并查询原始描述、usage、format/dimension 和 lifecycle。

US2 — 通过 layout 与 descriptor set 绑定资源 P1

支持 multi-set pipeline layout，descriptor binding 使用 set index + binding slot，descriptor set 能验证 buffer、texture、sampler 与 combined texture-sampler 更新。

US3 — 定义 graphics/compute pipeline P1

shader module 保存 stage、entry point 和 opaque payload identity；graphics/compute pipeline 验证 shader stage、layout 和 render target 兼容性。

US4 — 建模 render pass 与 framebuffer P2

单 subpass render pass 描述 color/depth-stencil attachment、load/store 行为，framebuffer 验证 texture attachment 的 count、format、dimension 和 sample count。

US5 — 生命周期与聚合 smoke flow P2

所有新增对象都有 Valid/Invalidated 状态，mock tests 覆盖成功路径、负路径和 renderer-facing 完整串联流程。

2. 架构目标与定位

本阶段仍属于 RHI 层，只定义跨后端的 contract。Renderer 可以依赖这些接口来表达资源和管线意图，Backend 可以在后续阶段实现真实 GPU 对象；测试 mock 则提供当前唯一的行为实现。

3. 边界与非目标（约束）

不做什么原因
真实 GPU memory allocation / resource upload属于 Vulkan resource management 阶段。
shader bytecode validation / compiler integrationshader module 只保存 opaque payload identity。
真实 backend handles 或 graphics API 头public RHI header 必须保持 backend/renderer/application 独立。
full multi-subpass render graph当前只固定 single-subpass render pass contract。
ray tracing / mesh shader pipeline枚举预留未来阶段，但当前请求会被显式拒绝。

三、交互与产品设计

1. 用户使用路径

IRHIDevice
  -> CreateBuffer / CreateTexture / CreateSampler
  -> CreatePipelineLayout
  -> CreateDescriptorSet(layout, set index)
  -> UpdateBuffer / UpdateTexture / UpdateSampler
  -> CreateShaderModule
  -> CreateGraphicsPipeline / CreateComputePipeline
  -> CreateRenderPass
  -> CreateFramebuffer

2. 核心规则与状态机

对象状态/规则
Resource / Pipeline-family objectsValid -> Invalidated；Invalidated 后仍可查询状态，但不能用于绑定、pipeline 创建或 framebuffer 创建。
Usage flagsbuffer/texture usage 可组合；显式非法组合返回 InvalidState 或 Unsupported。
Pipeline layoutbinding 使用 SetIndex + BindingSlot，同一 set 内重复 binding 被拒绝。
Descriptor set只能更新 layout 中声明过的 binding；descriptor type、array index、resource lifecycle 均要验证。
Shader module必须有支持的 stage、entry point、payload identity；bytecode 不在本阶段验证。
Render pass / framebuffersingle-subpass；framebuffer attachment 必须匹配 render pass 的 format、count、dimension 和 sample count。

3. 架构决策记录（ADR）

ADR-008-01：public header 只定义 contract，mock behavior 放测试

这保持 RHI 层干净，避免测试替身变成生产 backend。真实 Vulkan/Metal/DX12 后端以后实现同一 contract 即可。

ADR-008-02：multi-set pipeline layout 一开始就进入 contract

set index + binding slot 能表达 global、material、object、pass 等常见资源集合，避免未来 render graph/material system 重写 binding 模型。

ADR-008-03：shader module 不验证 bytecode

当前阶段只需要 stage、entry point、opaque payload identity 来验证 pipeline 组合。编译器、反射和字节码校验留给 shader/backend 阶段。

ADR-008-04：single-subpass render pass 作为最小稳定模型

它足以支持早期 forward rendering 与 framebuffer 兼容性检查，同时避免在 render graph 尚未实现前引入完整 subpass dependency 复杂度。

六、设计巧思与最佳实践

6.1 当前业务场景与业务模型的最佳实践

  • 设备作为唯一工厂：资源、pipeline、render pass 都由 IRHIDevice 创建，便于未来统一能力检查和 backend ownership。
  • 分离描述与对象：F*Desc 表达意图，I* 对象表达已创建资源，mock tests 可验证描述保真。
  • 显式失败值：invalid desc、unsupported stage/format、Invalidated dependency 都返回 ERHIResult，不依赖异常或断言。
  • Invalidated 可查询但不可使用：这给 device shutdown、资源释放、descriptor update 和 framebuffer compatibility 提供统一语义。

6.2 优化方案与收益

  • contract header 轻量化降低后续 Backend/Renderer include 成本。
  • mock-only validation 让 feature 在无 GPU、无窗口、无 shader compiler 的环境中稳定测试。
  • multi-set descriptor layout 提前对齐现代显式图形 API 与常见 material/pass/object binding 结构。

  • constexpr 用于 flag operator 与轻量描述验证 helper。
  • pure virtual interface 继续保持 RHI contract-first 风格。
  • aggregate initialization 用于紧凑构造 descriptor 和 test case。

八、软件工程知识点

1. 设计模式与架构模式

  • Abstract Interface：所有 RHI 对象以 I* 抽象接口暴露，Backend 后续实现同一 contract。
  • Factory Method：IRHIDevice 作为创建入口，返回 TRHIObjectResult<T>。
  • Value Object：F*Desc 是可复制、可查询、可测试的描述对象。
  • Mock Object：测试内 mock 验证 contract，不污染生产层。

2. 工程原则与方法论

  • Spec-driven development：从 clarified spec 到 plan、tasks，再到实现与交付文档。
  • Layer isolation：RHI public headers 不依赖 Backend、Renderer、Application 或平台窗口系统。
  • Contract testing：每个 public contract 都有成功路径和负路径，形成后续 backend 的回归基线。
  • YAGNI：不提前实现 shader compiler、真实 GPU allocation、multi-subpass graph 或 ray tracing pipeline。

3. 测试策略与质量保障

测试覆盖 boundary values、invalid combinations、unsupported capability、missing dependency、wrong descriptor type、array out-of-bounds、Invalidated lifecycle 和完整 smoke flow。它们共同保证 008 是可执行的 contract，而不只是头文件声明。

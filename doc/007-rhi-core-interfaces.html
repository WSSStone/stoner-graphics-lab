2. 本期核心摘要

交付第一批 RHI 合约：device lifecycle、capabilities、command buffer、queue、fence/semaphore、headless swapchain、result/status 和 format identities。它先用 mock 测试锁定行为，不绑定任何真实图形 API。

最值得学习的是 RHI 的定位：RHI 不是 Vulkan 的薄 wrapper，而是 Renderer 与多个 backend 的契约层。显式 result、lifecycle matrix 和 mock-first 测试让后续 Vulkan/DX/Metal 可以各自实现同一语义。

3. 上下文与依赖

  • 前置依赖：Core platform/types/logging abstractions
  • 后续铺路：RHI resources/pipelines, Vulkan backend device, command submission, Renderer layer
  • 层级边界：RHI 只向下依赖已稳定 contract，不能反向 include 更高层模块。
  • 编译期依赖：公共头和 SCons 目标；概念依赖：spec/plan/tasks 中定义的 lifecycle、result、diagnostic 与测试替身。

二、目标与边界

1. 业务与功能目标

  • Renderer 或测试替身能查询设备能力。
  • 命令缓冲可建模 recording/executable/submitted 状态。
  • queue submit 能表达成功、错误状态和同步对象协作。
  • swapchain contract 可表达 headless/mock 行为。

2. 架构目标与定位

Application / Tests
    ↓ 使用 public contract
RHI feature: RHI Core Interfaces
    ↓ 依赖稳定下层能力
Core vocabulary / diagnostics / platform
    ↓ 按阶段连接
RHI contracts / Backend implementations / Renderer systems

本阶段的 public contract 是调用方可以依赖的最小稳定面；private implementation、测试替身和 backend-specific helper 都不能反向污染上层 API。

3. 边界与非目标（约束）

  • 不创建 buffer/texture/shader/pipeline，这些属于 008。
  • 不引入 Vulkan/Metal/DX headers，保持纯接口。
  • 不承诺真实 GPU execution，只定义可测试 contract。

三、交互与产品设计

1. 用户使用路径

Renderer/RHI client 持有 IRHIDevice -> 查询 capabilities -> 创建或取得 command queue/buffer -> Begin/End recording -> Submit -> fence/semaphore/swapchain contract 参与同步或呈现。mock tests 覆盖生命周期和负路径。

学习时建议把这一段当成“最小工作流”：先找到输入对象，再跟踪它如何变成状态、诊断、测试断言或 debug dump。

2. 核心规则与状态机

未创建/空状态
    -> 描述或 Begin/Declare/Create
    -> 可验证中间状态
    -> Success: 可查询、可绑定、可执行或可复用
    -> Reset/Shutdown/Invalidated
    -> 任何后续使用必须返回错误结果或诊断

这个状态机是本项目底层模块的共同风格：显式创建、显式验证、显式失效。不同 feature 的状态名不同，但测试都围绕“合法转换”和“非法转换可观察”展开。

3. 失败模式与调试入口

  • 未 Begin 就 End、未 End 就 Submit 必须返回错误，否则 backend 会收到非法命令状态。
  • queue type 不兼容必须被拒绝，否则 compute/transfer/graphics 能力边界失真。
  • headless swapchain 必须有定义行为，否则 CI 无 GPU/窗口环境无法测试。

调试入口优先看 Tests/RHICoreTests.cpp 中的负路径用例，再看对应 diagnostics、result code 或 debug dump 输出；这些测试比源码更快暴露设计意图。

四、技术架构与关键决策

1. 技术栈与基础设施

  • C++20，传统 header/source 分离；公共 API 遵守项目 UE-style 命名。
  • SCons 4.10.1 构建；验证入口保持在单一 StonerTest 可执行文件。
  • Core/RHI/Renderer public contract 尽量不泄漏 backend 或平台实现细节。
  • headless、fallback 和 mock 测试优先保证无 GPU/无窗口环境仍能验证语义。

3. 架构决策记录 (ADR)

(1) 接口先于 backend

背景：需要先稳定 Renderer 可依赖的语义。

理由：mock tests 能在没有 GPU 的环境覆盖大部分契约。

被否决方案：直接先写 Vulkan：容易把 Vulkan 细节固化进 RHI。

后果：真实 backend 接入时需要适配已有 result/lifecycle。

(2) 显式 ERHIResult 而不是异常

背景：渲染运行时错误常见且需要被调用方处理。

理由：结果码与诊断更适合跨 DLL/跨平台。

被否决方案：异常：简化代码但不符合后续 GPU API 风格。

后果：调用方需要检查返回值。

五、实施与验证（任务流）

1. 任务拆解清单

  • Setup/Foundation：建立公共头、private source、测试入口和 SCons 发现路径。
  • Contract/API：定义描述结构、接口、枚举、状态和 result/diagnostic 语义。
  • Core implementation：实现状态机、验证逻辑、数据结构和 deterministic formatting。
  • Integration：把本阶段能力接入已有 Core/RHI/Backend/Renderer 边界。
  • Diagnostics/debug tooling：补齐负路径记录、dump、fallback marker 或测试可观察输出。
  • Tests and validation：覆盖 happy path、failure path、lifecycle、compatibility 和 boundary isolation。
  • Documentation/roadmap update：更新 quickstart、roadmap 和本总结文档。

2. 验收标准

  • 构建命令可完成：scons。
  • 测试命令可完成并覆盖本 feature 对应测试文件：Tests/RHICoreTests.cpp。
  • 关键成功场景和关键失败场景都有测试，而不是只验证能编译。
  • 公共头不 include 不该依赖的高层或 backend/API 头。
  • deterministic 输出在重复运行中保持稳定，便于 regression diff。

六、设计巧思与最佳实践

1. 当前业务场景与业务模型的最佳实践

(1) RHI

是什么：Renderer 和具体图形 API 之间的稳定协议。

项目表达：IRHI* public headers 只表达能力和生命周期。

真实引擎/API 对应：UE RHI、bgfx、Dawn/WebGPU 都是类似抽象层。

(2) Lifecycle matrix

是什么：对象状态决定哪些操作合法。

项目表达：command buffer/queue/sync tests 覆盖负路径。

真实引擎/API 对应：Vulkan/DX12 都强依赖显式状态，隐式容错会掩盖 bug。

(3) Mock-first contract

是什么：先证明接口语义，不依赖硬件。

项目表达：Tests/RHICoreTests.cpp 用替身验证 Renderer-facing flow。

真实引擎/API 对应：真实引擎 CI 通常也需要 null/mock/headless backend。

2. 优化方案与收益

本阶段的优化重点不是追求最终性能，而是建立可替换的语义基线：先让行为被测试锁住，再在未来引入 SIMD、真实 Vulkan runtime、更复杂 allocator、pipeline disk cache、render graph aliasing 或 async compute。

这种做法的收益是 migration cost 可控：只要 public contract 和测试矩阵稳定，private implementation 可以逐步从 mock/fallback 演进到真实 GPU 路径。

七、编程语言知识点

1. 标准库接口与用法

本项目优先使用标准库可移植能力，例如容器、智能指针、字符串、chrono、filesystem、mutex 和 algorithm。关键不是“用了哪个库”，而是把标准库行为包装进项目自己的 contract，减少跨模块直接耦合。

2. 语言特性与惯用法

  • RAII/ownership：资源对象在 shutdown/invalidate 时显式失效，避免悬空后继续成功。
  • enum class：用强类型枚举表达 result、queue、usage、stage、state，避免整数误传。
  • 值语义和移动语义：desc、handle、record 适合轻量复制；拥有对象则通过指针或明确 lifecycle 管理。
  • 宏只用于日志/断言等需要调用点上下文的场景，其余优先函数和类型系统。

3. 平台相关与编译器行为

平台相关代码应留在 Core platform 或 Backend private 边界内。公共头尽量避免平台宏分叉和图形 API 头泄漏，这样 Windows/macOS/Linux 与未来 Vulkan/DX/Metal/OpenGL backend 才能共享上层代码。

八、软件工程知识点

1. 设计模式与架构模式

  • Layered Architecture：Core -> RHI -> Backend/Renderer 的依赖方向必须单向。
  • Facade/Aggregate Header：CoreMinimal、RHIMinimal 或 RendererMinimal 提供便利入口，但不能隐藏边界污染。
  • Builder/Compiler/Executor：复杂声明式系统先收集意图，再编译计划，最后执行。
  • Adapter：Backend/Vulkan 把具体 API 对象适配成 RHI contract。

2. 工程原则与方法论

  • Contract-first：先定义 public behavior，再实现 backend 或优化。
  • Fail fast but diagnosable：错误尽早返回，同时留下能解释原因的记录。
  • Determinism：排序、dump、fallback 和测试输出都尽量稳定。
  • YAGNI with escape hatch：推迟工业级复杂能力，但保留未来接入点。

3. 测试策略与质量保障

测试不是只证明“代码能跑”，而是把工程假设固化下来：合法路径、非法路径、边界隔离、重复运行稳定性和 fallback/headless 环境都应该被覆盖。对图形工程而言，mock 与 fallback 不是偷懒，而是让 CI 可以在没有真实 GPU 的情况下守住 contract。

2. 跨 API 映射

API本阶段概念如何映射
VulkanIRHICommandBuffer 对应 VkCommandBuffer；queue/fence/semaphore 对应 VkQueue/VkFence/VkSemaphore。
DX12命令列表/命令队列/fence 分别映射到 ID3D12GraphicsCommandList/CommandQueue/Fence。
MetalMTLCommandBuffer 与 MTLCommandQueue 语义更高层，但仍可适配 RHI contract。
OpenGL传统 GL 隐式状态多，RHI 需要模拟 command buffer 语义或限制能力。

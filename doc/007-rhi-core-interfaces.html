2. 本期核心摘要

本阶段定义第一层真正的 RHI 合约：设备生命周期与能力查询、队列分类、命令缓冲录制与提交、Fence/Semaphore 同步、headless/mock swapchain、格式枚举和显式结果码。实现策略是 interface-first、mock-test-driven，确保 Renderer 和 Backend 能在没有真实 GPU/窗口/图形 API 的情况下先对齐工作流。

二、目标与边界

1. 业务与功能目标

US1 — 统一查询渲染设备能力 P1 MVP

通过 IRHIDevice 获取生命周期状态、能力快照、queue 支持和 device-owned 对象创建结果。

US2 — 录制并提交核心 RHI 工作流 P1

命令缓冲可录制 symbolic draw/dispatch/barrier，完成后提交到兼容队列，并通过显式状态观测完成。

US3 — 使用同步原语协调工作 P2

Fence 表达 CPU/GPU 完成观察，Semaphore 表达队列间顺序，不暴露任何 backend-specific handle。

US4 — 通过 Swapchain 合约表达呈现 P2

headless/mock swapchain 覆盖 acquire、present、resize-required、unavailable 与 invalid-state。

2. 架构目标与定位

RHI Core 位于 Renderer 与具体 Backend 之间，负责定义可被 Vulkan、Metal、DX12、OpenGL/GLES/WebGL 和测试 mock 共同实现的最小渲染硬件接口。

三、交互与产品设计

1. 用户使用路径

IRHIDevice
  -> GetCapabilities()
  -> CreateCommandQueue(Graphics)
  -> CreateCommandBuffer(Graphics)
  -> Begin() / RecordDraw() / RecordDispatch() / RecordBarrier() / End()
  -> Submit(command buffer, wait semaphores, signal semaphores, fence)
  -> WaitIdle() / Fence.Wait()
  -> Swapchain.AcquireNextFrame() / Present()

2. 核心规则与状态机

对象状态/规则
IRHIDeviceUninitialized -> Active -> Shutdown；shutdown 后创建对象返回 InvalidState。
IRHICommandBufferIdle -> Recording -> Completed -> Submitted -> Resettable；double begin、end without begin、record after end 均失败。
IRHICommandQueue只接受兼容 queue type 且已 completed 的 command buffer。
IRHIFenceUnsignaled -> Signaled -> Waited；未 signal 时 wait 可返回 NotReady/Timeout。
IRHISemaphoreUnsignaled -> Signaled -> Consumed；用于 submit 依赖，不暴露 backend handle。
IRHISwapchainReady -> Acquired -> Ready，也可进入 ResizeRequired 或 Unavailable。

四、技术架构与关键决策

1. 技术栈与基础设施

  • C++20 纯接口头与 UE5-style 命名：I* interface、F* struct、E* enum。
  • 公共 RHI 头位于 Source/RHI/Public/RHI/。
  • mock 实现位于 Tests/RHICoreTests.cpp，不污染生产 Backend 层。

3. 架构决策记录（ADR）

ADR-007-01：先定义接口，不引入假 Backend

生产代码只增加公共 RHI 合约，mock 行为放在测试里。这样不会把测试替身误当作引擎后端实现，也让真实 Vulkan/Metal/DX12 后端可以独立实现同一接口。

ADR-007-02：所有可恢复失败使用 ERHIResult

生命周期错误、unsupported queue、timeout、resize required、unavailable 等都通过显式状态表达，测试可以稳定断言，不依赖异常或 debug-only assertion。

ADR-007-03：命令 payload 保持 symbolic

本阶段记录 draw/dispatch/barrier 的意图和顺序，不验证具体资源、pipeline 或 shader。这样先固定工作流，避免资源系统还没设计时提前制造错误耦合。

六、设计巧思与最佳实践

6.1 当前业务场景与业务模型的最佳实践

RHI 是 Renderer 和 Backend 的共同语言。这个阶段没有急着写 Vulkan 或真实资源对象，而是先让“设备、队列、命令、同步、呈现”这些概念形成可测试的合同。后续 Backend 只需要证明自己满足合同，Renderer 则可以先面向接口开发。

6.2 优化方案与收益

  • device-owned creation 统一对象生命周期，避免调用者绕过设备能力创建不支持的对象。
  • explicit result/status 让负路径成为一等公民，后续 backend 可以直接映射 API 返回码。
  • mock swapchain 让呈现工作流提前可测，又不绑定窗口和 surface。
  • symbolic commands 降低 MVP 复杂度，同时保留未来资源/pipeline 扩展位置。

七、编程语言知识点

1. 标准库接口与用法

本阶段生产 RHI 头几乎不直接依赖复杂标准库，主要通过已有 Core 容器和智能指针表达对象关系：TSharedPtr 用于 device factory 返回对象，TArray 用于 semaphore 列表和 format 支持集。

2. 语言特性与惯用法

  • 纯虚接口和虚析构函数定义 backend/mock 可替换边界。
  • enum class 表达强类型状态、结果、queue type 和 format。
  • 模板结果包装 TRHIObjectResult<T> 同时返回状态和值，避免 null 指针语义不清。
  • [[nodiscard]] 和 noexcept 用于查询函数，强调状态结果不可随意忽略。

3. 平台相关与编译器行为

RHI 公共接口本身不包含平台分支，也不包含图形 API 头。跨平台差异会在未来 Backend 实现中处理，当前合同保持 Windows/macOS/Linux 共同可实现。

八、软件工程知识点

1. 设计模式与架构模式

本阶段体现 Interface Segregation 和 Abstract Factory：IRHIDevice 是对象创建入口，但 queue、command buffer、fence、semaphore、swapchain 的职责彼此独立。mock tests 是 contract test，而不是生产架构的一部分。

2. 工程原则与方法论

  • Spec-driven development：clarification、plan、tasks 到实现逐步收敛。
  • 依赖倒置：Renderer 依赖 RHI contract，Backend 实现 RHI contract。
  • 最小可行接口：只固定当前 roadmap 需要的核心 RHI 概念。
  • 可测试设计：每个生命周期状态和负路径都能由 mock 明确触发。

3. 测试策略与质量保障

测试采用 lifecycle matrix、negative-path validation 和 renderer-facing smoke flow 三层组合。矩阵测试覆盖状态转换，负路径测试覆盖非法操作，smoke flow 则证明 device、queue、command buffer、sync、swapchain 能按未来渲染帧流程协作。

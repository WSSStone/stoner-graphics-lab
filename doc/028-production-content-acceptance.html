028 - Asset Production Content Integration & Acceptance

版本 1.0 · 2026-08-23 · 主体实现完成 / final-revision closeout 进行中 · 分支 028-production-content-acceptance
工程结论：Feature 028 把“单元测试里能导入资产”提升为可审计的生产内容闭环：真实 GLB/glTF 和 KTX2 从 source 进入确定性 cook generation，经 source-unavailable strict manager 加载、Renderer 事务化 realization、Vulkan/Metal 原生 Deferred 与 Forward 执行，再由 attachment semantic probes、accepted baseline、CPU FLIP、1,000 次生命周期和 artifact digest 共同证明。Metal 上曾经 nonblank 但明显过暗的画面说明：生命周期门禁不能代替图像正确性门禁。

2. 本期核心摘要

工程交付上，本期引入了两级真实内容：仓库内有界 Lantern GLB 用于相关 PR 的 regular gate，hash-pinned 外部 Sponza 包用于 weekly/closeout medium gate。两个包都必须完成真实 Image/Texture/KTX2、Material/Shader、StaticMesh/StaticModel cook，生成 immutable generation；运行期卸载 source 后仍要从一个 generation 发布完整 typed closure，并把全部 primitive、material、texture 和 shader 事务化 realization 为 Renderer/RHI 对象。

学习价值上，Feature 028 最重要的是理解“渲染验收是一组互补 oracle”。nonblank 只能证明写过像素，attachment probe 能定位 GBuffer/lighting/composition 哪一层错，FLIP 能衡量感知差异，生命周期 counter 能证明 ownership 回到基线，semantic equivalence 能证明 source/cooked 含义一致。任何单一 oracle 都可能产生假绿。

3. 上下文与依赖

  • Features 020-024 提供 Asset identity、Image/Texture、Material/Shader 和 glTF 静态模型 CPU payload。
  • Feature 025 提供 DDC、manifest、generation publication 和 standalone validation；Feature 026 提供 development/strict manager、lease 与 typed request。
  • Features 019、022、023 提供 Deferred pipeline、KTX2 和 shader payload；Feature 027 提供独立 Metal backend 与 offline metallib。
  • FLIP 1.7 仅作为 test-side CPU single-header dependency；runtime 不链接 FLIP。cgltf、stb_image、KTX-Software、WAMR、yyjson、SPIRV-Cross 继续保持各自 private 边界。
  • Feature 029 可在这套真实内容、确定性 cook、严格生命周期与图像证据上继续做 Meshlet Derived Data，而不必重新发明 acceptance。

二、目标与边界

1. 业务与功能目标

  • 内容维护者能验证 package inventory、hash、root identity 和 source tree，没有隐式网络或 license-policy 判断。
  • cook owner 能对每个目标 profile 做 clean determinism、warm 100% eligible reuse、publication 和 consumer-side digest revalidation。
  • runtime/Renderer 能在 source 不可用时加载完整 closure，拒绝 wrong target、corrupt payload、missing dependency 和 partial realization。
  • 渲染维护者能查看 BaseColorAO、NormalRoughness、MaterialProperties、Depth、LightingAccumulation、FinalOutput 和 ForwardColor 的原始 GPU readback，并用 semantic probe + exact baseline + FLIP 判定。
  • CI owner 能用 regular、medium、hardware 三种 profile 表达 cadence、预算、capability owner 和 Unsupported replacement lane。

3. 边界与非目标（约束）

  • 不自动决定 license 合规：自动化只验证 bytes 与 metadata，法律判断需要明确的人类 owner。
  • 不把 Sponza bytes 提交到 Git：medium 内容较大且许可/存储策略独立，使用 revision + inventory hash 的外部 staging。
  • 不做 source fallback：strict acceptance 必须在 source 已撤销后通过，否则无法证明 shipping 路径。
  • 不自动接受 Candidate baseline：校准可以生成候选，只有用户明确接受后才能成为 Accepted。
  • 不在本期加入抗锯齿或通用后处理：Feature 028 冻结 sampleCount=1 的正确几何、相机和光照输出；后续图像管线 feature 必须升级 workload revision 并重新校准。
  • 不做 streaming、residency、archive/package、LOD/Meshlet、virtual geometry 或 ray tracing：这些会改变 ownership 与可见结果，分别留给后续 feature。
  • 不要求不同 API 的原始浮点字节完全相同：先统一图像方向、row pitch、transfer 和格式，再比较语义与感知差异。

三、交互与产品设计

1. 用户使用路径

python3 .github/scripts/run_production_content_validation.py \
  --profile medium \
  --target-profile Config/AssetCooker/Profiles/Production/Mac-Metal-Arm64.json \
  --build-root Build/Mac/Release \
  --output Build/Validation/028/medium-metal \
  --timeout-seconds 1800
  1. 按 corpus manifest 验证文件集合、大小和 SHA-256；medium 缺包时只能走显式 pinned acquisition。
  2. 将 package 与仓库 shader 复制到隔离 source roots，做 clean cooks 与 unchanged warm cook。
  3. standalone validation 通过后运行 development-versus-cooked semantic equivalence，再删除复制的 source roots。
  4. strict manager bind generation、批量 request 全部 manifest records、发布 typed closure；resolver/importer/source decoder counters 必须为零。
  5. Renderer 在事务中创建 mesh buffers、KTX2 textures、descriptors 和 pipelines；任一失败则 reverse-order rollback，不发布 partial snapshot。
  6. 每轮执行 Deferred full 与 Forward smoke，submit/fence 后读取 attachment；释放 session、snapshot 和 RHI resource，再采 ownership/RSS。

1.1 校准相机路径

--production-camera-preview 只允许 interactive、visible、strict-cooked production-content 模式。右键拖动观察方向，W/S/A/D/Q/E 移动，Shift 加速，滚轮调 FOV，R 恢复 revision preset，Enter 输出规范 View/Projection JSON，Escape 退出。正式 gate 不读取输入或调用方矩阵，只按 workload revision 选择代码内冻结矩阵；Sponza 正式视角为 production-content-sponza-v2 中庭纵深构图。

2. 核心规则与状态机

Corpus:      Unverified -> Verified -> Staged
Cook:        Source -> DDC entries -> Generation -> Current pointer
Session:     Empty -> Bound -> Requests pending -> Closure published -> Shutdown
Realization: Validate -> Create transaction -> Commit snapshot
                                  `-> Failure -> Rollback
Baseline:    Candidate -> Calibrated -> Reviewed -> Accepted -> Superseded
Gate:        Started -> Passed | Failed | Unsupported | Timeout

regular 固定 20 次、1-2 warm-up；medium/hardware 固定 1,000 次、1-20 warm-up。warm-up 计入总次数，内部 owners 必须归零且 stale handle 必须被拒绝。GitHub-hosted RSS、task-VM、allocator 与耗时只作为 observation；Feature 028 的维护者本机 native arm64 Metal 与手动同步的 x86_64 Windows Vulkan 分别通过 exact host/target/device class、独占进程锁、clean committed revision、默认 allocator、声明采样协议和窗口 readback preflight 后，裁决各自的 accepted-image gate，且二者必须在同一最终 revision 上通过。Metal 继续裁决 warm-up 到 terminal 的 16 MiB RSS；Windows working-set RSS 因同路径多次运行受驱动驻留和 OS trimming 影响而只作为完整有界 observation，不得单独判失败，也不得通过 working-set trim、特殊 allocator、移动采样点或抬高阈值制造通过。regular 的 operational cap 为 600 秒；hosted medium 每包/native 为 5,400/4,800 秒并置于 120 分钟 job；每个本地 hardware target 保持 3,600 秒串行预算。设备不需要注册 self-hosted runner，push 不会远程执行；macOS Vulkan 与稳定 Windows reference-set/WPR 内存资格仍延期到未来 hardware lab。

四、技术架构与关键决策

1. 技术栈与基础设施

主体使用 C++20，Metal private implementation 使用 Objective-C++20/ARC，自动化使用 Python 3 标准库，构建系统为 SCons 4.10.1。Vulkan lane 使用真实 Vulkan/MoltenVK/Lavapipe capability；Metal lane 使用 macOS native Metal 和 offline MSL 2.4 metallib。CPU FLIP 固定为 NVIDIA FLIP 1.7 commit b475eb4b...，只编入测试。

2.2 数据流、控制流与资源流

verified source bytes
  -> importer values + complete dependency graph
  -> target-specific cook (KTX2 / SPIR-V or metallib / mesh / material)
  -> digest-addressed DDC entries
  -> immutable generation + atomic Current.json
  -> full standalone validation and semantic equivalence
  -> source roots revoked
  -> strict typed requests + closure
  -> transactional Renderer snapshot
  -> Deferred + Forward RHI command records
  -> Vulkan/Metal submit + fence + raw readback
  -> semantic probes + accepted baseline + FLIP
  -> release + counters + RSS + artifact manifest

session 的前置 generation 检查使用 IndexAndLayout，因为 strict loader 随后会对每个被请求 payload 验证文件大小、body digest、envelope digest、AssetId/type/codec/schema，并完成 typed decode。这样每轮仍覆盖全 manifest，却避免在 manager load 前把全部 payload 重复解码一次。

2.3 日志、诊断与可视化

  • deterministic report 只含 identity、digest、generation、结果和稳定 first failure；host path、PID、native pointer、credential 不得进入。
  • timing、RSS、device class、FLIP 和 image observation 明确属于 observational fields，不参与 correctness digest。
  • native integration 输出 [EVIDENCE] 行，含 cycles、warm-up RSS、terminal/peak/growth、captures、readbacks、counters 和 stale。
  • image failure 先输出 probe 名称与 attachment，再输出 FLIP mean/p95/max/bad fraction；避免只给“截图不同”。

3. 架构决策记录（ADR）

(1) 真实内容分为 checked-in regular 与 staged medium

决策：Lantern 有界入库，Sponza 用 revision + file inventory hash 外部 staging。理由：PR 需要离线、快速、可复现，medium 需要更大 primitive/material/texture 规模。否决方案：把 Sponza 全量入库会扩大仓库和许可治理面；只用 Lantern 又无法暴露 103 primitive、69 texture 的规模问题。后果：medium runner 必须显式处理 acquisition failure 和 cache integrity。

(2) baseline 必须 exact device class 且由人明确接受

决策：registry 由 backend implementation、CPU architecture、adapter family、shader profile、color/depth format、sample count 和 texture family 构造 canonical signature，精确匹配一个 class；只有 Accepted baseline 可运行。否决方案：nearest-device fallback 会把真实硬件差异隐藏为容差。后果：新增硬件要先校准和评审，但不会静默借用错误参考图。

(3) semantic probe 优先于 FLIP

决策：coverage、orientation、primitive/material region、base color、normal、metal/roughness、emissive、depth 和 current-frame token 先过，FLIP 后过。理由：感知指标可以容忍局部差异，却不能解释 attachment 读错或整帧 stale。否决方案：只比较最终图曾让旧门禁 nonblank 假绿。后果：失败更可定位，baseline threshold 也不能掩盖结构错误。

(4) 一个 snapshot 共享 Deferred 与 Forward realization

决策：同一 immutable aggregate snapshot 被两条 render path 共享。理由：几何和纹理 ownership 相同，重复 realization 曾把 Sponza 20-cycle RSS 推高到 30 MiB 以上。否决方案：分别创建两套 snapshot 简单但制造无意义的 GPU 内存和销毁压力。后果：两条 path 必须保持只读 contract，未来若需要不同资源需显式拆分。

(5) 批量 request、profile-bound worker 与 package 调度

决策：先提交全部 manifest request，再按稳定顺序完成；arm64 Metal regular 用一个 worker、其余 regular 用四个 workers，medium/hardware 用八个 workers；medium 最多并发两个拥有独立 source/DDC/publication/lease/report roots 的 package，hardware 串行。理由：四 worker 的 regular 在 hosted arm64 仍出现 24 MiB allocator 驻留波动；全平台一 worker 又使 Linux Lavapipe 在 cycle 2 后延迟分配并让 Intel Metal 超出 600 秒预算；顺序 medium 则在 Linux 和 clean macOS workspace 用尽 1,800 秒。包级并发把 Lantern 与较长的 Sponza 重叠，同时不改变任何单包 cycle/RSS/strict contract。否决方案：提高到 16 workers 没有缩短 Sponza 且增加 RSS；并发 hardware 会争用窗口和 capture device。后果：worker count 与 package concurrency 都成为显式、受限的 target/profile contract。

(6) Vulkan-to-Metal vertex Y 语义在 derivation 中处理

决策：SPIRV-Cross common options 启用 vertex.flip_vert_y，identity 增加 flip-vertex-y=1，Metal producer version 升级以隔离旧 DDC/metallib。理由：surface 和 fullscreen pass 坐标错位会在两次错误后伪装出正确轮廓，却让 deferred lighting 采错 GBuffer。否决方案：在每个 shader 手工修正会污染 GLSL authority 并遗漏 pass。后果：derivation policy 变化必须进入 cook identity。

(7) 校准自由相机与正式冻结矩阵分离

决策：preview 可交互移动并输出 View/Projection 候选，正式 gate 只能查 revision-owned preset。理由：每个 draw 的 Model 不同，单一 MVP 不能作为相机 authority；调用方覆盖又会破坏 CI 确定性。后果：视角变化必须升级 workload revision、更新 semantic regions 并重新接受 baseline。

(8) Vulkan resource tracking 不拥有 client resource

决策：device 用会自动修剪的 weak references 跟踪 fences、resources、render objects、shaders 和 pipelines；shutdown 仍锁定并 invalidates 尚存对象。理由：强 tracking 让 native counters 已归零的 C++ wrapper、shader bytes、pipeline description 和 cache key 仍可达，导致 1,000-cycle RSS 与查找成本线性增长。否决方案：每 cycle 强制 pressure relief 无法释放可达对象；重建设备会逃避 persistent-device lifecycle。后果：最后一个 snapshot owner 释放即真正结束 RHI ownership。

六、设计巧思与最佳实践

1. 当前业务场景的最佳实践

  • 证据链而非单一截图：source digest、generation、target、GPU readback、baseline 和 lifecycle 都能互相追溯。
  • fail closed：missing baseline、ambiguous device class、Unsupported backend、timeout 和 source fallback 都不能聚合为 success。
  • 事务化 publication：cook generation 用原子 Current pointer；Renderer snapshot 只在全部 RHI object 成功后 commit。
  • 稳定 identity 与 observation 分离：时间/RSS/设备观察可以变化，不应污染 deterministic correctness digest。
  • 负例是 contract 的一部分：至少 30 类 first failure 让 CI 失败可以复现，而不是只给非零退出码。

2. 优化方案与收益

  • macOS SHA-256 使用平台 CommonCrypto，在不改变 FAssetDigest public contract 的前提下降低大 payload hash 成本。
  • strict loader 复用 parser 已计算的 envelope digest，避免同一 bytes 重复 SHA；body 与 envelope 两层校验仍保留。
  • 批量提交 189 个 Sponza request，把顺序 sleep 转成受限并行；20-cycle 从约 84 秒降至约 27 秒。
  • Deferred/Forward 共享 snapshot，使 Sponza GPU ownership 回归有界，并让校准后的 Metal RSS 保持在 16 MiB 门禁内。
  • 未来可研究 decoded-body buffer ownership、GPU resource pooling 和更细粒度 lifecycle benchmark，但不能跨 cycle 保留本应释放的验收对象。

3. 已知限制与后续演进

  • 外部 medium acquisition 依赖网络/cache 可用性；Unavailable 必须由 replacement lane 承担。
  • baseline 只覆盖已接受的确切 device class；新 GPU/driver family 需要单独校准。
  • 当前正式输出为单采样且没有通用后处理；抗锯齿/后处理属于后续 roadmap，不能在不升级 revision 和重跑图像验收时静默加入。
  • 当前一次性加载完整 closure，不代表已有 streaming/residency；Feature 029+ 若改变资源粒度必须保留本期 semantic/image/lifecycle 回归。

2. 语言特性与惯用法

  • RAII：manager lease、registration token、RHI transaction 和 Objective-C++ owner 在所有失败路径释放。
  • 移动语义：typed payload、readback 和 closure 在 publication 时 move，避免复制大 KTX2/mesh 数据。
  • enum class：result、stage、baseline status、profile 和 validation policy 不发生隐式整数混用。
  • [[nodiscard]]：创建、validate、load、shutdown result 不能被无意忽略；有意忽略时显式 (void)。
  • Result + out value：跨层不用异常传播业务失败，保证 partial output 在失败时为空。
  • 条件编译：CommonCrypto 和 Metal 只在 macOS private implementation 生效，公共 digest/RHI contract 跨平台不变。

3. 平台相关与编译器行为

macOS 使用 CommonCrypto 加速 SHA 和 Metal offline toolchain；Windows/Linux 使用 portable SHA fallback，Linux native lane可用 Lavapipe。MSL derivation 可在非 macOS Tools build 测试，但 metallib finalization 只能在 macOS。strict build 的 -Werror 还暴露了 aggregate initializer 新字段缺失，因此新增 DependencyResolver 时所有 request initializer 都必须同步。设备 class signature 明确允许 CPU architecture 中的下划线，例如 x86_64。

八、软件工程知识点

1. 设计模式与架构模式

  • Strategy：Asset Manager 在 development source 与 strict cooked loading strategy 间切换；acceptance 比较两者语义。
  • Builder：composition、Deferred execution 和 report builder 先验证完整输入，再发布值。
  • Transaction：generation publication 与 Renderer realization 都采用 commit/rollback，避免 partial state。
  • Value Object：AssetId、digest、target evidence、device signature、baseline key 都可比较、可序列化、无 native pointer。
  • Adapter：Renderer 把 CPU Asset snapshot 适配到 RHI；Vulkan/Metal 再把 RHI intent 映射到各自 API。
  • Contract Test：同一 production workload 在 mock、Vulkan、Metal、regular、medium 与 hardware lane 上复用不变量。

2. 工程原则与方法论

  • 分层与依赖倒置：Asset 不知道 GPU，Backend 不知道 Asset；Renderer 是唯一桥梁。
  • 契约式设计：cycles/warm-up/budget、target、baseline status 和 first failure 均是 schema/代码双重约束。
  • 防御性编程：所有 path、count、bytes、depth、deadline、artifact 数量都有上界。
  • 确定性优先：identity-bearing report 与 observational evidence 分开，重复 cook 可 byte-compare。
  • YAGNI：没有借真实内容之机加入 editor、hot reload、streaming 或新渲染效果。
  • 可测试设计：capability unavailable 有 Unsupported 结果，CI 不必伪造 native success。

3. 测试策略与质量保障

单元测试负责 schema、codec、failure catalog 和 deterministic report；contract test 负责 development/strict semantic equivalence；mock RHI 负责 transaction rollback；native offscreen 证明真实 API submit/readback；visible hardware 证明窗口 present 和 reference image；1000-cycle 证明长期 ownership/RSS。架构扫描与 privacy scan 则覆盖“代码能跑但边界已腐化”的风险。不同层互补，不能用大量 mock 测试替代一次真实 GPU，也不能用一张截图替代 failure/lifecycle 矩阵。

九、渲染、引擎与图形 API 学习笔记

1. 本期核心概念拆解

(1) Deferred attachment 是调试接口

GBuffer 不只是中间纹理，也是定位几何、材质、坐标和 lighting 错误的分层证据。BaseColor 正常而 Lighting 过暗，说明问题更可能在 normal/depth reconstruction、fullscreen sampling 或 light math，而不是 texture import。真实引擎常有 RenderDoc capture；本项目用 bounded readback 与 semantic probes 建立自动化等价物。

(2) Framebuffer 坐标语义不是“把 UV 翻一下”

Vulkan clip/framebuffer 与 Metal 的坐标约定必须在 shader derivation policy 中一致处理。surface pass 和 fullscreen pass 若分别以错误方向写/读，最终轮廓可能偶然抵消，但 GBuffer 像素含义已经错位。常见误区是只看最终 silhouette，不检查 world normal、depth 和 lighting attachment。

(3) KTX2 artifact 与 GPU texture 不是同一层

KTX2 是 immutable CPU cooked artifact，包含 mip、semantic、color space 和 compressed bytes；Renderer 根据真实 RHI capability 选择 target/transcode 并创建 GPU texture。Asset 不应持有 VkImage/MTLTexture，RHI 也不应理解 glTF URI。

(4) 感知指标不是结构正确性的替代

FLIP 模拟人眼对亮度、颜色和空间差异的敏感度，适合跨 GPU/API 的最终图比较；但它不知道“这个像素是否来自当前 frame”或“normal attachment 是否方向正确”。因此本期规定 semantic probe 先于 FLIP。

(5) GPU correctness 与 ownership correctness 同等重要

一帧正确不代表反复 recreate 安全。每轮完整 load-realize-render-release 后，Asset、Renderer、RHI、native 和 presentation owner 都要回到 runtime baseline；否则 1,000 次后可能 OOM 或 stale-handle alias。

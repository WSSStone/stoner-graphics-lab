2. 本期核心摘要

Feature 026 把 Features 020-025 的“可识别、可导入、可 cook、可发布”资产，变成运行时可请求的 CPU 资产。调用方通过同一个 FAssetManager 异步请求 typed Asset；开发模式从 source resolver/importer 加载，strict cooked 模式只读取已验证且绑定的 generation。两条路径共享 AssetId、依赖关系和 typed payload contract。

最值得学习的工程主题是身份、物理工作、调用者兴趣与对象生命周期的分离。等价请求可共享一次物理加载，但取消仍属于单个调用者；缓存不拥有永久 grace period，最后一个外部 handle、request interest 和 dependency retention 释放后立即卸载；worker 只产生结果，用户 callback 必须由显式 completion pump 在调用线程确定性分发。

3. 上下文与依赖

  • Feature 020 提供 FAssetId、registry、resolver/importer/loader 与 extension registry。
  • Features 021-024 提供 Image/Texture、KTX2、Material/Shader、StaticMesh/Model typed payload。
  • Feature 025 提供 immutable cooked generation、manifest、payload envelope、publication validator 与原子 Current.json。
  • Feature 026 只依赖 Asset 与 Core；它不链接 Tools/AssetCooker，也不拥有 RHI/GPU 对象。
  • 后续 Meshlet、backend shader payload、Streaming/Residency 可以消费 typed handles 和依赖调度，但不得把 manager 变成 GPU residency 系统。

二、目标与边界

1. 业务与功能目标

Renderer、Application 或未来 runtime subsystem 可提交 typed Asset request，轮询其状态，取得 immutable TAssetHandle<T>，并在指定线程 pump completion callback。错误由稳定的 EAssetResult、terminal snapshot、依赖失败路径和 bounded inspection 表达，不通过异常或半成品 handle 暴露。

2. 架构目标与定位

→

→

RHI realization + GPU residency

Public contract 包括 manager config、request handle、typed handle、execution context 和 inspection snapshot；worker executor、request/operation table、scheduler、cache、loading strategy、completion queue 与 generation binding 都是 private implementation。具体 Vulkan、Metal、DX12 或图形格式选择不进入本阶段。

3. 边界与非目标（约束）

  • 不做 offline cook 或 pruning：它们属于 Tools/维护流程；runtime 只持 reader lease。
  • 不做 streaming、budget eviction 或 chunk scheduling：这些需要独立的 Feature 030 策略和 GPU/CPU budget 模型。
  • 不做 GPU residency：Asset 不能依赖 RHI；Renderer 才能把 CPU payload realization 为 GPU resource。
  • 不做 hot reload：开发模式在一次加载开始时 pin source/version；变化会失败且不自动重试，释放后新请求才读取新版本。
  • 不做网络或远程缓存：当前 generation、coordination root 和 payload 都是本机文件系统 contract。

三、交互与产品设计

1. 用户使用路径

FAssetManager Manager(Config);
FAssetRequestHandle Request = Manager.Request<FTextureAsset>(TextureId);

while (!Manager.Query(Request).IsTerminal()) {
    Manager.PumpCompletions();
}

TAssetHandle<FTextureAsset> Texture = Manager.GetResult<FTextureAsset>(Request);
Manager.ReleaseRequest(Request); // Texture 仍独立保持 immutable payload

strict cooked 启动时，manager 先读取并验证 current pointer、绑定 exact generation、取得 shared reader lease，再允许 admission。若 manifest、envelope、codec、extension、type 或 dependency closure 不匹配，请求 fail closed，且不会退回 source importer。

2. 核心规则与状态机

Accepted
  -> WaitingForDependencies
  -> Loading
  -> Succeeded | Failed | Cancelled

Shutdown: reject new admission -> signal cooperative cancellation
          -> join conforming work -> terminal audit -> release manager ownership
  • slot index 加 generation 防止旧 request handle 误指向复用后的新请求。
  • complete load key 决定能否 coalesce；AssetId 相同但 expected type、mode、target 或 bound generation 不同，不能共享。
  • 一个 caller 取消只移除自己的 interest；共享 operation 与 dependency 仍被其他 root 需要时继续执行。
  • callback reservation 在 admission 时完成，避免物理加载成功后才发现 completion queue 已满。

四、技术架构与关键决策

1. 技术栈与基础设施

实现使用 C++20、传统 header/source 分离、项目 Core ownership 和 SCons 4.10.1。并发使用标准库 mutex、atomic、condition variable、thread、shared/weak ownership 与 monotonic deadline。跨进程 generation reader ownership 通过 Core 的 POSIX flock / Windows LockFileEx 封装，不向 Asset public header 暴露 native handle。

(2) 数据与控制流

  1. admission 校验 config、AssetId、expected type 与容量，并预留 completion。
  2. complete load key 查询 cache/operation table；等价请求加入 caller membership。
  3. scheduler 解析 required closure 与允许的 optional fallback，产生稳定 ready order。
  4. mode strategy 从 pinned source 或 bound generation 生成 immutable typed payload。
  5. operation 一次性 commit 到 cache；每个仍有 interest 的 caller 独立进入 terminal state。
  6. callback 按 sequence 入队；调用方 pump 时才在当前线程执行。
  7. 最后一个 external/request/dependency retention 释放后，cache entry 立即移除。

(3) 关键日志、诊断与可视化

FAssetManagerInspection 输出 bounded immutable request、operation、cache 与 generation snapshot。排序、截断与 redaction 都是确定性的；只记录规范 identity、状态、decision 和 result，不泄漏 native handle、绝对 coordination path 或 worker 地址。result code 负责机器决策，inspection 负责解释“为什么”。

3. 架构决策记录（ADR）

(1) 显式 completion pump

决策：worker 只入队，callback 仅由显式 pump 调用。原因：Renderer/Application 往往要求 main-thread affinity，worker 直接回调会制造随机重入与 teardown race。被否决的是 worker callback 和隐式专用 callback thread；前者不安全，后者引入额外生命周期与调度语义。

(2) 引用驱动的即时卸载

决策：三类 retention 归零即移除，不保留时间 grace cache。这样测试和运行时都能准确推导内存所有权。LRU/budget eviction 被推迟到 Streaming & Residency，因为它需要独立预算、优先级和 telemetry，而非偷偷改变本期 handle 语义。

(3) generation 级跨进程 reader lease

决策：publication root 保持只读，另设 writable coordination root，并以规范 publication namespace 取得 generation shared lease。操作系统在 crash 后释放所有权，未来 packaging/pruning 无需 PID 猜测。锁住整个 Current.json 被否决，因为旧 generation reader 不应阻塞新 generation 发布。

(4) strict cooked fail closed

决策：cooked mode 验证 manifest/index/envelope/type/codec/required extension，任何不一致都失败且绝不 source fallback。这样发布包缺失不会在开发机上“看似可用”、到目标机才崩溃；代价是发布工具必须完整声明 runtime capability。

六、设计巧思与最佳实践

1. 当前业务场景与业务模型的最佳实践

  • 完整 load key：identity 不是 coalescing 的全部条件。mode、expected type、target evidence 和 bound generation 都进入 key，防止逻辑同名但物理语义不同的请求错误合并。
  • 预留后执行：completion capacity 在 admission 时预留，使系统不会在成功加载后才因通知资源不足而陷入无法表达的状态。
  • 独立 cancellation token：共享 dependency physical load 不继承第一个 root 的取消所有权；root 只管理自己的 interest。
  • immutable payload：handle 可安全跨 manager 生命周期保留；hot reload 不会原地改变既有对象。
  • strict boundary：cooked runtime 不链接 Tools，也不“帮忙” import source，保持发布环境可复现。

2. 优化方案与收益

已实现的优化包括：等价请求与 dependency node 合并以降低重复 I/O/import；pre-bound manifest index 避免每次请求重扫 generation；bounded FIFO worker 与 completion reservation 限制内存增长；引用驱动卸载降低无预算缓存的驻留；stable order 和 normalized diagnostics 降低并发测试噪声。M4 Pro reference gate 覆盖 8 请求 admission、1000 Asset/5000 edge 图、10000 completion pump 和 10000 lifecycle cycle。

未来优化铺垫包括 chunk request、priority、CPU/GPU budget、LRU/eviction 和 prefetch。它们尚未实现，不能把当前 benchmark 解读为 streaming 性能承诺。

3. 已知限制与后续演进

  • 本期加载粒度是完整 typed payload；后续 Feature 030 才拆分 mip/meshlet chunk 和 residency。
  • reader lease 只提供安全维护证据，不决定 pruning policy。
  • 跨平台 workflow 已建立，但本文生成时尚未对当前 revision 执行远程八任务验证。
  • Renderer 仍需显式把 Asset handle 转为 RHI resource；manager 不缓存 GPU object。
  • 后续 Feature 027 Metal 可依赖 cooked shader payload 与 runtime manager，但仍必须维持 Backend 不反向依赖 Asset 的既定边界。

2. 并发与所有权阅读提示

阅读本期代码时，先问三个问题：谁拥有 request interest，谁拥有 physical operation，谁保持 payload alive。它们分别落在 request table、operation/dependency coordinator 和 cache/typed handle。把这三者混成一个 reference count，通常会导致一个 caller 取消所有人、manager 析构使 handle 悬空，或 dependency 永远无法卸载。

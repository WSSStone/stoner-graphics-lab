2. 本期核心摘要

交付第一批真正可被全项目复用的 Core vocabulary：固定宽度类型、字符串/名字、所有权指针、数组/映射别名和内存工具。它让后续模块可以用统一命名、统一命名空间和统一聚合头进入工程，而不把标准库细节散落到每个层。

最值得学习的是“词汇类型先行”的工程思路：引擎不是一开始就写渲染器，而是先固定能跨模块传播的类型语义。FName 的 hash fast path 加 text fallback、FMemory 的显式对齐和容器 alias 都是在为之后资源句柄、日志类别、RHI 描述结构打地基。

3. 上下文与依赖

  • 前置依赖：SCons project skeleton and existing Core static library layout
  • 后续铺路：math, logging, platform, RHI public contracts
  • 层级边界：Core 只向下依赖已稳定 contract，不能反向 include 更高层模块。
  • 编译期依赖：公共头和 SCons 目标；概念依赖：spec/plan/tasks 中定义的 lifecycle、result、diagnostic 与测试替身。

二、目标与边界

1. 业务与功能目标

  • 引擎开发者通过 CoreMinimal.h 一次性获得稳定基础类型。
  • 需要精确依赖时，可以只 include FString、FName、FMemory 或容器别名头。
  • 内存操作提供 Allocate/Deallocate、AllocateAligned、Copy/Move/Set/Zero 等最小可测能力。
  • 成功以值语义、比较结果和测试断言表达；失败以空对象、无效参数保护或测试失败表达。

2. 架构目标与定位

Application / Tests
    ↓ 使用 public contract
Core feature: Core Foundation Types & Memory
    ↓ 依赖稳定下层能力
Core vocabulary / diagnostics / platform
    ↓ 按阶段连接
RHI contracts / Backend implementations / Renderer systems

本阶段的 public contract 是调用方可以依赖的最小稳定面；private implementation、测试替身和 backend-specific helper 都不能反向污染上层 API。

3. 边界与非目标（约束）

  • 不实现自研 allocator 池，因为当前阶段只需要可验证的基础行为。
  • 不实现 string intern table，因为 FName 先保持 collision-safe correctness。
  • 不实现小字符串优化或容器替换，避免过早复制标准库能力。

三、交互与产品设计

1. 用户使用路径

调用方 include CoreMinimal 或精准头文件 -> 构造 FString/FName/容器/指针 -> 通过 FMemory 做显式字节操作 -> CoreFoundationTests 验证尺寸、所有权、移动、对齐和 collision-safe equality。

学习时建议把这一段当成“最小工作流”：先找到输入对象，再跟踪它如何变成状态、诊断、测试断言或 debug dump。

2. 核心规则与状态机

未创建/空状态
    -> 描述或 Begin/Declare/Create
    -> 可验证中间状态
    -> Success: 可查询、可绑定、可执行或可复用
    -> Reset/Shutdown/Invalidated
    -> 任何后续使用必须返回错误结果或诊断

这个状态机是本项目底层模块的共同风格：显式创建、显式验证、显式失效。不同 feature 的状态名不同，但测试都围绕“合法转换”和“非法转换可观察”展开。

3. 失败模式与调试入口

  • FName hash 相同但文本不同必须比较为不等，否则资源名和日志类别会出现幽灵碰撞。
  • 无效 alignment 不能静默返回看似可用的指针，否则后续 SIMD/resource upload 会隐藏未定义行为。
  • CoreMinimal 不能 include 高层头，否则基础层会反向依赖 RHI/Renderer。

调试入口优先看 Tests/CoreFoundationTests.cpp 中的负路径用例，再看对应 diagnostics、result code 或 debug dump 输出；这些测试比源码更快暴露设计意图。

四、技术架构与关键决策

1. 技术栈与基础设施

  • C++20，传统 header/source 分离；公共 API 遵守项目 UE-style 命名。
  • SCons 4.10.1 构建；验证入口保持在单一 StonerTest 可执行文件。
  • Core/RHI/Renderer public contract 尽量不泄漏 backend 或平台实现细节。
  • headless、fallback 和 mock 测试优先保证无 GPU/无窗口环境仍能验证语义。

诊断记录应覆盖失败原因、对象状态、兼容性判断和 deterministic ordering；result code 负责控制流，diagnostic/debug dump 负责解释“为什么”。不记录大块二进制或平台私有句柄，避免输出不可复现。

3. 架构决策记录 (ADR)

(1) 用 alias 包装标准库容器

背景：当前目标是稳定 public vocabulary，不是重写容器。

理由：减少实现风险，后续可在别名背后替换。

被否决方案：立即自研 TArray/TMap：测试量和 bug 面过大。

后果：API 名称稳定，但性能语义暂时跟随 std 容器。

(2) FName 保留文本 fallback

背景：hash 只能优化比较，不能决定语义正确性。

理由：collision-safe equality 适合早期无全局 name table 的阶段。

被否决方案：只存 hash：会在碰撞时破坏 correctness。

后果：未来若引入 intern table，需要迁移构造和存储策略。

六、设计巧思与最佳实践

1. 当前业务场景与业务模型的最佳实践

(1) Vocabulary Type

是什么：给常见值一个项目内名字，减少跨模块语义漂移。

项目表达：FString/FName/TArray/TMap 让后续 RHI 描述结构不用直接暴露 std 类型。

真实引擎/API 对应：UE 的 FString/FName/TArray 是同类思想，但本项目先用轻量版本。

(2) Alignment

是什么：CPU/GPU 数据经常有对齐要求，错误对齐会导致性能下降或未定义行为。

项目表达：FMemory::AllocateAligned 在 CoreFoundationTests 中覆盖有效和无效 alignment。

真实引擎/API 对应：Vulkan uniform buffer、Metal argument buffer、DX constant buffer 都要求开发者理解对齐。

(3) Collision-safe identity

是什么：hash 是索引，不是身份。

项目表达：FName 比较使用 hash fast path 但保留 text fallback。

真实引擎/API 对应：真实引擎 name table、shader cache key、pipeline cache key 都需要避免 hash-only bug。

2. 优化方案与收益

本阶段的优化重点不是追求最终性能，而是建立可替换的语义基线：先让行为被测试锁住，再在未来引入 SIMD、真实 Vulkan runtime、更复杂 allocator、pipeline disk cache、render graph aliasing 或 async compute。

这种做法的收益是 migration cost 可控：只要 public contract 和测试矩阵稳定，private implementation 可以逐步从 mock/fallback 演进到真实 GPU 路径。

七、编程语言知识点

1. 标准库接口与用法

本项目优先使用标准库可移植能力，例如容器、智能指针、字符串、chrono、filesystem、mutex 和 algorithm。关键不是“用了哪个库”，而是把标准库行为包装进项目自己的 contract，减少跨模块直接耦合。

2. 语言特性与惯用法

  • RAII/ownership：资源对象在 shutdown/invalidate 时显式失效，避免悬空后继续成功。
  • enum class：用强类型枚举表达 result、queue、usage、stage、state，避免整数误传。
  • 值语义和移动语义：desc、handle、record 适合轻量复制；拥有对象则通过指针或明确 lifecycle 管理。
  • 宏只用于日志/断言等需要调用点上下文的场景，其余优先函数和类型系统。

3. 平台相关与编译器行为

平台相关代码应留在 Core platform 或 Backend private 边界内。公共头尽量避免平台宏分叉和图形 API 头泄漏，这样 Windows/macOS/Linux 与未来 Vulkan/DX/Metal/OpenGL backend 才能共享上层代码。

八、软件工程知识点

1. 设计模式与架构模式

  • Layered Architecture：Core -> RHI -> Backend/Renderer 的依赖方向必须单向。
  • Facade/Aggregate Header：CoreMinimal、RHIMinimal 或 RendererMinimal 提供便利入口，但不能隐藏边界污染。
  • Builder/Compiler/Executor：复杂声明式系统先收集意图，再编译计划，最后执行。
  • Adapter：Backend/Vulkan 把具体 API 对象适配成 RHI contract。

2. 工程原则与方法论

  • Contract-first：先定义 public behavior，再实现 backend 或优化。
  • Fail fast but diagnosable：错误尽早返回，同时留下能解释原因的记录。
  • Determinism：排序、dump、fallback 和测试输出都尽量稳定。
  • YAGNI with escape hatch：推迟工业级复杂能力，但保留未来接入点。

3. 测试策略与质量保障

测试不是只证明“代码能跑”，而是把工程假设固化下来：合法路径、非法路径、边界隔离、重复运行稳定性和 fallback/headless 环境都应该被覆盖。对图形工程而言，mock 与 fallback 不是偷懒，而是让 CI 可以在没有真实 GPU 的情况下守住 contract。

2. 本期核心摘要

把 Phase 001 中的空 Core 骨架推进为可用的 Core 基础层，提供固定宽度类型、字符串、名称、智能指针别名、容器别名和内存工具。 它是后续 Math、RHI、Backend、Renderer、Application 等阶段共享的底层词汇表，目标是让后续代码不再各自发明局部类型和内存接口。

二、目标与边界

1. 业务与功能目标

面向引擎开发者，解决"底层类型、所有权、容器、内存操作没有统一入口"的问题。完成后，开发者可以在 Core 或后续层中直接使用项目统一命名的基础设施：

  • FPlatformTypes 以及 int8、uint32、uintptr 等固定宽度与平台相关类型别名
  • FString 作为拥有型字符串值
  • FName 作为不可变、支持快速比较且碰撞安全的名称值
  • TSharedPtr<T>、TUniquePtr<T> 作为统一所有权词汇
  • TArray<T>、TMap<K, V> 作为统一容器词汇
  • FMemory 作为分配、对齐分配、释放、复制、移动、填充、清零的统一入口

2. 架构目标与定位

本阶段定位为整个引擎的 Core Foundation。它位于所有后续层之下，只向上提供稳定公共头文件，不向上依赖任何层。

2. 核心规则与状态机

(1) FString 状态

Empty -> Assigned -> Copied
Empty -> Assigned -> MovedFromValid
Assigned -> Cleared -> Empty
  • 默认构造为空字符串
  • 拷贝后内容相等
  • 移动后目标保留原文本，源对象仍可析构、赋值和查询
  • Clear() 后重新回到空状态

(2) FName 比较规则

input text -> FString text storage -> hash fast path -> text fallback equality
  • 相同文本创建的 FName 必须相等
  • 不同文本创建的 FName 必须不相等
  • 即使两个名称哈希相同，也必须继续比较文本，保证碰撞安全
  • 当前阶段只保证单进程内行为

(3) FMemory 生命周期

Unallocated -> Allocated -> Deallocated
Unallocated -> AllocationFailed
Allocated -> Written -> Deallocated
  • Allocate(0) 返回 nullptr
  • 合法对齐请求返回满足对齐要求的地址
  • 非法对齐请求返回 nullptr，不破坏已有内存
  • Deallocate(nullptr) 和 DeallocateAligned(nullptr) 安全

3. 架构决策记录 (ADR)

ADR-1: 先使用标准库背书的初始实现

决策：TSharedPtr、TUniquePtr、TArray、TMap 当前阶段使用项目命名别名，底层依托标准库设施。

理由：本阶段目标是建立稳定 vocabulary，而不是一次性实现完整自研容器系统。后续如果需要自研 allocator 或容器，可以保留项目公共命名不变，在内部替换实现。

被否决的方案：从第一阶段就实现完整自研 string/container/smart pointer——范围过大，会拖慢后续核心路线。

ADR-2: FString 使用 class 而不是纯 alias

决策：FString 是拥有型 class，而不是 using FString = std::string。

理由：未来可以扩展项目特定行为，而不破坏公共名字。能明确提供 Len()、IsEmpty()、View()、Clear() 等引擎风格接口。与 FName 的输入和比较关系更稳定。

被否决的方案：直接 alias 到标准字符串——短期最简单，但未来改造公共 API 成本更高。

ADR-3: FName 不做全局 intern table

决策：FName 当前保存文本和 hash，不引入全局名称池。

理由：满足当前快速比较和碰撞安全需求。避免全局生命周期、线程安全、序列化策略等额外复杂度。更适合第一阶段 Core 基础设施。

被否决的方案：类似生产级引擎的全局 intern table——未来可考虑，但不适合 spec003 范围。

ADR-4: FMemory 使用手动 aligned allocation 包装

决策：FMemory::AllocateAligned 自行保存原始指针并返回对齐后的地址。

理由：行为可控，DeallocateAligned 能找到原始分配地址。可以明确规定零大小和非法 alignment 的确定性行为。避免平台 API 分歧在公共接口中泄漏。

被否决的方案：直接把不同平台 allocator 行为暴露给调用方——会导致 zero-size 和 alignment 边界行为不一致。

ADR-5: 测试继续使用 StonerTest

决策：不引入第三方测试框架，继续扩展现有 StonerTest。

理由：Phase 001 已经建立测试可执行文件。当前验证逻辑简单，手写 Record() 足够。避免为第一批 Core primitives 引入额外依赖。

被否决的方案：引入 Google Test / Catch2——增加外部依赖，不符合学习导向项目的自研原则。

六、设计巧思与最佳实践

6.1 当前业务场景与业务模型的最佳实践

为什么 FString 是 class 而非 alias

引擎的字符串需求远超标准库 std::string：未来需要 Len()、IsEmpty()、View()、Clear() 等引擎风格接口，以及可能的编码转换、格式化、本地化能力。使用 class 包装可以在不改变公共 API 的前提下逐步扩展内部实现。

为什么 FName 使用 hash + text fallback

名称比较是引擎中极高频的操作（资源查找、类别匹配等）。hash fast path 将大多数比较降为一次整数比较（O(1)），仅在 hash 碰撞时才回退到文本比较。这在不引入全局 intern table 复杂度的前提下，获得了接近 O(1) 的比较性能。

为什么容器和智能指针先用 alias

项目是学习导向 [[memory:9rx96rfq]]，但"先建立词汇表，后替换实现"是工程上的最佳分阶段策略。这样后续阶段可以在不改变调用方代码的前提下，逐步替换为自研容器（如自定义 allocator、内存池、SOA 布局等）。

为什么 FMemory 手动管理对齐

不同平台的 aligned_alloc / _aligned_malloc 行为差异大（零大小、非 2 的幂对齐、释放方式）。手动包装保证了所有平台上的确定性行为：零大小返回 nullptr、非法对齐返回 nullptr、释放 nullptr 安全。这消除了平台差异对上层代码的影响。

6.2 优化方案与收益

优化点场景收益
FName hash fast path 名称比较（资源查找、日志类别匹配） 大多数比较降为 1 次整数比较，避免字符串逐字符比较
FMemory 对齐分配 SIMD 数据、缓存行对齐结构 未来 SIMD 优化路径可直接使用，无需额外对齐处理
项目命名词汇表 全引擎代码统一性 后续替换底层实现时，调用方代码零修改
CoreMinimal.h 聚合入口 日常开发 一次 include 获得所有 Core 能力，减少头文件管理负担

已知限制与后续演进

  • 仅在 Windows / Win64 / Debug / MSVC 环境验证通过，macOS 和 Linux 尚未在本机执行
  • TArray、TMap、TSharedPtr、TUniquePtr 当前是项目命名别名，还不是自研容器/智能指针
  • FName 当前不是全局 intern table，也不保证跨进程稳定 ID
  • FString 还不包含格式化、编码转换、本地化、allocator 注入等能力
  • 后续 Math 阶段可直接依赖 FPlatformTypes、FString、TArray 和 FMemory
  • 当 allocator 体系成熟后，再评估是否替换 TArray、TMap 的底层实现

七、编程语言知识点

7.1 标准库接口与用法

接口含义与用法
std::shared_ptr<T> 引用计数共享所有权智能指针。多个 shared_ptr 可指向同一对象，最后一个销毁时释放资源。本项目中 TSharedPtr<T> 是其项目命名别名。
std::unique_ptr<T> 独占所有权智能指针，不可拷贝只可移动。本项目中 TUniquePtr<T> 是其项目命名别名。保证资源在作用域结束时自动释放。
std::make_shared<T>() 一次分配同时创建对象和控制块，比先 new 再构造 shared_ptr 更高效（减少一次堆分配）。
std::vector<T> 动态数组，连续内存存储。push_back() 追加元素，size() 查询大小。本项目中 TArray<T> 是其项目命名别名。
std::unordered_map<K,V> 哈希表实现的键值映射，平均 O(1) 查找。本项目中 TMap<K,V> 是其项目命名别名。
std::string 标准拥有型字符串。FString 内部使用 std::string 存储文本数据，对外提供引擎风格接口。
std::string_view 非拥有型字符串视图，零拷贝引用已有字符串。FString::View() 返回此类型，用于高效传递字符串而不复制。
std::hash<T> 标准哈希函数对象。FName 使用 std::hash<std::string> 计算名称哈希值，用于快速比较路径。
std::malloc / std::free C 标准库堆分配/释放。FMemory::Allocate() 内部使用，提供统一的分配入口。
std::memcpy / std::memmove / std::memset 内存操作原语。FMemory::Copy()、Move()、Set() 分别封装这三个函数，提供类型安全的项目接口。

7.2 语言特性与惯用法

using 类型别名

using int32 = int32_t; 使用 C++11 的 using 声明创建类型别名，比 typedef 更清晰。本项目用此建立固定宽度类型词汇表（int8、uint32、uintptr 等）。

移动语义 (Move Semantics)

FString 支持移动构造和移动赋值。std::move() 将左值转为右值引用，触发移动构造函数，避免深拷贝。移动后源对象处于"有效但未指定"状态——可以析构、赋值和查询，但内容不确定。

模板别名 (Template Alias)

template<typename T> using TArray = std::vector<T>; 使用模板别名为标准容器建立项目命名。这保留了模板参数推导能力，同时提供了未来替换底层实现的接缝。

struct 作为纯数据类型容器

FPlatformTypes 使用 struct 而非 class，因为它只包含类型别名，没有行为或状态。struct 默认 public 访问，语义上表达"这是一组公开的类型定义"。

指针算术与对齐

FMemory::AllocateAligned() 使用 reinterpret_cast<uintptr_t> 将指针转为整数进行对齐计算，再转回指针。uintptr_t 保证能无损保存指针值。对齐公式：(addr + alignment - 1) & ~(alignment - 1)。

7.3 平台相关与编译器行为

平台/编译器差异处理方式
MSVC (Windows) _aligned_malloc / _aligned_free 是平台特有 API FMemory 不使用平台 API，自行实现对齐逻辑，保证跨平台一致
Clang / GCC aligned_alloc() 要求 size 是 alignment 的倍数 同上，不依赖平台 aligned_alloc，避免此限制
所有平台 sizeof(void*) 在 32/64 位系统不同 uintptr / intptr 类型别名保证与指针大小一致
C++17 标准 std::string_view 需要 C++17 或更高 项目使用 C++20，此特性可用

八、软件工程知识点

8.1 设计模式与架构模式

Facade 模式 — CoreMinimal.h

CoreMinimal.h 是 Core 层的 Facade：一个聚合入口头文件，隐藏了内部多个头文件的组织细节。调用方只需 #include "Core/CoreMinimal.h" 即可获得所有 Core 能力，无需了解内部文件结构。

Vocabulary Type 模式

本阶段的核心模式是建立"词汇类型"——FString、FName、TArray、TMap 等。这些类型是项目中所有代码共享的"语言"，确保不同模块之间的类型兼容性和语义一致性。

Wrapper / Adapter 模式 — FString

FString 包装 std::string，对外提供引擎风格接口（Len()、IsEmpty()、View()），对内使用标准库实现。这是 Adapter 模式的应用——将标准库接口适配为项目约定的接口。

8.2 工程原则与方法论

YAGNI (You Aren't Gonna Need It)

不实现全局 FName intern table、不实现自研容器、不实现 allocator 注入——这些都是"当前不需要"的能力。YAGNI 原则指导我们只实现当前阶段必要的最小功能集，避免过度设计。

接口稳定性优先 (Stable Interface First)

先建立稳定的公共 API（FString、TArray<T> 等命名），再在后续阶段替换内部实现。这保证了上层代码不会因底层重构而修改。这是"面向接口编程"原则的体现。

防御性编程 (Defensive Programming)

FMemory::Allocate(0) 返回 nullptr 而非未定义行为；DeallocateAligned(nullptr) 安全无操作；非法对齐返回 nullptr 而非崩溃。每个边界情况都有确定性行为，不依赖平台实现的"恰好正确"。

碰撞安全设计 (Collision Safety)

FName 的 hash fast path + text fallback 是"乐观路径 + 安全兜底"的工程方法论：大多数情况走快速路径（hash 比较），极少数碰撞情况走安全路径（文本比较）。这在不牺牲正确性的前提下获得了性能。

8.3 测试策略与质量保障

分类覆盖测试 (Category Coverage)

测试按类型分类组织：平台类型大小、FString 行为、FName 行为、智能指针行为、容器行为、FMemory 行为。每个类别独立验证，确保每个模块的正确性不依赖其他模块的实现。

边界值测试 (Boundary Testing)

重点测试边界情况：零大小分配、nullptr 释放、非法对齐、空字符串、hash 碰撞、移动后状态。这些边界是 bug 最容易出现的地方，也是平台差异最容易暴露的地方。

确定性行为验证

每个边界情况都有明确的预期行为（而非"未定义"或"实现定义"）。测试验证的是"确定性行为"——相同输入在所有平台上产生相同结果。这消除了"在我机器上能跑"的问题。

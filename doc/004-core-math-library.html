2. 本期核心摘要

把 Core 层从"基础类型与内存工具"推进到"可表达空间、颜色和几何关系"的数学基础层。 新增向量、矩阵、四元数、变换、颜色、包围盒、球体、平面和标量数学工具，为后续 RHI、Renderer、Application、相机、可见性、Meshlet、Ray Tracing、GI 等系统提供统一数学词汇。

最大设计取舍：先实现可验证、跨平台、标准库-only 的标量基线版本，同时把公开 API 设计成未来可加入 SIMD 优化而不改变调用方代码的形状。

二、目标与边界

1. 业务与功能目标

面向引擎开发者，解决"后续引擎层需要空间数学但项目没有统一数学类型"的问题。完成后，开发者可以使用：

  • FMath：标量数学常量和工具函数
  • FVector2、FVector3、FVector4：2D、3D、4D 浮点向量
  • FMatrix4x4：4x4 变换矩阵
  • FQuat：四元数旋转
  • FTransform：平移、旋转、缩放组合变换
  • FColor、FColorBytes：RGBA 浮点颜色和字节颜色转换
  • FBox：轴对齐包围盒
  • FSphere：包围球
  • FPlane、EPlaneClassification：平面和点分类

2. 架构目标与定位

定位为 Core Foundation 的第二个能力层：在 Types & Memory 之上提供数学值类型。仍然位于所有图形和应用层之下。

2. 核心规则与状态机

(1) 坐标系与矩阵规则

Core Math Convention
├── right-handed coordinate
├── row-major FMatrix4x4 storage
├── point transform: implicit W = 1
└── direction transform: implicit W = 0
  • FVector3::UnitX().Cross(FVector3::UnitY()) == FVector3::UnitZ()（右手叉乘）
  • FMatrix4x4 使用 float M[4][4] 保存 row-major 数据
  • 平移矩阵将平移值放在最后一列：M[0][3]、M[1][3]、M[2][3]

(2) 浮点比较规则

raw float result -> FMath::IsNearlyEqual / IsNearlyZero -> deterministic pass/fail
  • FMath::DefaultTolerance = 1.0e-5f
  • 标量使用 FMath::IsNearlyEqual() 和 FMath::IsNearlyZero()
  • 向量、矩阵、四元数、颜色提供 NearlyEquals() 风格能力
  • 直接构造出的组件值可使用 operator== 做精确比较
  • 计算结果必须使用 tolerance

(3) 向量状态

Zero Vector -> SafeNormalize -> Zero Vector
Finite Vector -> SafeNormalize -> Unit Direction
Computed Vector -> NearlyEquals -> Tolerance-aware Result

(4) 矩阵逆状态

Invertible Matrix -> TryInverse -> true + inverse matrix
Singular Matrix -> TryInverse -> false + identity fallback

(5) 四元数与变换规则

Axis + Angle -> FQuat -> RotateVector / ToMatrix
Translation + Rotation + Scale -> FTransform -> TransformPoint / TransformVector
  • FQuat 默认是 identity；零轴时 FromAxisAngle() 返回 identity
  • A * B 语义：旋转向量时先应用 B，再应用 A
  • FTransform 应用顺序：Scale → Rotation → Translation
  • TransformPoint() 应用平移，TransformVector() 不应用平移

(6) 颜色与几何规则

  • FColor 使用 RGBA 浮点通道，默认 opaque black
  • FColor::ToBytes() 将通道 clamp 到 [0, 1]，再四舍五入到 [0, 255]
  • FBox 默认 invalid/empty，第一次 AddPoint() 后变为 valid
  • FSphere 半径小于 0 时 invalid
  • FPlane::ClassifyPoint() 使用 tolerance 将点分为 Front、Back、On

3. 架构决策记录 (ADR)

ADR-1: 为什么不用 GLM

决策：不引入 GLM，先自研 Core Math。

理由：项目是学习导向，Core 子系统优先自研。当前需求规模可控，主要是建立 engine vocabulary。自研能显式记录坐标系、矩阵布局、tolerance、invalid behavior。

被否决的方案：GLM——成熟但会隐藏很多底层数学实现细节，不符合本阶段学习目标。

ADR-2: 为什么先做标量基线而不是 SIMD

决策：先实现 scalar baseline，后续再加 SIMD。

理由：标量路径跨 MSVC、Clang、GCC 更容易稳定。测试可以作为未来 SIMD 路径的 reference behavior。公开 API 不暴露 SIMD 类型，未来内部优化不影响调用方。

被否决的方案：立即使用 SSE/NEON/AVX——平台分支复杂，会提前引入非业务风险。

ADR-3: 为什么使用右手坐标系

决策：Core Math 使用右手坐标系。

理由：X cross Y = Z 的规则直观，测试可明确验证。Vulkan 和大量图形资料中右手约定更常见。具体图形 API 需要不同约定时，可以在 Backend 或 shader 边界转换。

被否决的方案：① 每个 Backend 自定义坐标系（Core 数学不可预测）；② 左手 Core（与 Vulkan-first 学习路径不如右手直观）。

ADR-4: 为什么矩阵使用 row-major 存储

决策：FMatrix4x4 使用 row-major 存储，平移放在最后一列。

理由：C++ 中 M[row][column] 的阅读和调试直接。测试可以明确检查 At(0, 1) 等 row-major 访问。存储顺序与 shader 上传约定可以在后续 RHI/Backend 边界处理。

被否决的方案：① Column-major（在 Core C++ 层并不天然更优）；② 不声明布局（测试、序列化、上传和调试都变得模糊）。

ADR-5: 为什么 inverse 使用 Try 模式

决策：矩阵和变换逆使用 TryInverse(out) 返回 bool。

理由：奇异矩阵、零 scale transform 是正常边界情况。bool 返回值使调用方必须显式处理失败。失败时输出 identity fallback，避免未初始化输出。

被否决的方案：① 直接返回矩阵（无法区分成功和失败）；② 抛异常（Core 风格偏 deterministic return）。

ADR-6: 为什么 FBox 默认 invalid

决策：默认 FBox 是 invalid/empty，而不是零大小 valid box。

理由：空包围盒和位于原点的零大小包围盒语义不同。AddPoint() 第一次调用可以自然初始化 min/max。后续 culling 或 bounds combine 不会误把空 box 当成真实原点 bounds。

被否决的方案：默认 min=max=0 且 valid——会混淆 empty 和 zero-size。

六、设计巧思与最佳实践

6.1 当前业务场景与业务模型的最佳实践

为什么自研数学库而不用 GLM

项目是学习导向 [[memory:9rx96rfq]]，Core 子系统优先自研。自研数学库让开发者深入理解坐标系约定、矩阵布局、浮点精度、边界行为等底层细节。这些知识在使用任何第三方库时都是必要的基础。

为什么 API 设计为 SIMD-ready 但不实现 SIMD

公开 API 以普通值类型暴露（FVector3、FMatrix4x4），内部实现可以在未来替换为 SIMD 路径。这样调用方代码不需要修改，同时标量基线作为 reference behavior 验证 SIMD 实现的正确性。

为什么使用 TryInverse 模式而非直接返回

奇异矩阵和零 scale 变换是图形引擎中的常见边界情况。TryInverse(out) -> bool 模式强制调用方处理失败路径，避免静默产生错误的逆矩阵导致后续渲染异常。失败时输出 identity fallback 保证输出始终有效。

为什么测试优先验证行为而非实现

测试名称描述行为（如"singular inverse fails deterministically"），而非实现细节（如"Gauss pivot branch works"）。这样当内部实现从标量切换到 SIMD 时，测试无需修改，只要行为一致即可。

为什么坐标系和布局约定在 Core 层固定

Core 选择右手坐标系 + row-major 存储，所有上层系统共享同一约定。Backend 或 shader 需要不同约定时在边界转换。这避免了"每个系统各自约定"导致的 bug 和混乱。

6.2 优化方案与收益

优化点场景收益
Header-only value types 向量/矩阵运算 编译器可内联所有数学操作，避免函数调用开销
SafeNormalize 零向量保护 归一化计算 避免除零崩溃，返回零向量而非 NaN/Inf
Tolerance-based comparison 浮点计算结果比较 消除浮点精度累积导致的假阴性测试失败
FBox invalid 默认状态 包围盒累积计算 第一次 AddPoint 自然初始化，无需特殊的"第一个点"逻辑
FQuat 零轴 identity fallback 动画/旋转插值 退化输入不产生 NaN，保持系统稳定

已知限制与后续演进

  • 当前只实现 float 数学类型，无 double precision
  • 当前没有 SIMD 优化路径
  • 当前没有矩阵分解、look-at、projection、frustum 等相机相关工具
  • FMatrix4x4::TryInverse() 是通用高斯-约旦实现，适合正确性基线，不代表最终性能路径
  • FBox 仅为轴对齐包围盒，不支持 oriented box
  • FPlane 分类只返回 front/back/on，不包含裁剪或相交结果
  • 后续应通过新的 spec 逐步扩展，而不是在本阶段继续发散

七、编程语言知识点

7.1 标准库接口与用法

接口含义与用法
std::sqrt() 平方根函数。FMath::Sqrt() 封装此函数，用于向量长度计算、归一化等。
std::sin() / std::cos() 三角函数。FMath::Sin()、FMath::Cos() 封装，用于旋转矩阵构造、四元数轴角构造。
std::atan2() 反正切函数，返回角度范围 [-π, π]。用于从向量计算角度。
std::abs() / std::fabs() 绝对值。FMath::Abs() 封装，用于 tolerance 比较、行列式计算等。
std::numeric_limits<float> 提供浮点数的极限值（max()、lowest()、infinity()）。FBox 用 max() 初始化 invalid 状态。
std::isinf() / std::isnan() 检查浮点数是否为无穷大/NaN。FVector3::HasInfinite() 使用，用于安全检查。
<cstring> / std::memcpy 内存拷贝。矩阵乘法中用于初始化结果矩阵为零。

7.2 语言特性与惯用法

constexpr 常量

FMath::Pi、FMath::DefaultTolerance 等使用 static constexpr float 声明。编译期常量避免运行时初始化开销，且可用于模板参数和数组大小。

static 工厂方法

FVector3::UnitX()、FQuat::FromAxisAngle()、FMatrix4x4::Identity() 等使用静态方法作为命名构造器。比重载构造函数更清晰地表达意图。

运算符重载

向量、矩阵、四元数重载了 +、-、*、== 等运算符。这让数学表达式可以用自然的数学符号书写（如 A * B 而非 A.Multiply(B)）。

out 参数模式

TryInverse(FMatrix4x4& OutResult) 使用引用参数作为输出。返回 bool 表示成功/失败，避免了 std::optional 的拷贝开销（矩阵是 64 字节大对象）。

enum class 类型安全枚举

EPlaneClassification { Front, Back, OnPlane } 使用 enum class 而非普通 enum。这防止枚举值隐式转换为整数，避免意外的类型混用。

7.3 平台相关与编译器行为

八、软件工程知识点

8.1 设计模式与架构模式

Value Object 模式

所有数学类型（FVector3、FMatrix4x4、FQuat 等）都是 Value Object——无身份、仅通过值比较、不可变（或者每次操作返回新值）。这简化了推理：不需要考虑共享状态、别名、生命周期等问题。

Factory Method 模式

FQuat::FromAxisAngle()、FMatrix4x4::Translation()、FPlane::FromThreePoints() 等静态工厂方法提供命名构造。比重载构造函数更清晰地表达意图，且可以在工厂内部处理边界情况（如零轴返回 identity）。

Null Object 模式

FVector3::Zero()、FQuat::Identity()、FMatrix4x4::Identity() 提供“无操作”默认值。当边界情况发生时（如零向量归一化、奇异矩阵求逆），返回这些安全默认值而非崩溃或产生 NaN。

8.2 工程原则与方法论

确定性行为 (Deterministic Behavior)

每个边界情况都有明确的预期结果：零向量 SafeNormalize 返回零向量，奇异矩阵 TryInverse 返回 false + identity，零轴 FromAxisAngle 返回 identity。不依赖“未定义行为”或“实现定义”。

分层架构 (Layered Architecture)

Core Math 位于 Core Types 之上、RHI/Renderer 之下。严格的单向依赖：上层可以使用下层，下层不知道上层存在。这保证了 Core Math 可以独立测试、独立演进。

开闭原则 (Open-Closed Principle)

API 对扩展开放（未来可加 SIMD、可加 double 版本），对修改关闭（现有调用方代码不需改变）。这通过值类型 + 隐藏内部实现实现。

约定优于配置 (Convention over Configuration)

右手坐标系、row-major 存储、平移在最后一列——这些约定在 Core 层固定，所有上层系统共享。不需要每个模块各自配置坐标系，减少了混乱和 bug。

8.3 测试策略与质量保障

Baseline Equivalence Testing

四元数旋转、矩阵旋转、变换旋转三条路径应用相同旋转后结果必须一致。这是“基线等价测试”——多条实现路径交叉验证，确保它们语义一致。

Tolerance-Aware Assertion

浮点测试不使用 == 而使用 NearlyEquals()。这是数值计算测试的标准实践——浮点精度累积是不可避免的，测试应该验证“足够接近”而非“精确相等”。

边界值与退化输入测试

重点测试退化输入：零向量归一化、奇异矩阵求逆、零轴四元数、负半径球体、三点共线平面。这些是数学库最容易出错的地方，也是生产环境中实际会遇到的场景。

行为驱动测试命名

测试名称描述行为而非实现（如“singular matrix inverse fails deterministically”而非“Gauss pivot returns false”）。这样当内部实现从标量切换到 SIMD 时，测试无需修改。

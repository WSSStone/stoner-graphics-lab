2. 本期核心摘要

交付 Core 数学层：标量 helper、向量、矩阵、四元数、Transform、Color、Box、Sphere 和 Plane。所有类型保持 header-only、标准库可移植、确定性测试优先，为渲染空间、相机、裁剪和资源描述中的尺寸/颜色表达提供统一基础。

最值得学习的是“数学约定也是 API”：右手坐标、row-major 矩阵、tolerance、inverse failure、safe normalize 都是引擎一致性的根。图形 bug 经常不是算法错，而是矩阵布局、乘法顺序、退化输入处理没有写成契约。

3. 上下文与依赖

  • 前置依赖：003 Core Foundation Types and Memory
  • 后续铺路：camera, transform hierarchy, culling, RHI viewport/scissor, renderer spatial reasoning
  • 层级边界：Core 只向下依赖已稳定 contract，不能反向 include 更高层模块。
  • 编译期依赖：公共头和 SCons 目标；概念依赖：spec/plan/tasks 中定义的 lifecycle、result、diagnostic 与测试替身。

二、目标与边界

1. 业务与功能目标

  • 开发者能表示 2D/3D/4D 向量、矩阵、旋转、位移缩放组合和基础几何体。
  • 通过 TryInverse/SafeNormalize 等 API 明确退化输入。
  • 颜色支持 float 与 byte channel 互转。
  • 测试输出证明 baseline 行为可供未来 SIMD 优化对照。

2. 架构目标与定位

Application / Tests
    ↓ 使用 public contract
Core feature: Core Math Library
    ↓ 依赖稳定下层能力
Core vocabulary / diagnostics / platform
    ↓ 按阶段连接
RHI contracts / Backend implementations / Renderer systems

本阶段的 public contract 是调用方可以依赖的最小稳定面；private implementation、测试替身和 backend-specific helper 都不能反向污染上层 API。

3. 边界与非目标（约束）

  • 不引入 GLM，避免外部依赖掩盖项目约定。
  • 不实现 SIMD，先用 baseline tests 锁定语义。
  • 不实现相机、投影矩阵完整工具和物理几何库，这些属于后续 Renderer/Application。

三、交互与产品设计

1. 用户使用路径

构造空间值 -> 使用 FMath tolerance 执行运算 -> 对 inverse/normalize 等退化输入返回显式状态 -> CoreMathTests 验证普通、边界和 NaN/Infinity 场景 -> 后续 Renderer 以同一约定解释坐标。

学习时建议把这一段当成“最小工作流”：先找到输入对象，再跟踪它如何变成状态、诊断、测试断言或 debug dump。

2. 核心规则与状态机

未创建/空状态
    -> 描述或 Begin/Declare/Create
    -> 可验证中间状态
    -> Success: 可查询、可绑定、可执行或可复用
    -> Reset/Shutdown/Invalidated
    -> 任何后续使用必须返回错误结果或诊断

这个状态机是本项目底层模块的共同风格：显式创建、显式验证、显式失效。不同 feature 的状态名不同，但测试都围绕“合法转换”和“非法转换可观察”展开。

3. 失败模式与调试入口

  • 矩阵 row/column major 约定不一致，会导致物体位置正确但旋转/位移看似随机。
  • Normalize(Zero) 若返回 NaN，会污染整个 transform hierarchy。
  • 颜色 byte/float 转换如果不 clamp，后续 clear color 或 material 参数会出现越界。

调试入口优先看 Tests/CoreMathTests.cpp 中的负路径用例，再看对应 diagnostics、result code 或 debug dump 输出；这些测试比源码更快暴露设计意图。

四、技术架构与关键决策

1. 技术栈与基础设施

  • C++20，传统 header/source 分离；公共 API 遵守项目 UE-style 命名。
  • SCons 4.10.1 构建；验证入口保持在单一 StonerTest 可执行文件。
  • Core/RHI/Renderer public contract 尽量不泄漏 backend 或平台实现细节。
  • headless、fallback 和 mock 测试优先保证无 GPU/无窗口环境仍能验证语义。

3. 架构决策记录 (ADR)

(1) 自研最小数学库而不是 GLM

背景：引擎需要明确自己的坐标、矩阵和 tolerance 约定。

理由：早期类型小而可测，便于后续优化。

被否决方案：直接使用 GLM：快但项目学习价值和契约清晰度较低。

后果：未来可用 SIMD 替换内部实现，但测试必须保持行为一致。

(2) TryInverse 返回成功状态

背景：逆矩阵可能不存在，不能假装每个 transform 都可逆。

理由：调用方被迫处理失败路径，测试也能覆盖退化输入。

被否决方案：抛异常或返回未定义矩阵：不符合当前显式状态风格。

后果：调用代码略多，但调试更容易。

六、设计巧思与最佳实践

1. 当前业务场景与业务模型的最佳实践

(1) Coordinate Convention

是什么：坐标系决定矩阵、叉乘、剔除和相机方向。

项目表达：FMath/FMatrix4x4 注释固定右手与 row-major 规则。

真实引擎/API 对应：Vulkan/DX/Metal 的 clip space 和 NDC 差异都需要从这里接入转换。

(2) Tolerance-aware comparison

是什么：浮点数不能像整数一样精确比较。

项目表达：NearEqual 与测试容差让行为跨平台更稳定。

真实引擎/API 对应：shader 结果验证、CPU culling、physics broadphase 都需要容差思维。

(3) Safe operations

是什么：退化输入是常态，不是异常。

项目表达：SafeNormalize/TryInverse 防止 NaN 传播。

真实引擎/API 对应：真实引擎中 NaN transform 会让 culling、shadow 和 skinning 级联失效。

2. 优化方案与收益

本阶段的优化重点不是追求最终性能，而是建立可替换的语义基线：先让行为被测试锁住，再在未来引入 SIMD、真实 Vulkan runtime、更复杂 allocator、pipeline disk cache、render graph aliasing 或 async compute。

这种做法的收益是 migration cost 可控：只要 public contract 和测试矩阵稳定，private implementation 可以逐步从 mock/fallback 演进到真实 GPU 路径。

七、编程语言知识点

1. 标准库接口与用法

本项目优先使用标准库可移植能力，例如容器、智能指针、字符串、chrono、filesystem、mutex 和 algorithm。关键不是“用了哪个库”，而是把标准库行为包装进项目自己的 contract，减少跨模块直接耦合。

2. 语言特性与惯用法

  • RAII/ownership：资源对象在 shutdown/invalidate 时显式失效，避免悬空后继续成功。
  • enum class：用强类型枚举表达 result、queue、usage、stage、state，避免整数误传。
  • 值语义和移动语义：desc、handle、record 适合轻量复制；拥有对象则通过指针或明确 lifecycle 管理。
  • 宏只用于日志/断言等需要调用点上下文的场景，其余优先函数和类型系统。

3. 平台相关与编译器行为

平台相关代码应留在 Core platform 或 Backend private 边界内。公共头尽量避免平台宏分叉和图形 API 头泄漏，这样 Windows/macOS/Linux 与未来 Vulkan/DX/Metal/OpenGL backend 才能共享上层代码。

八、软件工程知识点

1. 设计模式与架构模式

  • Layered Architecture：Core -> RHI -> Backend/Renderer 的依赖方向必须单向。
  • Facade/Aggregate Header：CoreMinimal、RHIMinimal 或 RendererMinimal 提供便利入口，但不能隐藏边界污染。
  • Builder/Compiler/Executor：复杂声明式系统先收集意图，再编译计划，最后执行。
  • Adapter：Backend/Vulkan 把具体 API 对象适配成 RHI contract。

2. 工程原则与方法论

  • Contract-first：先定义 public behavior，再实现 backend 或优化。
  • Fail fast but diagnosable：错误尽早返回，同时留下能解释原因的记录。
  • Determinism：排序、dump、fallback 和测试输出都尽量稳定。
  • YAGNI with escape hatch：推迟工业级复杂能力，但保留未来接入点。

3. 测试策略与质量保障

测试不是只证明“代码能跑”，而是把工程假设固化下来：合法路径、非法路径、边界隔离、重复运行稳定性和 fallback/headless 环境都应该被覆盖。对图形工程而言，mock 与 fallback 不是偷懒，而是让 CI 可以在没有真实 GPU 的情况下守住 contract。

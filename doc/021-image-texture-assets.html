2. 本期核心摘要

本期把 PNG、JPEG 与 Radiance HDR 源文件转换为 immutable CPU FImageAsset 和 FTextureAsset，固定 top-left 方向、straight alpha、显式 semantic/color space、完整 mip chain、版本证据与原子 registry publication。Renderer 再通过独立 adapter 把 CPU 资产映射为 RHI texture，并由 Vulkan fallback 或 native staging path 同步上传。

最值得学习的是 texture 不只是“一串像素”。Color、normal 与 generic data 的下采样数学不同；source RGB 与 GPU format capability 也不同。把 source interpretation、semantic filtering、portable RHI upload 和 native API ownership 分层，才能同时获得正确性、可测试性与未来 KTX2/streaming 的扩展空间。

3. 上下文与依赖

021 复用 020 的 FAssetId、digest、metadata、dependency、importer dispatch 与 execution lease；复用 008 的 texture contract、009-012 的 Vulkan device/resource/command 基础。它为 022 KTX2 cooking、023 material/shader assets、024 static mesh/model 和后续 runtime asset manager 提供第一种真实 payload。stb 只在 Asset private wrapper 中编译，public Asset contract 不接触 RHI 或 Vulkan。

二、目标与边界

1. 业务与功能目标

引擎开发者提供 source lease、稳定 Image/Texture ID 和显式 semantic。成功时得到两个不可变 payload 及一批原子 metadata；失败时得到稳定 result、stage、subject、participant、field/limit。Renderer 调用方可把 Texture asset 同步 realization 成 sample-ready RHI texture，失败不会留下半成品 GPU resource。

2. 架构目标与定位

source bytes
    |
    v
Asset: inspect -> decode -> orient -> semantic mips -> Image + Texture
    |                                                  |
    +---------------- registry metadata ---------------+
                                                       v
Renderer: format plan -> temporary RGB/RG expansion -> RHI upload plan
                                                       |
                                                       v
RHI contract -> Vulkan fallback / native image + staging + barriers

Asset ---> Core
Asset -X-> RHI / Renderer / Backend / graphics API

CPU interpretation、identity、semantic 与 mips 属于 Asset public contract；stb、container parser、transfer LUT 与 mip generator 属于 Asset private。GPU-compatible expansion 属于 Renderer，因为它理解“资产含义”和“RHI capability”两侧；native image/memory/command/fence 则只属于 Vulkan Backend。

3. 边界与非目标（约束）

  • 不做 KTX2、Basis、BC/ASTC/ETC compression：由 022 处理，避免 source import 与 platform cook 混为一体。
  • 不做 async request、cache、cancel 与 residency：它们需要 runtime asset manager 的生命周期模型。
  • 不做 cubemap、array、volume、sparse/virtual texture：021 先固定 2D contract 与 correctness baseline。
  • 不在 Asset 中创建 GPU handle：否则离线 cooker 与 headless tools 会被迫依赖 graphics runtime。
  • native Vulkan readback 是补充证据；CPU exact bytes 与 mock-RHI contract 才是三平台必需 gate。

三、交互与产品设计

1. 用户使用路径

FImageImportParameters P;
P.ImageId = ...;
P.TextureId = ...;
P.Settings.Semantic = ETextureSemantic::Color;

auto Imported = FAssetImportService::ImportAndRegister(
    Extensions, Registry, Request);

auto GPU = FTextureAssetRealizer::Realize({
    Device, Imported.Texture
});

happy path 先 bounded probe，再完成 container inspection、decode、top-left normalization 和 semantic mip，最后一次 registry batch 发布 Image/Texture。失败路径可查看 FAssetDiagnostics::FormatNormalized；GPU 失败则查看 realization stage 与 mip index，CPU asset 始终仍可 inspection。

2. 核心规则与状态机

request
  -> Probe
  -> Inspect
  -> Decode
  -> Validate Image
  -> Generate Mips
  -> Validate Texture
  -> Registry Commit

realization
  -> Plan Format
  -> Create Texture
  -> Upload mip 0..N
  -> Publish resource
  any failure -> invalidate request-owned texture -> return no resource

Semantic 必须显式填写。Color 可为 linear/sRGB；Normal/Data 只能 linear。FullChain 默认按 max(1,floor(previous/2)) 到 1x1，BaseOnly 必须显式选择。未知 enum、零 limit、错误 row pitch、越界 mip 或 source/chain budget 都 fail closed。

3. 失败模式与调试入口

  • TruncatedSource/MalformedSource：看 Inspect/Decode stage 与 fixture mutation；PNG CRC 会报告 field=crc。
  • UnsupportedColorProfile：输入 transfer/ICC 无法精确表达为 linear 或 sRGB，禁止静默近似。
  • ImageLimitExceeded：检查 source、dimension、mip 或 chain limit；失败发生在对应 allocation 前。
  • InvalidInput：优先检查缺失 semantic、Normal/Data+sRGB、未知 enum 或 chain layout。
  • RHI realization 失败：检查 format plan、device capability、CopyDestination usage、row pitch 和失败 mip。

四、技术架构与关键决策

1. 技术栈与基础设施

C++20、传统 header/source、SCons 4.10.1；std::span 传递 bounded bytes，shared_ptr<const T> 持有 immutable payload，std::optional 表达 source metadata 与请求覆盖。stb_image 2.30 使用 STBI_NO_STDIO、STBI_NO_SIMD 且仅开启 PNG/JPEG/HDR；第三方 warning 只在 wrapper translation unit 隔离。

2.2 数据流与资源流

Source bytes 的 SHA-256 成为 provenance；canonical top-left base bytes 与 interpretation 生成 Image content digest；Texture digest 再加入 semantic、color、mip policy、limits 和每级 bytes。Realizer 不改这些 bytes：仅在目标 RHI 不支持 RGB/RG color layout 时建立临时 RGBA buffer，按 mip 升序调用同步 upload。Vulkan native path 用 host-visible staging buffer，执行 Undefined/ShaderRead 到 TransferDst、copy、再到 ShaderReadOnly 的 barrier，并等待 fence 后才返回 success。

2.3 关键诊断与可视化

Result 用于程序分支；diagnostic 补充 stage/code/subject/participant/field/limit；inspection 汇总 metadata 与 payload facts。它们不记录 address、thread ID、timing 或任意 native error text，因此 20 次重复和三平台可以做 exact compare。Fixture manifest 固定 source digest、decoded facts 与 mutation provenance。

3. 架构决策记录 (ADR)

(1) CPU RGB 保留，GPU expansion 后移

决策：Asset 保留 RGB8/RGB32F；Renderer 必要时扩成 RGBA。背景：很多 GPU portable formats 不保证三通道支持。否决：import 时统一 RGBA，会改变 source-class payload、浪费 CPU/cook 空间。后果：Asset evidence 更忠实，但 realization 有短生命周期转换成本。

(2) sRGB 使用 checked literal LUT

决策：8-bit sRGB 转 linear 使用 Q0.24 table，inverse 取确定性最近项；alpha 独立算术平均。否决：运行时 pow 可能因 libm/编译器产生边界字节差异。后果：跨平台 exact bytes 可验证，代价是固定 256-entry table。

(3) Native upload 服从 RHI 同步语义

决策：native staging/copy/barrier/fence 全部完成后再返回。否决：先返回 pending 再由隐式 queue 追踪，这会提前引入 async handle 与 cancellation。后果：当前接口简单可靠；Feature 026 再以新 lifecycle contract 引入异步。

(4) Import publication 是最后一步

决策：Image 与 Texture 全部验证后才提交一个 registry batch。否决：先注册 Image 再生成 Texture，mip 失败会留下孤儿记录。后果：峰值临时内存稍高，但 registry reader 永远只观察完整状态。

六、设计巧思与最佳实践

1. 当前业务场景与业务模型的最佳实践

  • Semantic 是数据 contract：同一 source 可成为 Color、Normal 或 Data，不允许 importer 猜测文件用途。
  • 方向只规范化一次：Asset 固定 top-left，Renderer 禁止 source-format V flip，避免 PNG/JPEG/HDR 各走一套坐标约定。
  • Capability mismatch 在 adapter 解决：RGB 扩展不是 codec 责任，也不是 RHI 对资产含义的猜测。
  • 先 checked arithmetic 再 allocation：dimension、row、mip、chain 全部以 uint64 检查，恶意 header 不能诱导 wraparound。
  • Native proof 不可伪造：runtime unavailable 是有效结果，但 deterministic fallback 不能满足 native readback gate。

2. 优化方案与收益

已实现的优化包括 <=64 KiB probe、只读 immutable source/payload、RGB 保留、按需短期 expansion、紧凑 row upload、mip 顺序复用以及 deterministic fallback。它们分别控制 I/O、并发共享、CPU/cook 占用、转换峰值与调试成本。后续 KTX2 可在不改 FAssetId 的前提下用 target profile 选择压缩 payload。

3. 已知限制与后续演进

stb decode 仍是 source-time 路径；没有 compression、streaming、hot reload 或 async manager。Native upload 当前为同步测试友好的路径，不是高吞吐 upload queue。021 的 exact CPU corpus、RHI upload contract 与 rollback tests 将成为 022 KTX2、026 runtime manager 和 028 residency 重构时的回归基线。

七、编程语言知识点

1. 标准库接口与用法

std::span 让 parser 在不复制的情况下获得有界视图；std::optional 区分 source 未声明 transfer 与明确设置；std::shared_ptr<const T> 共享 immutable mip storage；std::bit_cast 明确 float 字节编码；std::lower_bound 对 Q0.24 LUT 做确定性 inverse；std::numeric_limits 驱动 overflow 与 non-finite 边界测试。

2. 语言特性与惯用法

enum class 表达 format/semantic/stage，并对未知 cast 值 fail closed；constexpr std::array 固定 transfer evidence；[[nodiscard]] 迫使调用方处理 result；move-only temporary arrays 降低 payload copy；virtual overload 的默认实现保持 Feature 020 importer 源兼容，同时为 021 增加 diagnostic sink。

3. 平台相关与编译器行为

MSVC、Clang、GCC 使用相同 scalar decode/mip contract；禁用 stb SIMD 可减少不同 ISA decode path。sRGB 不调用平台 libm。Vulkan native 代码由 SDK/runtime capability 守卫；Windows/Linux/macOS 都必须编译，只有真实 runtime 可用时才要求 readback success。ThreadSanitizer 独立于 ASan/UBSan 构建，因为这些 sanitizer 不可组合。

八、软件工程知识点

1. 设计模式与架构模式

IAssetImporter 是 Strategy；FAssetImportService 是 orchestration service；FTextureAssetRealizer 是跨层 Adapter；FImageAsset/FTextureAsset 是 immutable Value Object；RHI mock 与 Vulkan fallback/native 共享 Contract Test。每个模式都对应所有权边界，而不是只为命名增加类。

2. 工程原则与方法论

Dependency Inversion 让 Renderer 依赖 RHI interface，而 Asset 不知道 GPU；YAGNI 把 compression/async/streaming 留给明确 feature；Design by Contract 把 semantic、layout、limit 与 lifecycle 前置验证；deterministic evidence 让跨平台 CI 比较事实而非日志措辞。

3. 测试策略与质量保障

lossless fixture 检查 exact bytes，JPEG 检查固定 canonical decode evidence；合成 2x2/3x1 mip 用等价类直接证明数学；mutation/limit 属于 negative 与 boundary testing；mock RHI 证明 portable contract，native Vulkan 证明 API mapping；architecture scanner 则证明错误依赖没有进入生产边界。

九、渲染、引擎与图形 API 学习笔记

1. 本期核心概念拆解

  • sRGB 是解释而非不同像素结构：存储仍是 8-bit channel，但过滤必须先映射到 linear light。
  • Normal map 是向量场：channel 平均后必须重新归一化；近零向量使用稳定 +Z。
  • Image layout 是 GPU 状态：Asset top-left origin 与 Vulkan VkImageLayout 是完全不同的两个“layout”概念。
  • Upload success 是可见性承诺：同步 RHI API 返回后，命名 mip 必须 sample-ready，不能只表示 staging 已排队。

2. 本期核心摘要

为引擎 Core 层实现结构化日志系统和运行时断言宏——引擎最基础的可观测性基础设施。 日志系统提供五级严重性（Verbose → Fatal）、类别过滤、宏级别零开销早期过滤和线程安全控制台输出； 断言宏提供 Debug 构建中的条件检查与调试器断点，Release 构建中完全编译移除。

二、目标与边界

1. 业务与功能目标

引擎开发者需要在开发和调试过程中观察引擎行为、追踪执行流程和诊断问题。本子系统解决四个核心痛点：

US1 — 引擎开发者记录诊断消息 P1 MVP

使用 SG_LOG 宏在任意引擎层发出带类别和严重性的结构化日志消息，无需任何初始化代码。

US2 — 引擎开发者捕获无效状态 P1

使用 SG_CHECK / SG_VERIFY / SG_CHECKF 在运行时验证假设和不变量，Debug 构建中报告失败位置。

US3 — 按类别过滤日志输出 P2

配置日志系统仅显示特定类别或特定严重性以上的消息，实现聚焦调试。

US4 — 声明自定义日志类别 P2

新子系统开发者可以声明自己的日志类别（如 LogMeshlet），自动注册并可用于过滤。

2. 架构目标与定位

日志与断言系统位于引擎的最底层（Core 层），是所有上层模块的基础依赖。它不依赖任何图形 API 或上层模块。

三、交互与产品设计

1. 用户使用路径

(1) 日志使用路径

// 1. 在任意引擎源文件中包含 CoreMinimal.h（通常已包含）
#include "Core/CoreMinimal.h"

// 2. 直接使用 SG_LOG 宏 —— 无需任何初始化
SG_LOG(LogCore, Info, "Engine initialized version %d.%d", 1, 0);
SG_LOG(LogRHI, Warning, "Buffer size %zu exceeds limit", size);
SG_LOG(LogRenderer, Error, "Failed to compile shader: %s", name);

// 3. 声明自定义类别（头文件中）
SG_DECLARE_LOG_CATEGORY_EXTERN(LogMeshlet, ELogSeverity::Verbose)

// 4. 定义自定义类别（源文件中）
SG_DEFINE_LOG_CATEGORY(LogMeshlet)

// 5. 使用自定义类别
SG_LOG(LogMeshlet, Info, "Processing cluster %d", id);

(2) 断言使用路径

// SG_CHECK — Debug 构建中检查，Release 中完全移除
SG_CHECK(ptr != nullptr);

// SG_VERIFY — 所有构建中都执行表达式，仅 Debug 中检查结果
SG_VERIFY(Initialize());

// SG_CHECKF — 带格式化消息的断言
SG_CHECKF(index < count, "Index %d out of range [0, %d)", index, count);

2.3 关键性能特性

宏级别零开销早期过滤

当消息被过滤时，SG_LOG 宏仅执行一次整数比较——不调用任何函数、不格式化字符串、不求值参数：

#define SG_LOG(Category, Severity, Format, ...) \
    do { \
        if (static_cast<int>(ELogSeverity::Severity) >= \
            static_cast<int>(Category.GetMinSeverity())) \
        { \
            FLog::LogMessage(Category, ELogSeverity::Severity, \
                __FILE__, __LINE__, Format, ##__VA_ARGS__); \
        } \
    } while (0)

线程安全策略

消息格式化在调用者栈上完成（无锁），仅在写入 Sink 时获取 std::mutex，最小化临界区：

// 1. 格式化 (无锁, 调用者栈上)
char UserBuffer[1024];
std::vsnprintf(UserBuffer, sizeof(UserBuffer), Format, Args);

// 2. 写入 (加锁, 最小临界区)
{
    std::lock_guard<std::mutex> Lock(GLogMutex);
    FLogConsoleSink::Write(Severity, FinalBuffer);
}

3. 架构决策记录 (ADR)

ADR-1: 日志消息格式化策略 — 选择 vsnprintf + 1024 字节栈缓冲区

决策：使用 vsnprintf 配合 1024 字节固定栈缓冲区。超长消息截断并附加 ... 指示符。

理由：栈缓冲区避免了常见情况下的堆分配（大多数日志消息远小于 1KB）。截断对诊断消息是可接受的。vsnprintf 是安全的（无缓冲区溢出）且在所有目标平台可用。

被否决的方案：① vasprintf 动态堆分配（不必要的复杂性和堆压力）；② std::format（规范明确选择 printf 风格以获得更广泛的编译器兼容性）；③ fmt::format 第三方库（学习导向项目不引入外部依赖）。

ADR-2: 宏级别早期过滤 — 选择 if 语句内联检查

决策：SG_LOG 宏展开为 if 语句，在求值任何格式参数或调用任何函数之前检查类别的当前最低严重性。

理由：规范 FR-016 明确要求——被过滤消息的开销最多为一次整数比较。宏读取类别的 MinSeverity 字段并与消息严重性比较。

被否决的方案：① 在 FLog::LogMessage 内部格式化后过滤（违反 FR-016）；② 编译时剥离 SG_LOG_STRIP_BELOW_WARNING（本阶段不需要）。

ADR-3: 线程安全日志输出 — 选择 std::mutex 最小临界区

决策：使用单个 std::mutex 序列化 Sink 写入。格式化在调用者栈上完成（无锁），仅写入时加锁。

理由：规范假设尚无自定义线程库。std::mutex 是最简单的正确方案。格式化在获取锁之前完成，最小化竞争。

被否决的方案：① 无锁环形缓冲区 + 后台写入线程（过度工程化）；② 每 Sink 独立 mutex（仅一个 Sink，不必要的抽象）；③ 无同步（违反 FR-013）。

ADR-4: 日志类别注册模式 — 选择静态自注册

决策：每个 FLogCategory 实例在构造函数中自注册到全局类别列表。类别使用声明宏作为全局/静态变量声明。

理由：镜像 UE5 的 DECLARE_LOG_CATEGORY_EXTERN / DEFINE_LOG_CATEGORY 模式。静态初始化确保类别在 main() 之前可用（FR-014 零配置启动）。

被否决的方案：① 显式 FLog::RegisterCategory() 调用（违反 FR-014）；② 编译时模板元编程类别表（过于复杂）。

ADR-5: 平台调试器断点 — 选择 __builtin_debugtrap()

决策：提供 SG_DEBUG_BREAK() 宏，展开为平台特定的调试器断点内联函数。MSVC 使用 __debugbreak()，GCC/Clang 使用 __builtin_debugtrap()。

理由：使用 __builtin_debugtrap() 而非 __builtin_trap()，因为 debugtrap 是可恢复的（开发者可以在调试器中继续），而 trap 不可恢复。

被否决的方案：① raise(SIGTRAP)（Windows 不可用）；② 所有平台 std::abort()（失去调试器断点能力）。

ADR-6: Fatal 日志 vs 断言失败行为分离

决策：实现两条不同的终止路径：

  • 断言失败（SG_CHECK）：日志 → SG_DEBUG_BREAK()（仅 Debug）。不调用 std::abort()。开发者可继续。
  • Fatal 日志（SG_LOG(Cat, Fatal, ...)）：日志 → SG_DEBUG_BREAK()（仅 Debug）→ std::abort()（始终）。

理由：断言是"软停止"用于捕获开发中的 bug。Fatal 日志是"硬停止"用于不可恢复错误。行为差异是有意的。

ADR-7: 控制台输出格式 — 选择 [HH:MM:SS.mmm] Cat: Sev: Msg

决策：使用格式 [HH:MM:SS.mmm] CategoryName: SeverityLabel: Message\n。

理由：紧凑、可扫描。毫秒精度对时间敏感的调试有用。类别和严重性清晰标记，便于 grep/过滤工作流。无日期组件——开发期间日志会话通常短暂。

被否决的方案：① ISO 8601 完整时间戳（控制台输出过于冗长）；② ANSI 彩色代码（不可移植）；③ UE5 风格带日期格式（本阶段不必要）。

ADR-8: 验证策略 — 选择自定义断言处理器注入

决策：提供 FLog::SetAssertionHandler() 允许测试拦截断言失败。生产环境使用默认处理器（SG_DEBUG_BREAK()），测试中使用自定义处理器记录失败详情。

理由：避免 fork/exec 子进程测试的复杂性。SC-003 要求 100% 覆盖断言行为。

被否决的方案：① Fork/exec 子进程（复杂且平台依赖）；② 跳过断言失败测试（违反 SC-003）。

六、设计巧思与最佳实践

6.1 当前业务场景与业务模型的最佳实践

为什么使用宏而非模板/函数作为日志入口

宏级别早期过滤是零开销的关键：当消息被过滤时，不求值格式参数、不调用任何函数，仅执行一次整数比较。如果使用函数或模板，参数求值（包括可能昂贵的字符串格式化）会在过滤判断之前发生，违反 FR-016 零开销要求。

为什么断言和 Fatal 日志行为分离

断言是"软停止"——开发者在调试器中可以继续执行，用于捕获开发中的 bug。Fatal 日志是"硬停止"——不可恢复错误必须终止进程。两条路径的行为差异是有意的设计，让开发者可以根据场景选择合适的诊断工具。

为什么使用静态自注册而非显式注册

日志类别使用静态自注册模式（构造函数中注册到全局列表），镜像 UE5 的 DECLARE_LOG_CATEGORY_EXTERN / DEFINE_LOG_CATEGORY 模式。这保证了类别在 main() 之前可用，实现零配置启动——开发者无需在任何初始化代码中手动注册类别。

为什么格式化在调用者栈上完成

消息格式化使用 1024 字节栈缓冲区，在获取 mutex 之前完成。这最小化了临界区（仅 Sink 写入时加锁），减少线程竞争。大多数日志消息远小于 1KB，栈分配避免了堆分配的开销和碎片化。

为什么选择 __builtin_debugtrap 而非 __builtin_trap

__builtin_debugtrap() 是可恢复的——开发者可以在调试器中按"继续"跳过断点。而 __builtin_trap() 不可恢复，会直接终止进程。对于断言失败场景，可恢复性让开发者能够检查状态后决定是否继续，极大提升调试效率。

6.2 优化方案与收益

七、编程语言知识点

7.1 标准库接口与用法

接口含义与用法
std::mutex 互斥锁，保护 Sink 列表的并发写入。lock() 获取锁，unlock() 释放锁。本项目中用于保证多线程日志写入的原子性。
std::lock_guard<T> RAII 锁守卫，构造时自动 lock，析构时自动 unlock。避免忘记释放锁导致死锁。用于 FLog::LogInternal() 的临界区。
std::vector<T> 动态数组，用于存储已注册的 Sink 列表和 LogCategory 列表。支持 push_back()、迭代器遍历。
std::vsnprintf() 格式化字符串到固定大小缓冲区，返回实际需要的字符数（不含 null）。用于在栈缓冲区上完成日志消息格式化，避免堆分配。
std::abort() 立即终止进程，不执行析构函数。用于 Fatal 级别日志的终止行为——不可恢复错误必须立即停止。
std::strcmp() C 风格字符串比较，返回 0 表示相等。用于 LogCategory 名称比较。
va_list / va_start / va_end C 可变参数机制。宏将格式参数传递给内部函数，内部函数使用 va_list 解析并调用 vsnprintf 格式化。

7.2 语言特性与惯用法

预处理器宏与条件编译

SG_LOG、SG_CHECK、SG_VERIFY 使用宏实现零开销过滤。#if SG_BUILD_DEBUG 控制断言在 Release 中完全移除。宏的关键优势：参数在条件不满足时不求值，这是函数/模板无法做到的。

可变参数宏 (__VA_ARGS__)

SG_LOG(Category, Level, Fmt, ...) 使用 __VA_ARGS__ 将格式化参数透传给内部函数。##__VA_ARGS__（GNU 扩展）在无额外参数时移除前导逗号。

静态局部变量与自注册

FLogCategory 使用构造函数中的自注册模式：静态局部变量在首次执行时构造（C++11 保证线程安全），构造函数将 this 注册到全局列表。这保证了类别在 main() 之前可用。

do { ... } while(0) 宏惯用法

多语句宏使用 do { ... } while(0) 包裹，确保宏在 if/else 等控制流中行为正确。这是 C/C++ 宏编程的标准惯用法。

栈缓冲区 vs 堆分配

char Buffer[1024] 在函数栈帧上分配，生命周期自动管理，无需 new/delete。对于已知上限的短字符串（日志消息），栈分配比堆分配快一个数量级且无碎片化。

八、软件工程知识点

8.1 设计模式与架构模式

Observer / Sink 模式

日志系统使用 Sink 模式（Observer 变体）：FLog 是 Subject，ILogSink 是 Observer 接口。多个 Sink 可以同时注册（控制台、文件、网络），日志消息广播给所有已注册 Sink。这实现了日志生产者和消费者的解耦。

Facade 模式

FLog 作为日志子系统的统一入口（Facade），隐藏了 Category 管理、Level 过滤、格式化、Sink 分发等内部复杂性。调用方只需 SG_LOG(Cat, Level, Fmt, ...) 一行代码。

Self-Registration 模式

FLogCategory 在构造时自动注册到全局列表，无需显式初始化代码。这是 UE5 中 DECLARE_LOG_CATEGORY / DEFINE_LOG_CATEGORY 的核心模式——利用静态变量的构造顺序实现"声明即注册"。

8.2 工程原则与方法论

零开销抽象 (Zero-Overhead Abstraction)

日志宏在消息被过滤时不产生任何运行时开销——不格式化、不调用函数、不求值参数。这体现了 C++ 的核心哲学："你不用的东西，不应该为之付出代价"。

契约式设计 (Design by Contract)

SG_CHECK 和 SG_VERIFY 是契约式设计的实现工具。前置条件（precondition）通过断言在开发期强制执行，违反时立即暴露 bug。Release 中移除断言是因为"契约已在开发期验证通过"。

防御性编程 (Defensive Programming)

Fatal 日志路径使用 std::abort() 确保不可恢复错误不会被忽略。SG_VERIFY 保证即使在 Release 中，副作用表达式仍然执行。这些都是防御性编程的体现——假设调用方可能犯错，系统应该安全地处理。

关注点分离 (Separation of Concerns)

日志系统分为三个独立关注点：① Category 管理（谁产生消息）；② Level 过滤（什么消息需要处理）；③ Sink 输出（消息去哪里）。每个关注点可以独立扩展而不影响其他部分。

8.3 测试策略与质量保障

行为驱动测试 (Behavior-Driven Testing)

测试名称描述行为而非实现（如"filtered message produces zero overhead"而非"macro expands to if-check"）。这样当内部实现变化时，只要行为一致，测试无需修改。

边界值测试 (Boundary Testing)

测试覆盖关键边界：空格式字符串、超长消息（超过栈缓冲区）、所有日志级别的过滤行为、Fatal 后的终止行为、断言在 Debug/Release 的不同表现。

编译期验证

部分正确性通过编译期保证：SG_CHECK 在 Release 中展开为空（编译器验证无副作用警告）；ELogLevel 枚举保证级别值的类型安全；ILogSink 纯虚接口保证 Sink 实现的完整性。

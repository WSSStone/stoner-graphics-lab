2. 本期核心摘要

交付 Core 诊断系统：分类日志、严重性过滤、控制台 sink、线程安全输出和 SG_CHECK/SG_VERIFY/SG_CHECKF 断言宏。它为后续 platform、RHI、Vulkan 和 Renderer 提供统一的错误观察入口。

最值得学习的是“诊断是工程 API 的一部分”：日志类别、严重级别、断言和 fatal 行为必须有明确边界。图形后端尤其需要在 runtime 不存在、SDK 缺失、资源不兼容时留下可复现证据，而不是只返回 false。

3. 上下文与依赖

  • 前置依赖：003 Core vocabulary and 004 math tests
  • 后续铺路：platform diagnostics, Vulkan runtime/fallback markers, render graph debug dumps
  • 层级边界：Core 只向下依赖已稳定 contract，不能反向 include 更高层模块。
  • 编译期依赖：公共头和 SCons 目标；概念依赖：spec/plan/tasks 中定义的 lifecycle、result、diagnostic 与测试替身。

二、目标与边界

1. 业务与功能目标

  • 开发者能用 SG_LOG 按类别和严重性记录消息。
  • 断言宏在 debug 场景可触发 break，在测试中可观测。
  • 自定义日志类别能静态注册并参与过滤。
  • 日志输出在多线程中保持单条消息原子性。

2. 架构目标与定位

Application / Tests
    ↓ 使用 public contract
Core feature: Core Logging & Assertions
    ↓ 依赖稳定下层能力
Core vocabulary / diagnostics / platform
    ↓ 按阶段连接
RHI contracts / Backend implementations / Renderer systems

本阶段的 public contract 是调用方可以依赖的最小稳定面；private implementation、测试替身和 backend-specific helper 都不能反向污染上层 API。

3. 边界与非目标（约束）

  • 不实现异步日志队列，当前吞吐不是瓶颈。
  • 不引入 fmt/spdlog，避免基础层外部依赖。
  • 不做文件 sink 和远程 telemetry，后续工具链阶段再接入。

三、交互与产品设计

1. 用户使用路径

调用 SG_LOG -> 宏层判断类别和严重性 -> 格式化消息 -> FLog 分发给 sink -> console sink 原子写出。调用 SG_CHECKF -> 条件失败时记录 assert diagnostic -> 触发平台 break 或测试替身观察。

学习时建议把这一段当成“最小工作流”：先找到输入对象，再跟踪它如何变成状态、诊断、测试断言或 debug dump。

2. 核心规则与状态机

未创建/空状态
    -> 描述或 Begin/Declare/Create
    -> 可验证中间状态
    -> Success: 可查询、可绑定、可执行或可复用
    -> Reset/Shutdown/Invalidated
    -> 任何后续使用必须返回错误结果或诊断

这个状态机是本项目底层模块的共同风格：显式创建、显式验证、显式失效。不同 feature 的状态名不同，但测试都围绕“合法转换”和“非法转换可观察”展开。

3. 失败模式与调试入口

  • 日志过滤如果发生在格式化之后，disabled verbose 仍会产生无谓分配和字符串成本。
  • 断言和 Fatal 若语义混杂，测试无法安全覆盖 fatal-like 行为。
  • 静态注册顺序必须谨慎，否则类别在 main 前后的生命周期会变成隐性 bug。

调试入口优先看 Tests/LoggingAssertionTests.cpp 中的负路径用例，再看对应 diagnostics、result code 或 debug dump 输出；这些测试比源码更快暴露设计意图。

四、技术架构与关键决策

1. 技术栈与基础设施

  • C++20，传统 header/source 分离；公共 API 遵守项目 UE-style 命名。
  • SCons 4.10.1 构建；验证入口保持在单一 StonerTest 可执行文件。
  • Core/RHI/Renderer public contract 尽量不泄漏 backend 或平台实现细节。
  • headless、fallback 和 mock 测试优先保证无 GPU/无窗口环境仍能验证语义。

2.2 数据流、控制流或资源流

调用 SG_LOG -> 宏层判断类别和严重性 -> 格式化消息 -> FLog 分发给 sink -> console sink 原子写出。调用 SG_CHECKF -> 条件失败时记录 assert diagnostic -> 触发平台 break 或测试替身观察。

2.3 关键日志、诊断与可视化

诊断记录应覆盖失败原因、对象状态、兼容性判断和 deterministic ordering；result code 负责控制流，diagnostic/debug dump 负责解释“为什么”。不记录大块二进制或平台私有句柄，避免输出不可复现。

3. 架构决策记录 (ADR)

(1) 日志入口使用宏

背景：需要保留调用点表达式、文件行号和早期过滤。

理由：宏能在 disabled path 避免格式化成本。

被否决方案：纯函数接口：更安全但失去零成本过滤和调用点上下文。

后果：宏需要严格 do-while 包装和测试覆盖。

(2) 断言与日志分离

背景：日志是观察，断言是契约失败。

理由：二者共享诊断基础但保持不同控制流。

被否决方案：所有错误都用日志：会让不可恢复状态继续执行。

后果：调用方需要选择合适宏，文档要说明边界。

六、设计巧思与最佳实践

1. 当前业务场景与业务模型的最佳实践

(1) Category filtering

是什么：大型引擎日志必须可局部打开，否则信号会被噪声淹没。

项目表达：FLogCategory 记录类别状态，SG_LOG 在调用点快速过滤。

真实引擎/API 对应：Vulkan validation、Renderer graph dump、asset import 都需要按子系统过滤。

(2) Assertion as contract

是什么：断言表达“这里不应该发生”。

项目表达：SG_CHECK/VERIFY 把条件和可调试 break 连接起来。

真实引擎/API 对应：图形 API 的 invalid usage 往往应在 debug 早停，而 runtime failure 则返回 result。

(3) Sink abstraction

是什么：日志产生和日志去向分离。

项目表达：FLog 分发，FLogConsoleSink 只是一个输出目标。

真实引擎/API 对应：真实引擎会扩展到文件、IDE console、remote profiler。

2. 优化方案与收益

本阶段的优化重点不是追求最终性能，而是建立可替换的语义基线：先让行为被测试锁住，再在未来引入 SIMD、真实 Vulkan runtime、更复杂 allocator、pipeline disk cache、render graph aliasing 或 async compute。

这种做法的收益是 migration cost 可控：只要 public contract 和测试矩阵稳定，private implementation 可以逐步从 mock/fallback 演进到真实 GPU 路径。

七、编程语言知识点

1. 标准库接口与用法

本项目优先使用标准库可移植能力，例如容器、智能指针、字符串、chrono、filesystem、mutex 和 algorithm。关键不是“用了哪个库”，而是把标准库行为包装进项目自己的 contract，减少跨模块直接耦合。

2. 语言特性与惯用法

  • RAII/ownership：资源对象在 shutdown/invalidate 时显式失效，避免悬空后继续成功。
  • enum class：用强类型枚举表达 result、queue、usage、stage、state，避免整数误传。
  • 值语义和移动语义：desc、handle、record 适合轻量复制；拥有对象则通过指针或明确 lifecycle 管理。
  • 宏只用于日志/断言等需要调用点上下文的场景，其余优先函数和类型系统。

3. 平台相关与编译器行为

平台相关代码应留在 Core platform 或 Backend private 边界内。公共头尽量避免平台宏分叉和图形 API 头泄漏，这样 Windows/macOS/Linux 与未来 Vulkan/DX/Metal/OpenGL backend 才能共享上层代码。

八、软件工程知识点

1. 设计模式与架构模式

  • Layered Architecture：Core -> RHI -> Backend/Renderer 的依赖方向必须单向。
  • Facade/Aggregate Header：CoreMinimal、RHIMinimal 或 RendererMinimal 提供便利入口，但不能隐藏边界污染。
  • Builder/Compiler/Executor：复杂声明式系统先收集意图，再编译计划，最后执行。
  • Adapter：Backend/Vulkan 把具体 API 对象适配成 RHI contract。

2. 工程原则与方法论

  • Contract-first：先定义 public behavior，再实现 backend 或优化。
  • Fail fast but diagnosable：错误尽早返回，同时留下能解释原因的记录。
  • Determinism：排序、dump、fallback 和测试输出都尽量稳定。
  • YAGNI with escape hatch：推迟工业级复杂能力，但保留未来接入点。

3. 测试策略与质量保障

测试不是只证明“代码能跑”，而是把工程假设固化下来：合法路径、非法路径、边界隔离、重复运行稳定性和 fallback/headless 环境都应该被覆盖。对图形工程而言，mock 与 fallback 不是偷懒，而是让 CI 可以在没有真实 GPU 的情况下守住 contract。

2. 本期核心摘要

本期交付 Renderer 层第一个 Forward Renderer 规划面：调用方可以提交 view、output、draw candidates、PBR-style material binding、directional/point lights 和 sky/background 输入，得到确定性的 frame plan、pass order、render graph-compatible resource declarations、diagnostics 和 debug dump。它还支持默认 4 个 point light 的可配置裁剪、按影响力排序、透明物体 back-to-front 排序，以及无 accepted light 时的 ambient-only fallback。

学习价值在于：这不是“画出一帧”的最终后端，而是把可见渲染前的 frame planning contract 建起来。真实引擎里，Forward/Deferred/Meshlet/RayTracing 都需要先把 view、draw、material、light、resource requirement 组织成可验证计划，再交给 Render Graph 和 backend 执行。本期正是这个中间层。

3. 上下文与依赖

  • 建立在 Phase 012 Render Graph Foundation 和 Phase 013 Material & Shader System 之上。
  • 向后铺路给 Phase 017 Triangle Demo、Phase 018 Deferred Rendering、Phase 019 Meshlet、Phase 020 Ray Tracing。
  • 编译期依赖 Core math/container/string 与 Renderer material/resource contracts；概念上依赖 RHI resource/result 语义，但不暴露 backend handle。
  • 继续维持 Application/Renderer/RHI/Backend/Core 的层级边界：Renderer forward public contract 不包含具体图形 API 或 presentation 细节。

二、目标与边界

1. 业务与功能目标

引擎开发者现在可以在 headless 测试中准备一帧 forward rendering workload：验证 camera/output、筛选 opaque 和 transparent draw、验证完整 PBR-style 输入、选择 light set、声明 depth/opaque/sky/transparent pass，并通过 debug dump 比对确定性。

2. 架构目标与定位

Application / future Scene
    -> submits frame-like inputs
Renderer Forward Pipeline
    -> validates view, output, materials, draws, lights
    -> emits frame plan + graph-compatible declarations
Renderer Render Graph / Material System
    -> consumes pass/resource intent
RHI / Backend
    -> future execution path, not owned by this feature
Core
    -> math, strings, containers, diagnostics foundation

public contract 包括 FForwardRenderer、FForwardFramePlan、FForwardViewData、FForwardLightSet、FMeshDrawCommand 和 FForwardRenderGraphDeclaration。private implementation 负责排序、验证、diagnostic 合并、debug dump 格式和 declaration 组装。

3. 边界与非目标（约束）

  • 不执行真实 GPU command：本阶段只输出计划和声明，避免把 backend runtime 成败混入 Renderer contract。
  • 不做 presentation、display surface、user input：这些属于 Application/demo 集成阶段。
  • 不做 shadow mapping、post-processing、deferred rendering：它们需要更多 pass/resource policy，后续独立 feature 接入。
  • 不做 runtime shader compilation 或 shader file loading：Material & Shader System 当前使用显式内存记录，forward 只消费 material/resource summary。

三、交互与产品设计

1. 用户使用路径

happy path 是创建 FForwardFrameInputs，填入 view、output、draw candidates、lights 和 environment，然后调用 FForwardRenderer::PrepareFrame。成功时得到 FForwardFramePlan，其中包含 pass order、accepted/rejected draws、accepted/rejected lights、graph declaration、diagnostics 和 debug dump。

FForwardRenderer Renderer;
FForwardFramePlan Plan;
EForwardResult Result = Renderer.PrepareFrame(Inputs, Plan);
// Result == Success
// Plan.PassOrder: Depth -> Opaque -> SkyBackground -> Transparent
// Plan.GraphDeclaration: resources/accesses/outputs
// Plan.DebugDump: stable text for regression tests

2. 核心规则与状态机

Draft renderer
    -> PrepareFrame(valid view + output)
    -> Accepted frame plan
    -> Reset back to Draft
    -> Invalidate blocks future trusted state until reset/reconfiguration

view/output 是硬门槛，失败时不会继续生成 render-ready plan。draw/material/light 是逐项验证：无效 draw 或 light 会被拒绝并产生 deterministic diagnostic，但只要必要输入仍有效，frame plan 可以继续生成。

3. 失败模式与调试入口

  • invalid view：看 FWD-VIEW-* 诊断，例如 extent、camera、matrix。
  • missing output：看 FWD-OUTPUT-*，它会在 pass order 最终化之前失败。
  • incomplete PBR：看 FWD-PBR-*，用于定位 BaseColor/Metallic/Roughness/Normal/Occlusion/Emissive/Alpha 缺项。
  • excess point lights：看 FWD-POINT-LIMIT 和 AcceptedPointLights 排序。
  • transparent sorting：看 Plan.AcceptedTransparentDraws 和 debug dump 中的 depth/material/object key。

四、技术架构与关键决策

1. 技术栈与基础设施

  • C++20，传统 header/source 分离，无 C++20 Modules。
  • SCons 4.10.1 自动发现 Renderer private source 与 Tests source。
  • 无新增外部 SDK；不依赖 Vulkan SDK 或平台 presentation runtime。
  • 测试走 headless 单可执行文件 StonerTest，适合 CI 和无显示设备环境。

2. 关键信息

2.1 模块对应关系

2.2 数据流、控制流或资源流

数据流为：输入 frame desc -> validate view/output -> validate draw/material -> sort opaque/transparent -> validate/select lights -> decide ambient fallback -> append passes -> declare graph resources/accesses -> sort diagnostics -> build debug dump。每一步都只消费上一阶段确定下来的抽象数据，不持有 backend command buffer 或 live resource。

2.3 关键日志、诊断与可视化

诊断记录 stable code、severity、category、subject 和 message，不记录指针地址、平台 handle 或运行时不可复现值。debug dump 包含 frame summary、view/output、pass order、draw identity、light counts、background、fallback 和 graph declarations，用于 20 次重复准备的 byte-stable 检查。

3. 架构决策记录 (ADR)

(1) 先做 frame planning，不做真实执行

背景：Forward Rendering 是 Renderer 与 Render Graph/Material System 的第一个 frame-level 接点。直接接真实 backend 会把 execution、presentation、shader runtime 都混在一起。

理由：frame plan 和 declaration 是后续所有 backend 执行路径的共同输入，先稳定它能减少后续返工。

被否决方案：直接录制 RHI command 或创建真实 graphics pipeline。这样会跳过当前 feature 的 headless 可测边界。

后果：本期还不是可见画面，但 Triangle Demo 可以在更稳定的 frame contract 上继续推进。

(2) Point light default 4 且可配置

背景：用户明确要求 8 已经偏多，默认 4，并按 distance/effectiveness 排序取前 N。

理由：这逼迫 Renderer 在 planning 阶段建立 light budget 和 deterministic ordering，避免未来 shader/light packing 无边界膨胀。

被否决方案：提交顺序取前 N。它简单但不表达“最有影响力的灯优先”。

后果：测试可以稳定覆盖 accepted/rejected counts、zero-limit fallback 和 tie-breakers。

(3) Transparent sort 不依赖提交顺序

背景：透明排序天然和 view 相关，提交顺序来自 Application/Scene，不能作为稳定渲染语义。

理由：camera-space depth descending + material id + object id 既满足 back-to-front，又让相等 depth 可复现。

被否决方案：保留 caller order 作为 tie-breaker。它会让 dump 受容器迭代顺序影响。

后果：debug dump 可做 20-run byte-stable 回归测试。

六、设计巧思与最佳实践

1. 当前业务场景与业务模型的最佳实践

(1) Draw command 是 Renderer-level description

本期的 FMeshDrawCommand 不录制 backend command，而是保存 object/mesh/material/pass/sort key/resource requirement。这样 future backend 可以消费它，但当前测试不需要真实设备。

(2) Light selection 是 planning 规则，不是 shader 细节

point light 先在 CPU planning 阶段排序和裁剪，shader 只应看到已经打包好的 light set。否则 shader path 会被输入集合大小和顺序拖入不可控状态。

(3) Diagnostics 是 public behavior

错误码如 FWD-PBR-OCCLUSION、FWD-POINT-LIMIT、FWD-AMBIENT-FALLBACK 是测试和调试入口。它们让 headless feature 也能有可靠“输出”。

2. 优化方案与收益

当前算法偏确定性和清晰性：使用 vector、sort、stable identities 和文本 dump。未来可以引入 draw batching、material pipeline key、light clustering 或 render graph compile-time optimization，但这些优化应该在 contract 不变的前提下替换 private implementation。

七、编程语言知识点

1. 标准库接口与用法

实现大量使用 std::sort、std::ostringstream、std::any_of 和 value-type records。关键点是排序比较器必须完整定义 tie-breaker，避免 equal keys 导致输出依赖原始提交顺序。

2. 语言特性与惯用法

  • enum class 用于 result、stage、category、access，避免跨领域整数误传。
  • 轻量 struct 使用值语义，frame plan 可以直接复制到 renderer last state。
  • 公共头保持抽象类型，不 include backend API，减少编译与平台耦合。

3. 平台相关与编译器行为

本期新增代码没有平台分支。构建时 macOS 工具链出现临时目录 warning，但不影响编译和测试。Windows/Linux 兼容性依据是 C++20 标准库、SCons 层级自动发现和无平台私有依赖。

八、软件工程知识点

1. 设计模式与架构模式

  • Facade：FForwardRenderer 作为 frame preparation 入口。
  • Data-oriented records：view、light、draw、resource declaration 都是可测试数据。
  • Pipeline staging：Depth -> Opaque -> SkyBackground -> Transparent 是明确 stage contract。
  • Boundary pattern：public contract 保持 backend-agnostic，private implementation 可以迭代。

2. 工程原则与方法论

本期体现的是 spec-driven 的价值：先澄清 point light budget、execution boundary、PBR input set、transparent ordering 和 no-light fallback，再写 plan/tasks/analyze，最后实现。这样代码里的每个规则都能追溯到 spec，而不是临场拍脑袋。

3. 测试策略与质量保障

forward rendering 还没有真实像素输出，所以测试必须更重视结构输出：pass order、draw order、light accepted/rejected counts、diagnostic codes、graph declaration、debug dump stability。等未来接入真实 presentation 后，这些测试仍能防止 frame planning 退化。

九、渲染、引擎与图形 API 学习笔记

1. 核心概念拆解

(1) Forward rendering

Forward path 通常在每个物体 pass 中直接结合 material 与 light。它结构简单、适合透明和小规模灯光，但 light budget 和 material validation 必须清晰，否则 shader permutation 与 draw cost 会膨胀。

(2) Render graph-compatible declarations

本期不执行 Render Graph，而是输出 pass/resource/access summary。真实 Render Graph 后续可以把这些声明编译成 lifetime、barrier 和 execution schedule。

(3) Transparent back-to-front

透明混合通常依赖绘制顺序。camera-space depth descending 是常见近似规则，material/object tie-breaker 则解决回归测试里的稳定性。

2. 跨 API 映射

API未来映射
Vulkanpass/resource/access declaration 可转为 render pass scope、image layouts、descriptor reads 和 command recording。
DX12同一 plan 可映射到 resource states、root signature/descriptor heap 和 command list。
Metal可映射到 render command encoder、resource usage 和 argument buffers。
OpenGL/GLES可用较薄的 state binding layer 消费排序后的 draw descriptions。
